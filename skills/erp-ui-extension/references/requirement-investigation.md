# Requirement investigation and scoping (steps 1-3)

Use when turning user feedback into findings (regression / never implemented / misremembered surface / order-conditional), scoping a field merge or split, bootstrapping a picker on an empty catalog, or designing a "remember what I typed" field. This is the detail behind Procedure steps 1-3 in `SKILL.md`; read only the item that matches the change.

1a. **Treat a batched UI-feedback list as an investigation, not a to-do list.** When the user sends several screenshots and a paragraph of observations and asks for "your understanding and suggestions", produce one section per item: the current implementation as it really is (read the template, route, and CSS — do not infer from the screenshot), the **root cause**, the proposed change, and the risk. Separate the items that are pure styling from the ones that are structural, because a structural one (different DOM nesting, a colliding identifier, a scope difference) cannot be fixed by restyling. Surface conflicts between items explicitly — a request that contradicts existing data or an existing rule must be raised, not silently implemented in a way that breaks it. Then ask only the **blocking** decisions (typically two: one naming/semantics collision, one scope question) and wait;
do not open the implementation plan until they are answered. Grep the test tree for assertions on each control you plan to restructure and list the tests that will need updating in the same plan. Read the current behaviour from the template and the live rendered HTML, not from the screenshot: a vision pass readily misidentifies which page an image shows and misses controls that are actually present, and a cropped region is easily misread. Use the images only to locate *what the user is pointing at*, then confirm every claim about existing behaviour in the source before proposing a change. When the user states a rule change that collides with an existing invariant (e.g. a prefix that already belongs to a sibling document type), surface the collision and the alternatives in the same reply instead of picking one silently. Locate an annotation **programmatically, not by eye**: a box drawn on a screenshot is a saturated colour, so scan the image's pixels for that colour and compute the bounding box to learn exactly which region it covers, then map that region back to the owning container in the source (the shell's top bar, a specific card,
a table cell). A zoomed vision pass over a crop loses the surrounding labels and readily misreads which container the box sits in, and a region with no text of its own is easy to attribute to the wrong element.
1b. **Classify every item into one of three kinds before proposing anything, because each needs a different reply.** The user's framing ("这个功能坏了" / "我记得之前设计过") is a hypothesis, not a finding, and the three kinds are routinely confused:
   - **Regression** — the behaviour existed and was removed. Prove it with history, not memory: `git log --oneline -S"<distinctive marker>" -- <path>` (the identifier, the CSS class, the function name — not the prose). The session that found a product picker had been replaced twice (custom combobox → two native `<select>`s → `datalist` + free text) could answer "你没记错，是被换掉了" with a commit and a version, which changes the fix from "design it" to "restore it".
   - **Never implemented** — say so plainly and show the zero: `grep -rn "<marker>" app/` returning nothing, plus `git log -S` finding no commit in the whole history, is conclusive. Do not let the user's recollection pull you into treating it as a bug.
   - **Misremembered surface** — the feature exists but on a *different* surface. An affordance designed into the **print/PDF** template (a per-slip continuation notice, a per-page subtotal) is easily recalled as belonging to the **entry page**; check the sibling surfaces before agreeing, and when the entry-page version is genuinely absent, re-frame it as a new feature with its own acceptance bar.
   - **Implemented but order-conditional** — the feature works, but only under one input sequence, so an operator who uses the other order concludes it does not exist at all and reports it as missing ("this field has no value for this record?"). The usual shape: a row-level value resolved from a form-level field **at the instant of one interaction** (a line price read when the product is picked) is never re-read when the header field changes afterwards. Prove it by driving both orders against seeded data and tabulating the result per order — that turns "no such feature" into a wiring gap with a number attached, and it is a real bug like the first kind.
   Only the first and the last are bug reports. Say which kind each item is in the first line of that item's section — the user's next decision depends on it.
1c. **When the item is "merge / split a field", scope it by grepping the symbol in both trees, then separate the data-model change from the UI change.** Count occurrences of the field name in `app/` and in `tests/` separately (a merge of two identity fields measured 273 vs 239 across 54 and 62 files) and enumerate what the change reaches: the unique index over the pair, every detail table carrying a snapshot of the field, the print template, the analysis filter that requires the first field before the second, the import header matrix, the "incomplete record" badge. Two things must be said in the reply: what the merge **fixes** (a merge of name+model dissolves the deadlock where auto-created records with an empty second field can never be given one because the pair is already taken) and what invariant it **loses**. Then offer a staged migration (data layer → surfaces → call sites/tests) with the field left in place but unused first, and ask the blocking question (the separator/format of the merged value) before opening a plan. Never open with "工程量比较大" — scope it with numbers, or the user cannot weigh it.

2a. **Before deleting a control the user calls useless, find out whether it is the only writer of a state.** "把这个按钮/原因输入框删掉" is a request about the **UI**, and it is usually satisfiable without touching the underlying mechanism — but only if you first trace what the control actually does. Check whether the control is the sole entry point to a state transition or a reversal/compensation routine (a void that reverses a posted document, a refund that restores a balance, an approval that unlocks the next state), and whether other code reads the field it writes (`status='void'`, `void_reason`, a timestamp). When it is load-bearing, say so plainly with the mechanism and the blast radius (how many tests and requirement clauses assert it), then offer the shape the user actually wants: **remove the UI, keep the mechanism** — move the transition behind the action the user does want (deleting a document auto-reverses it first) with a fixed internal reason, so the ledger stays conserved and the user never fills a form. Only strip the mechanism itself if the user, after hearing the cost, still asks for that;
then treat it as a correction-model redesign with its own plan, not a UI tidy-up. Note the ordering trap: if deletion is gated on the state the removed control produces ("must be voided before deleting"), deleting the control first makes every document permanently undeletable.

3a. **A two-level picker cannot bootstrap itself; check whether the control can express "not in the catalog yet".** A two-level picker built from the existing catalog is correct for a populated database and unusable on an empty one: with no products the dropdown has no options and the operator cannot issue the first document at all. Same for any control whose options come only from existing records. Before extending entry pages, determine whether the operator is expected to have master data already, or to grow it from documents; if the latter, the field must be free text with suggestions layered on top (a text input plus the existing autocomplete helper), where a hit binds the record id and a miss leaves plain text for the existing auto-create path. Two further checks when converting a picker to free text: give the identity its **own** input rather than one combined box, because a compound unique key cannot be expressed in a single box (the current product uses a **single-name identity**; when the project merges a second field into the name, keep one input and write the extra part into the name instead of leaving an empty second field);
and grep the form-parsing helper for every field name you add — these helpers typically read a **fixed list of keys**, so a field the service already consumes can still be missing from that list, leaving the new input decorative and silently dropping typed values. Assert the persisted value in a test rather than trusting the markup. When a page's document type rejects a not-yet-registered record (e.g. inbound requires a registered product), warn on the page before save instead of letting the server reject after the user has filled the form.
3b. **Before designing a "remember what I typed" feature, trace where that value actually lands — a submitted field can be silently discarded on one branch.** A request to remember a user-entered value (a unit, a remark, a price) presupposes the value persists today; verify that by reading the write service, not the form. The same form commonly has two branches — one that binds an existing record's id, one that creates a new record — and they can treat the submitted value **oppositely**: the id-bound branch returns the master record's own value and drops what the user typed, while the create branch adopts it and updates the master. The visible action is identical either way, so the user meets it as "I typed X and the saved document says Y" with no error surfaced anywhere;
that dropped value is a defect, and the sibling page is usually worse still — its control may not submit at all (a read-only display element carrying no `name` attribute, so `name="<field>" ` does not appear in the served HTML). Establish which case you are in by grepping the rendered page for `name="<field>"` and by reading each branch's return value, then report it as a table (branch → what the submitted value does → what the master record does) **before** proposing the feature. Aligning the branches is part of the same change, not a follow-up. **When you convert that read-only element into an editable control, every JS site that wrote to the old element must be rewritten or it throws on null.** A read-only display node is typically written from several places per page — the row binder, the picker's on-pick callback, `clearRow`, `clearAllRows`, the add-row clone reset, and any import/prefill handler — and each `tr.querySelector('.unit-display').textContent = …` becomes a `TypeError: Cannot read properties of null` the moment the node is replaced, killing the rest of that handler (reset, recalc,
focus) with no visible error. Grep the page for the **old class/module name** (`grep -n 'unit-display' <template>`) and rewrite every hit in the same edit, then re-run the extracted-JS check; a residual hit in a CSS block is harmless, one in a handler is not.
3c. **A "remember what I typed" field needs a candidate pool sourced from every table that can hold the value, and a two-control sync contract.** Once a free-text-or-pick field (a unit) is editable, the dropdown behind it must offer both the fixed defaults and every value already in the database. Source the pool as `defaults ∪ DISTINCT value` over **every** table that stores it — the master record *and* each document-line snapshot table — because the branch that must not write the master (document-type lock) keeps new values only in its own line table; a pool built from the master alone will never show them. Keep the pool in one server-side helper passed into every entry page's context (the template falls back to the default literal only for direct renders), render defaults **first in declaration order** then the rest sorted, and dedupe. Then wire the two controls: dropdown `change` → write the text input; text input `input` → set the dropdown value **and append the option first** if absent, so a value typed now is selectable without saving. Grep the templates for the hardcoded default list and delete every copy in the same change, or one sibling page silently ignores the pool.
