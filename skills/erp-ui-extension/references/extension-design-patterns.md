# Extension design patterns (step 4a-4i)

Use when designing a vertical slice or extending an accepted entry/list UI: cross-page conventions, counterparty and document direction, display precision, where page classes actually live, theme adaptation, bringing a second document type onto an accepted skeleton, consolidating per-type document lists, and the source-link preview. Detail behind Procedure step 4.

4a. **Map cross-page conventions before styling individual screens.** Create a matrix for list, detail, edit, and PDF-preview pages covering header placement, return action label/position, primary/secondary/danger button treatment, minimum button widths, and no-wrap behavior; implement one shared rule, with no return action on true top-level module pages.
4b. **Resolve counterparty and document direction before merging reconciliation records.** Classify every document as customer-side or supplier-side and as inflow, sale, return, or adjustment; only combine records that belong to the same ledger, otherwise provide separate customer and supplier reconciliation views.
4c. **Assign fields by business authority before adding them to forms.** This product has **no cost and no stock** (schema v15): purchase/inbound entry records only the counterparty price, no page shows cost, margin, or stock value, and customer-facing PDFs/statements exclude internal figures. Use separate fields or columns instead of stacking status, quantity, and price in one cell.
4d. **Define display precision before changing templates.** Preserve stored precision, format quantity according to unit semantics, format money to two decimals, and never truncate a numeric amount with an ellipsis; verify both integer-count and fractional-measure units.
4e. **Find where a page's classes are actually defined before restyling.** A class reused from a sibling template is often defined only in that sibling's page-scoped `<style>` block and renders unstyled everywhere else; extract the shared entry-page card/table/section-title rules into one common stylesheet or partial instead of copying the block or depending on load order, and re-check the original owner page after moving it. Layout variants (narrower sidebar, page-specific insets) are usually gated on a path-conditional class set by the shared layout — a path list that a newly added sibling page is typically missing, so extend that list and keep the rule in the shared layout rather than in one page's `<style>`; confirm parity by measuring the rendered geometry of every page in the family, not by eye.
4f. **Verify theme adaptation from source, not one screenshot.** Themes run on a root theme attribute plus `--token` variables; grep templates for hardcoded `#rrggbb`/`rgba(` colors and light-only utility classes (e.g. Bootstrap `.table-light`) and route them through theme tokens with dark values, covering native input icons, placeholders, disabled/focus states, and custom badges across light/dark/system. When the component library carries its own theme attribute (e.g. Bootstrap `data-bs-theme`), sync it to the app theme attribute from an inline `<head>` script placed before the library stylesheet, so uncovered library defaults follow dark mode without a flash; drive `system` from `prefers-color-scheme` with a change listener.
4g. **Bring a second document type onto an accepted entry skeleton without regressing the first.** When aligning a sibling page (e.g. purchase / supplier-return) to an accepted sales/return entry page, reuse the same column matrix, free-text counterparty combobox, order-number preview, status select, same-day history, and async save-success panel. Keep the synchronous path intact: leave the existing non-fetch redirect submission unchanged and add an explicit async branch keyed on a fetch header plus the primary button's action value, so the accepted page's existing tests and the no-JS behavior both survive. Return JSON for validation failures on that branch too — a server that re-renders the form HTML on error must not let the client print the whole page into the error banner; parse the response by content-type and fall back to a generic message.
4h. **Consolidate per-type document lists into one table before adding type facets.** When several document types render as separate sections and the user asks for one list, merge them into a single paginated `UNION ALL` projection with a literal type discriminator and one uniform row shape computed in the route, convert the type filter to multi-select while still accepting the legacy single value, and key bulk actions by `type:id` dispatching each type's own rule. The per-type tables rarely share column names — build each side's condition string with its own aliases rather than one shared WHERE, or the query fails on an unknown column. Adding an optional link from a document back to its origin document is a separate decision: confirm **linkage-only** (prefill rows/limits/reference price, everything still editable, pricing rules unchanged) versus **constraint** (the source bounds and prices the lines) before building, because the latter reverts a prior decoupling and its schema migration. Recipe and pitfalls: [`references/document-list-and-cross-document-links.md`](document-list-and-cross-document-links.md). The same consolidation applies to the recycle bin: restore and permanent-purge eligibility differs per type (some posted or historically-referenced records can never be physically deleted), so keep per-type rule dispatch inside one merged table instead of one shared bulk action.
4i. **Unify a source-link control by comparing DOM nesting, not styling.** When two sibling entry pages render the same block at visibly different depths (one appearing to float on its own card, one sharing the row with the other fields), the cause is almost always template nesting rather than CSS: read both templates and compare which card/`row` wrapper the block sits in, and move the control to the **first row of the document-info card on every page** instead of restyling. On selection, show a **preview panel** (source number, counterparty, date, total, lines with quantity/price and remaining limits) between the info card and the detail card, then let the user apply those rows — a preview the user can read beats silently prefilling the grid and keeps the apply step explicit. Feed the preview from each page's existing read-only source endpoint; do not add a parallel one.
