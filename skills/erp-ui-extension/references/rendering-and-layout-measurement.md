# Rendering, Layout and Measurement

Read before claiming a layout, size, depth, or legibility requirement is met, and before measuring any geometry.

Split out of the `Always-On Rules` list in `SKILL.md`; each rule keeps its original wording.

- **A visual or legibility requirement is not satisfied by geometry.** When the user asks for a screen to be 美观/整洁/方便/符合操作逻辑, or reports that a value is hard to tell apart, the acceptance bar is the user's stated quality — not "no horizontal overflow", "fields are equal width", or "the class is applied". Those confirm a layout *mechanism*; they do not confirm the *outcome* the user asked for. Do not mark such an item ✅ 完成 on a geometry measurement. Either get a real visual judgment on the rendered page, or leave the item open and say plainly which bar you measured against.

- **A "put X next to Y" layout request is a width-budget question: measure the budget at the user's own viewport before implementing, and report the numbers when it cannot fit.** Read the request as arithmetic — the container's real content width (measured from the rendered page, never derived from `window.innerWidth`: the shell's sidebar, content margin, pane padding and card padding are all subtracted, so a 1258px window left only 835px usable) against the sum of the groups that must share the row plus the row `gap`. When the sum exceeds the budget, `flex-wrap` folds the last group to the next line and the page renders **exactly the layout the user asked you to change** — the worst outcome, because it reads as "you didn't do it". So measure both numbers, and if it does not fit, answer with a per-viewport table (window width → usable width → required width → one row or wrapped) plus concrete options; naming the width at which their arrangement *does* work is usually the whole fix, because the layout is right and only the budget is short. **Before offering the user a trade-off, diff the row block-by-block and measure any sibling page they cite as already fitting.** The shortfall is usually one fat sub-block rather than the whole row: in one round the sibling page's time block measured 470px because it stacked label+buttons over the date range, while the target page's was 596px with everything on one line — replicating the sibling's internal stacking freed the third group's width with no control narrowed and no interaction changed, which is the answer the user was asking for when they said 「他们就是在一行的，有没有其他好的方案」. A wrapping flex container cannot be narrowed by making a child wrap — `flex:1 1 100%` moves the child to its own line while the parent's max-content width stays the sum of the unwrapped children (measured unchanged at 596px) — so use `display:grid` with `auto` columns plus `grid-column:1 / -1` for the full-width line, which sizes to the widest column (296px). Also state which sub-line the moved group lands on, since `align-items` decides it and both read as "same row" in a summary. Two things never to do unilaterally to make it fit: **narrow a control past usable** (a date field clips its own value under ~120px, a name field shows two or three characters under ~130px) and **change a control's interaction shape** (a segmented button group turned into a `<select>` frees the most space and changes how the page is operated — that is a user decision, offered as an option). Do not silently drop a visible label either. Recipe: [`references/template-styling-and-theming.md`](references/template-styling-and-theming.md).

- **A page-level overflow check is not evidence that a layout renders correctly; measure the leaf that carries the value.** Grid/flex children almost always carry `min-width:0` as the standard overflow guard, which makes an over-constrained child clip or wrap *inside its own box* — the page's `scrollWidth` stays equal to `clientWidth` and the check reads clean while the user is looking at squeezed, wrapped numbers. Measure the value element's `scrollWidth` against its **own** `clientWidth` (and the card's), not the document's, and treat the user's stated outcome (值不再溢出/换行) as the bar. When the user says a block 「全都炸了」, suspect a container-level cause before any of the classes: re-read the container's own `display` / `grid-template-*` / `flex-*` against its **current** child list, because a leftover track definition from an earlier structure re-parents the new children into tracks and no class name will look wrong.

- **When the user says a control must be 独立于 the card it sits in, independence is DOM parentage, not decoration.** Making it look separate *inside* the same parent — a border, a heavier divider, a `::before` rule, a lighter background — is read as 「同一张卡片里又嵌了一层」 and the user asks why you still put them together. Move the block out to be a **sibling** of the card and give the gap to the new wrapper's own `gap` (assert `card.contains(block) === false`); a real gap is measurable as page background between the two card edges rather than card colour. Apply the same split to the wrapper's narrow breakpoint, drop the pseudo-element divider the old nesting required, and re-check the sticky ancestry of whatever you moved — and assert the **sibling relationship** in a test, since a presence-only assertion on the block's class passes in both the broken and the fixed state.

- **Do not report cross-page parity you measured on only one page.** Reading the computed value on one page and asserting the sibling matches is how a 3-column and a 4-column filter card both get written up as "两页已统一". Measure the computed value on every page the claim names, and when they differ, report the difference instead of the intended convergence.

- **A stacking/de-stacking requirement is verified by measured depth, not by the presence of a rule.** When the user reports "卡片过多、互相叠加" or asks a region to show one layer, a passing test that asserts the de-stacking selectors exist proves only that the rule text shipped. Enumerate every nesting path — a glass card nested inside another glass card is the easy miss because it does not repeat the container class — and count the computed `backdrop-filter` depth along each table's ancestor chain on every page that renders it. See [`references/template-styling-and-theming.md`](references/template-styling-and-theming.md).

- **Do not fix a misbehaving control by restyling it when the cause is structural.** A fixed-height track, a `<td>` turned into a flex container, or a block nested in the wrong card all produce symptoms the user describes in visual terms; read the template/CSS that produces the geometry and change the structure, rather than nudging padding or colour until the symptom hides.

- **A control the user says is "missing" is often present but clipped or scrolled out of view.** Measure the container before adding or rebuilding anything: compare the element's `scrollWidth` against its `clientWidth`, and each child's right edge against the cell's. A `td`/wrapper carrying `overflow:hidden` + `text-overflow:ellipsis` + `white-space:nowrap` truncates an action cell that is a few pixels too narrow, so the last button is partially or wholly invisible while the markup and the tests are perfectly correct. The clipping threshold moves with viewport width and with the table's column count, so a row that is fine at one width loses a button at another — measure at several widths before concluding a control exists or does not. **The fix is structural and has two halves; doing only the first changes nothing.** Put the width-bearing class on the cell and the flex wrapper on an inner `<div>` — never a flex class (`action-wrap`) directly on the `<td>`, which both drops the cell's width contribution and, under `table-layout:fixed`, lets the column shrink to an equal share of the leftover width. Then give the header `<th>` the **same** width class: with `table-layout:fixed` the column widths are taken from the **first row**, so a width on the body `<td>` alone is ignored and the cell stays narrow. Measured on a real bin: a 66.9px cell clipping 76.1px of the button, still 128.8px after fixing only the `<td>`, then fully contained (buttons 7px inside the cell) once the `<th>` matched. Lock it with a template test asserting no `<td class="action-wrap"` remains and every action cell carries the width class.

- **The user's legibility bar is their eyes, not the CSS value.** A "字太小看不清楚" report is an outcome requirement: pick sizes against the page's own body size and the surrounding scale, then confirm on the rendered page at the user's real viewport. Do not close it on "the font-size property is set" or on a geometry measurement.
