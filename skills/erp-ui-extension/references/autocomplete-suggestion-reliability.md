# 联想/自动补全的可靠性排查

用户说“输入了字，但没有弹出来相似的”时，**不要直接去改查询**。这类缺陷有四个互不相干的原因，分属不同层，先定性再动手。

## 一、先确认用户跑的是哪个壳

截图里的版本字样能告你壳：模板里 `is_desktop` 分支渲染出的文案（如“本地桌面版”）只在 `ERP_DESKTOP=1` 时出现。确认它，然后核对监听端口的进程可执行文件是不是那个 EXE。

为什么要紧：桌面壳跑 WebView2，你的自动化只能开 Chrome/Edge——**同版本号、不同渲染引擎**。所以“你复现不出来”和“用户确实看不到”可以同时为真，不冲突。此时**不要**拿“我这边是好的”去驳回用户。

## 二、四个原因，分开验

### ① 滚动监听把刚弹出来的列表关掉

`document.addEventListener('scroll', closeFloatingSuggestions, true)` 这类捕获阶段监听器会在**任何**滚动时关闭浮层，包括内层滚动容器的 1px 位移和鼠标滚轮的单次 tick。实测：弹出后让滚动容器 `scrollTop += 1`，或派发一次 `deltaY: 1` 的 wheel 事件 → 浮层立即关闭。

页面内容高于视口时（正常情况），用户随手碰一下滚轮就丢掉刚出现的候选，报成“没有联想”。

复现与验证：

```js
// 弹出后
await send('Input.dispatchMouseEvent',{type:'mouseWheel',x:700,y:400,deltaX:0,deltaY:1},sid);
// 再读 box.matches(':popover-open')  → false 即命中
```

修法（已验证）：**不要关，改成跟随定位** —— 只在锚点真的离开视口时才关闭。

- 滚动处理里对每个已打开的浮层：读 `input.getBoundingClientRect()`，若 `bottom < 0 || top > window.innerHeight` → 关闭；否则按与打开时同一套方向逻辑重算 `left/top`（`below`/`above` 比较 + 视口内夹取），而不是无条件关。
- 保留两条已有豁免：`box.contains(event.target)` 的浮层内部滚动不关；`resize` 仍然直接关（尺寸变了，位置不再可信）。
- 实测（1280×900，内层 `.page-body` 滚动）：弹出后窗格 `scrollTop` 0→40，浮层 `top` 265→225（正好跟随 40px，仍 `:popover-open`）；滚到底 478 时锚点 `top` 变 -263 → 才关闭。旧实现同一操作在第一次滚动就关闭。
- 这类 handler 常被前端测试用**字符串切片**直接从模板里取出来在 `vm` 里跑（`source.slice(indexOf('function closeFloating...'), indexOf("document.addEventListener('scroll'," …))`）：别把函数改名、别移出这对锚点之间，也别在函数体里写出切片锚点那串字面量，否则取到的代码段会截断或为空。
- 钉住旧行为的用例要**改写语义并补反向用例**（滚动后仍打开且位置跟随 / 锚点出视口才关闭），而不是把 `f.closed === 1` 删掉——断言里的坐标（`left`/`top`）就是“跟随了多少像素”的证据。

### ② 输入法组合期间弹出误导性结果

中文输入法打字时，输入框的 value 会先短暂变成拼音串（`di`），上屏后才变汉字（`地`）。自定义 combobox 监听 `input` 事件，于是：

| 阶段 | value | 列表内容 |
|---|---|---|
| 组合中 | `di` | **「无匹配项」** |
| 上屏后 | `地` | 正确候选 |

用户眼睛在组合阶段扫到“无匹配项”，就报成“没匹配到”。这不是查询错，是**中间态被渲染**了。

修法（已实现，四页共享一个控制器）：组合期间**不查询、不重绘**，上屏后再查一次。

- 输入处理里先 `if (composing || event.isComposing) return;`，再走原来的取词 → 查询 → 渲染路径；`compositionstart` 置 `composing = true`，`compositionend` 复位并**立即用最终值再走一次同一路径**。把「取词 + 空值关闭 + 查询」抽成一个 `handleQuery()` 共用，避免两处逻辑漂移。
- 空结果不能渲染成断言性文案：把空结果文案做成 `bindAutocomplete(..., emptyText)` 参数、**由调用方给**。零建档（手输未命中即建档）的字段要写「无匹配项 · 保存时会新建该商品/该客户」，写在控制器里的固定「无匹配项」会让用户以为不能建。
- 验证：真浏览器里按序派发 `compositionstart` → 一个 `isComposing: true` 的 `input`（value 设成拼音串）→ `compositionend`（value 设成汉字）。断言组合期间浮层**未打开**且容器无「无匹配项」文本，上屏后才弹出正确候选。只断言「最终能弹出」会漏掉中间态渲染这个缺陷。
- 这条与前端 `vm` 测试互补：`vm` 里用 `new Event('compositionstart')` + `Object.defineProperty(event,'isComposing',{value:true})` 就能覆盖（Node 没有 `CompositionEvent`），断言「组合期间 loadItems 未被调用 / 未渲染」。

### ③ 一侧支持拼音、另一侧不支持（不对称）

同一应用里两个联想框走不同查询时极易不对称。实测例：商品 API 是 `name LIKE ? OR spec LIKE ? OR pinyin_initials LIKE ?`，客户 API 只有 `name LIKE ?`——而且客户表**根本没有拼音列**（读 `CREATE TABLE` 的 DDL 确认，不要猜）。结果：中文子串能匹配、输首字母永远“无匹配项”。

门店里输首字母是习惯动作，所以这是实打实的缺口。修法是给该表加拼音列（幂等加列 + 回填 + 写入时同步），不是改前端。

**核对方法**：对两个 API 各打一次同一组输入（中文子串 / 完整名 / 拼音首字母），把结果并排列表；再读两边的 SQL 与表结构确认根因。

**补一列纯派生字段时，先穷举两张清单，再动手。** 缺一处就是静默漏网，测试与页面都不会报错：

- **写入点（全部）**：新客户/新商品可能从多条路径产生，典型是 5 条 —— 列表页批量导入的新增分支、编辑页改名、销售开单自动建档、拿货开单自动建档、服务层 `create_customer`/`create_product`。逐条 `grep -rn "INSERT INTO <表>\(\|UPDATE <表> SET"` 枚举，确认每条 INSERT/UPDATE 都带上该列；漏掉的那条路径建出来的记录**此后永远搜不到**，而页面一切正常。改名路径（UPDATE）同样要刷新该列，否则改名后旧首字母还在。
- **回填**：启动时的幂等回填**只补空值、不覆盖已有值**（`WHERE COALESCE(col,'') = ''`），否则会把人工/历史值冲掉；纯派生列沿用既有 `ensure_*` 幂等加列约定，**不动 schema 版本号**。
- **匹配点（全部），但把「筛选条件」排除在外**：匹配点 = 供联想/自动补全选词的查询（列表搜索、suggestions API、开单页模糊匹配、PDF/报表按客户名查找等，实测有 8 处）。这类加 `OR <col> LIKE ?` 是对的。但另有几处是**纯筛选条件**（用户在筛选框里输完整名称去过滤结果，不是从候选里选词）——这些**保持按名称**，不要顺手加拼音：把筛选语义从「精确写名字」放宽成「模糊拼音」会改变结果集，是没被要求的语义扩张。判断标准是「这个框有没有候选下拉」：有候选的加，纯输入过滤的不加。
- **用测试钉死不对称**：逐个匹配点各写一条「`?q=<首字母>` 能命中」，再给纯筛选条件写一条反向断言（该处源码不含拼音列）——否则下一轮改动可能又把两边拉回不对称。

### ④ 原生 `<datalist>` 作为候选载体本身能力有限

用 `<input list="...">` + `<datalist>` 做联想时，以下四条是**规格限制**，不是接线 bug：

- 候选弹层是浏览器原生的浅色列表，**不受页面主题控制**，暗色主题下明显不搭；
- **没有拼音**：datalist 只做字面匹配，拼音需要自己查（服务端 API 往往已支持，但 datalist 不走 API）；
- **不能带附加信息**（价格、成本、是否启用库存）；
- 型号/二级字段的候选**不随一级字段联动**（除非每次重建 option 列表）。

而且它与“自定义 combobox”常在同一应用里并存，导致**同类字段四页两种交互**（销售/退货手输+datalist，拿货/退拿货两级原生下拉）。评审时把这点作为一致性问题单独列出。

**迁移到自定义 combobox 的收益**：走服务端 API（拼音、价格、成本、库存状态都能带）、可主题化、可键盘导航、可让二级字段联动。迁移成本主要在键盘/ARIA 语义与既有测试断言。

## 三、自动化能不能驱动原生 datalist？

**别拿它做判定。** 在 headless 与 headful Chrome 下用 CDP 驱动原生 datalist 候选（`insertText` / 真按键 + `ArrowDown` 选中）都测不通——**连最简的纯控件页也测不通**。所以：

- **绝不能**由“我驱动不了”推出“ERP 的 datalist 有缺陷”。
- 想证明/否证，必须配一个**同环境的纯控件对照组**（`<input list>` + 一个 `datalist>` 的最小 HTML），两边用同一方法、同一环境各跑一次：

```js
// 同一函数、同一浏览器、同一输入法路径，分别跑控件页与业务页
const control = await probe('file:///.../control.html', '#a', '加');
const erp     = await probe('http://127.0.0.1:PORT/orders/new', '.picker-name-input', '加');
// 两者都不通 → 方法/环境无法驱动，不是产品缺陷；两者通 → 可下结论
```

对照组的另一用处：确认**是不是这一层**的问题。控件页通、业务页不通，才说明接线错了；都不通就什么都证明不了。

## 四、验证自定义 combobox 的正确方法

自定义（非原生）联想框可以用 CDP 完整驱动，这也是为什么先把它和 datalist 分开。

- **用真鼠标点击 + 真按键/`insertText`，不要用 JS 直接改 `value` 再派 `input`**：后者会绕过真实事件路径，可能得出错误的“正常”。
- 输入**单个字**时不要同时发 `keyDown(text=...)` 与 `char`：两者都带 `text` 会插入两个字符（实测输入“加”得到“加加”）。只用 `keyDown`+`keyUp`（带 `text`），或用 `Input.insertText`。
- 断言三件事：`box.matches(':popover-open')`、候选行数、候选文本；再加一项**遮挡检查**——取候选行的中心点跑 `document.elementFromPoint()`，返回的必须是该候选元素（或其后代），否则说明浮层被别的层盖住了（虽然肉眼“看起来弹出来了”）。
- **列表页的联想要额外验证「就地刷新之后还活着」，这只能在真浏览器里验。** 静态测试只能钉死「初始化脚本不在 fragment 区块内」这个文本事实，钉不住运行时到底有没有重新绑定。做法：驱动页面真实的 `data-inplace` 提交（提交筛选表单）→ 等 fragment 被替换 → **再输入一次同样的词**，确认浮层仍能弹出候选（会话中实测：刷新前 1 条候选，刷新后重输仍弹出 1 条）。只验刷新前会漏掉“刷新后静默失效”这一类错误，而那正是这条约束要防的。
- 顺带查**浮层在 `popover` 不可用时的回退路径**：在页面脚本前注入 `delete HTMLElement.prototype.showPopover` 模拟旧内核，再走一遍。若回退路径用绝对定位落在 `overflow:hidden` 的祖先里，浮层会被裁掉——实测这类页面的祖先链上常有 `overflow:hidden`（外壳、内容区）。
- **headless + CDP 驱动环境的六条硬约束**（违反时表现为「脚本卡住、零输出」或「功能像是坏了」，很容易误判成页面/产品缺陷）：
  - **每个页面开一个新标签**：`PUT http://127.0.0.1:<调试端口>/json/new?<url>`，连返回里的 `webSocketDebuggerUrl`；不要复用 `/json/list` 里那个跑过一轮的旧标签 —— 旧标签（尤其上一页还开着 popover）会让 `Page.navigate` 之后的调用挂死。
  - **每个 CDP 调用套一层超时**：`Promise.race([send(...), 15000ms 后 reject])`；否则挂起时脚本零输出、退出码又被 `head`/管道吃掉，看起来像 node 崩了。
  - **开焦点仿真**：`Emulation.setFocusEmulationEnabled {enabled:true}` —— headless 页面默认无焦点，**focus 才拉候选**的字段（点击即列出最近单据、单位候选）在真鼠标点击下也不会触发。
  - **截图放最后一步**：`Page.captureScreenshot` 放在脚本中段偶发挂起；要多张图时每个页面各开一个标签，截图放在该标签的最后一次调用。
  - **从脚本连 DevTools 端点必须给 Chrome 加 `--remote-allow-origins=*`**：用 Python `websocket-client` / Node `ws` 连 `ws://127.0.0.1:<调试端口>/devtools/page/…` 时 Chrome 会校验 Origin，没这个启动参数直接 `WebSocketBadStatusException: Handshake status 403 Forbidden`（报错正文自己会写明该 flag）。把 flag 写进启动命令，不要去改客户端伪造 Origin 头。
  - **等状态，不要 `sleep`**：`Page.navigate` 之后固定睡几秒再读 DOM，读到的常常是**上一页**（URL 还没换、fragment 还没替换），于是得出「功能坏了」的假结论——实测因此白排查两轮。等待写成轮询谓词：`location.href` 含预期参数 / `document.readyState === 'complete'` / 结果区存在，每 0.3s 判一次、超时才算失败。
  - **点候选之前必须等浮层「可见且非空」**：上一次查询留下的候选按钮仍留在 DOM 里（容器已经 `d-none`），`getBoundingClientRect()` 全为 0 → 合成鼠标事件落在 (0,0) → 点选**静默无效**，而 hidden 字段空着，现象与「点选没写回 id」的产品 bug 一模一样。就绪条件要写成「容器不含 `d-none` **且** `innerText` 非空」（或含预期文本）；**不要**只判 `querySelectorAll('.suggest-item').length > 0` —— 空结果的占位项带同一个 class、同一个 `role="option"`，计数法会把「还没查完」当成「已就绪」。同理，点击选择器带上 `:not([aria-disabled])`，别把占位项点掉。
- **浮层宽度要跟输入框对齐，别只看「弹出来了」**：除 `:popover-open` 与候选文本外，再比一次 `box.getBoundingClientRect()` 与输入框的 `width`/`left` —— 窄列上的浮层常常横向溢出到相邻列（遮挡检查的 `elementFromPoint` 抓不到这种「弹出来了但压着别人」）。

## 六、把 datalist 换成自定义 combobox 的落地清单（已实测）

- **先统一实现，再接线。** 同一应用常是「一份共享控制器 + 某个页面内联的等价副本」。给那个页面引入共享脚本前必须**先删掉内联副本**，否则同名函数被重定义，联想**静默失效且无报错**。把「统一」当成独立的一步：删内联副本 + 改引脚本 + 把页内独有的滚动跟随并入共享文件并导出，先跑一遍回归，再动具体字段。
- **共享导出要保住页内调用点**：在内联脚本开头 `const { money, costMoney, bindAutocomplete } = window.ErpEntry;`，比逐个改调用行安全，也便于日后 diff。
- **每行的浮层 id 必须唯一**：控制器用 `box.id` 生成 option id 并写 `aria-controls`；克隆行时若各行沿用模板里的同一个 id，多行 ARIA 关系会互相串。绑定行时按序号赋 id（`..._1/2/…`）。**「绑过就跳过」的判重绝不能用 `dataset`/class 标记** —— `cloneNode(true)` 会连 attributes（含 `data-*`）一起复制，新增行被当成已绑定而静默跳过，结果是新增行没有联想、且点击时弹出的是上一行的浮层；改用元素上的 JS 属性（如 `input.__erpBound`，克隆不复制 JS 属性），并在 id 与已有元素冲突时重新生成、顺手收起克隆带过来的 `:popover-open` 展开态。这一处缺陷在同一份代码的其它页面通常也存在，改一处要顺手 grep 其余调用点。
- **包裹输入框要补一条 flex 规则**：把输入框包进 `.suggest-wrap`（浮层靠绝对定位/popover 相对它定位）后，原先靠输入框自身 flex 撑开的行会塌陷 —— 在同一处加 `.picker-row .suggest-wrap{flex:1 1 auto;min-width:0}`。
- **窄列复用通用候选浮层要先覆盖 `min-width`**：共享样式常给浮层 `min-width:240px`，而控制器只设 `width` —— min-width 赢，所以 110px 的单位列上浮层会横向压住数量/单价列。在该浮层自己的选择器（提高一层特异性）上覆盖 `min-width:0` 并给 `max-width`；候选行高也按列宽压一压（padding/字号），否则三四项就出现滚动条。
- **点选候选要复用页内原有的「按商品刷新行」逻辑**：把原先内联在 picker 回调里的行状态更新抽成命名函数（如 `applyProductToRow(product)`），手输命中与点选共用，避免两条路径对单位/单价/成本/常规价的处理漂移。**点选回调里必须显式调用它**：`picker.set(product)` 只写 name/id 两个值、**不触发输入框的 `input` 事件**，所以只调 set 的话单位/单价/成本永不填充 —— 现象是「选了商品，单位却空着」，而手输路径一切正常。
- **未命中后的字段保留是有意语义**：未命中只清 `product_id`，单位/单价按当前输入保留。不要把它当缺陷修（单位落库统一属于另一个阶段）。
- **源码切片型前端测试要跟着改**：`fs.readFileSync(模板) + indexOf('function x(')` 这类测试在函数搬到共享文件后会取到空片段。移动实现时同步改切片来源与结束锚点（改成共享文件里的下一个函数或导出行），并在用例上方注明这是决策变更，而不是删掉用例。**共享文件里新增的模块级 `const`/`let` 必须落在用例的切片区间内** —— 同一文件的两组用例常按不同锚点切片（一组取 `function money(`→`function closeSuggestions(`，另一组取 `function bindAutocomplete(`→`window.ErpXxx = {`），放错位置就报 `ReferenceError: X is not defined`；优先用不依赖文件布局的写法（元素上的 JS 属性、函数内局部状态）。同理，被切片代码里调用的 DOM API 要容忍 mock 缺方法（`typeof document.getElementById === 'function' ? … : …`），因为 `vm` 上下文里的 `document` 常常只有 `activeElement`。
- **列表页搜索框的迁移多两条硬约束。** 开单页是「提交表单」语境，列表页搜索框是「就地刷新」语境：
  - **初始化脚本必须放在 `data-refresh-fragment` 容器之外**（就地刷新只替换 fragment，被替换区块内的 `<script>` 不会重新执行，放进去就是更新筛选后联想静默失效、无报错）。搜索框本身通常在 fragment 之前，所以可行；完成后再用测试钉死「`bindAutocomplete` 的调用点不出现在 fragment 区块内」。
  - **共享脚本的 `<script src>` 必须在调用它的内联脚本之前**：共享控制器是普通脚本（非 module，解析即执行），内联块若先跑就报 `ErpOrderEntry is not defined`。把 `src` 放在页面内联脚本块之前。
  - **原服务端渲染的候选数据迁移后变成死代码，必须删掉并重定向它的测试。** 迁移前模板常把建议名服务端渲染进 `<datalist>{% for s in suggestions %}`，路由同时传 `suggestions`；改走前端 fetch 后这些都不再被消费。判断依据：模板里不再有读该变量的地方。此时服务端那条查询（和它的 `render_template` 参数）应当**直接删除**（而不是留着「备用」），同时把「页面 HTML 里有该名字」的测试改为**断 API 命中** + **断页面确实接线到该 API**（例如断言 `'/api/...?q='` 出现在页面里）——因为名字已经不在服务端 HTML 里，旧断言会失败，而它不是回归，是决策变更。

## 七、把全量下拉（`<select>`）换成联想框

「这个字段只能从下拉里挑、不能打字模糊找」是同一类缺陷的另一种载体：候选不是来自 `<datalist>`，而是路由把**全表**查出来塞进 `<select>`（`SELECT * FROM customers …` 整表传给模板）。先找页面：`grep -rn '<select' app/erp/templates/`，再看选项是否来自全量查询。动手前分清这是**换控件**还是**换值语义**。

- **先 grep 项目里有没有现成的联想控制器与候选接口。** 兄弟页面（单据列表的往来对象筛选、客户/商品列表的搜索框、开单页的两级选择器）通常早就用了共享的 `bindAutocomplete` + `xxx/api/suggestions?q=`。命中就说明这是**接线缺口**而不是新功能——成本从「设计一个控件」降到「把已有控制器接上去」，回复里应当直接这么说，用户据此判断优先级。
- **匹配口径用现成的模糊匹配助手，不要另写查询。** 项目里一般已有 `name_match_clause()`（名称 + 拼音首字母 + 全拼，`LIKE %…%`），别自己拼 SQL。
- **先定这个字段提交什么，再动手，并保住它。** 读模板里控件的 `name` 和页面上的消费方：提交**记录 id** 的字段（页面自己的收款/调整/作废表单、对账链接、PDF 路由都吃这个 id）必须保留 hidden 输入承载 id，可见输入框只承载名称；提交**名称**的字段可以继续提交名称。不要因为换了控件就把参数从 id 改成名称——那会静默改掉下游所有入口的语义。
- **逐个字段核对后端的匹配方式：精确 `= ?` 的字段不能被自由文本喂。** 实测坑：分析页的商品筛选是 `p.name = ?`，把下拉换成输入框后，用户打半截名字直接提交 → 命中 0 行 → 页面显示「暂无数据」，而数据其实存在，这是最难自查的一类假象。两条出路：**要求点选候选**（未点选时给明确提示），或**显式校验并报错**；**不要**顺手把该筛选放宽成模糊匹配——单品分析会因此变成多品合并统计，那是口径变化，必须用户拍板。
- **删掉迁移后变成死代码的全量渲染。** `<select>` 的 `{% for %}` 选项循环、以及给前端塞的全量商品 JSON（`<script type="application/json">`）都不再被消费，直接删；全量商品塞进页面本来也是首屏负担，换联想后顺手省掉。删完按第六节的规矩把测试从「页面 HTML 里有该选项」改成「断 API 命中 + 断页面接线到该 API」。
- **可选筛选项要留「全部/清除」出口，必填字段要留「未选」提示。** 空值 = 全部的字段需要一个显式的全部/重置路径；`required` 的单对象字段在未点选时不能静默提交空值。
- **候选载体用项目已有的自定义 combobox，不要用原生 `<datalist>`**（它作为候选载体本身能力有限，见上文第四节）。
- **真机验收**：真实页面/桌面壳里打字 → 候选出现 → 上下键/回车选中 → 提交 → URL 参数与结果对得上；再补一条输入法组合期不误报「无匹配项」（第二节②）。

## 五、给用户的定性问题要可选项化

复现不出来时，不要要求用户“再试一次并描述”，而是把可能原因写成**互斥的可选项**让他对号入座（什么框都没出现 / 出现但写着无匹配项 / 出现但一滚就没了 / 只有某一格不弹）。他一个回答就能定位到上面哪一节，比来回描述快得多。
