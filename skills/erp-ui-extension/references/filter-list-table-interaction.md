# Filter, List and Table Interaction

Read before touching a filter card, a document list, a table action column, an in-place row expansion, or a typeable select.

Split out of the `Always-On Rules` list in `SKILL.md`; each rule keeps its original wording.

- **A filter card shared by two pages needs one implementation, not two matching ones.** When the user reports that two pages' filter conditions "样式不一样", the cause is two parallel implementations (a page-scoped `<style>` block plus a page-scoped stylesheet) drifting apart on grid columns, spacing, button treatment, control order, and control type (free-text + datalist versus `<select>`). Extract one shared partial/stylesheet both pages load, and align the control order and control type in the same change. **The same defect applies to a hardcoded option list: when one page renders `<option>` values from a literal array in its template while its siblings read a shared candidate helper, adding a value to the helper silently skips the hardcoded page.** A unit/status/category list belongs in one server-side helper passed into every page's context (with the template falling back to a default only for direct renders); grep the templates for the literal list (`grep -rn "'个','套','件'" app/templates/`) and delete each copy in the same change. Keep the type chips and their remaining bulk action (清空) on one row together — do not push the bulk buttons to the far edge with `justify-content:space-between` / `flex-end`, which reads as unrelated to the chips they act on. When empty selection already means "all", **drop the 「全选」 button outright** — it is a no-op duplicate of leaving everything unchecked; the arrangement recipe for such bars lives in the `product-ui` skill (its filter query-bar IA reference).

- **When you remove or rename a filter control, retarget the tests at the element hook, not the visible label.** `assert "全选" in html` keeps passing after the button is deleted the moment that phrase survives anywhere on the rendered page — an HTML comment, a help note, a sibling control's label — so the change ships with a green suite and zero real coverage. Rewrite such assertions against the control's `class`/`data-*` hook **and** assert the removed hook is absent; a visible-label substring is not a contract, and a comment describing the design is enough to make it lie. **The bare class name has the same hole as the label**: shared stylesheets here carry design comments that name their own classes, so `assert "completion-chip" not in manual_html` fails on a page that renders no chip at all — the comment satisfied it. For an **absence** assertion always match the attribute form (`'class="completion-chip"'`); for a **presence** assertion match the element, not the token. **When the layout moves a block instead of deleting it, the assertion that breaks is the position/source-order one, not a presence one.** An assertion like `summary_start < html.index('name="name"')` was encoding "the read-only summary is prominent"; moving that block into a side rail inverts the source order while keeping the intent. Re-express the intent **structurally** in the same edit (the block lives in the second grid column and contains no form control), and write in the test's docstring that the old expression was replaced and why — do not delete the test, and do not reorder the markup back to satisfy a stale assertion. **A test asserting a raw CSS declaration substring (`assert '.x{display:flex;flex-direction:column' in css`) pins the layout *direction* itself**, so a request that reverses that direction — the same filter row asked to stack in one round and to sit side by side in the next — fails a test that was never about behaviour; update the assertion to the new declaration in the same edit and note in the comment which round reversed it, rather than keeping the superseded direction to keep the suite green.

- **A filter card's 查询/筛选 submit is the same flash-and-jump defect as a tab click; route it through the same in-place refresh.** When the user reports that clicking 查询 makes the page 闪烁刷新 and jump 回到最上方, do not answer from the template alone — measure it: set the page's scrolling pane `scrollTop` to a non-zero value, click the submit, wait for the load, read `scrollTop` back. It comes back 0. `history.scrollRestoration` will not save you, because the scroll container is an inner pane (`.page-body`), not the document, so the browser has no offset to restore. Fix by wiring the submit into the page's existing fragment-refresh helper (fetch → replace the result fragments → `history.replaceState` → restore the pane's scroll anchor), keeping a normal navigation as the fetch-failure fallback. **Check whether that helper is already wired for some controls on the same page** — a page whose heatmap/ranking switches refresh in place while the main filter still full-reloads produces exactly the "有的地方闪、有的地方不闪" complaint, and the un-wired half is the one to fix. Preserve any client script that keeps export links in sync with the filter form's live values; the sync must survive the switch to fetch. This defect is not specific to one module: audit every list/filter page in the same pass rather than fixing only the one the user named. **Extract the refresh into ONE shared module** the shell loads once (e.g. `static/page-refresh.mjs`), mark result regions with a fragment attribute + stable id and controls with a single `data-inplace` marker, and let the module auto-init — do not let each page grow its own copy. Three pitfalls make the difference between working and "still flashes": (a) any handler bound **directly to an element inside a fragment dies on the first swap** — delegate from `document`; (b) firing a submit with `form.submit()` from an inline `onchange` **bypasses the `submit` event**, so the interceptor never runs and the page full-reloads — use `this.form.requestSubmit()`; (c) a `<script type="module">` is deferred while a body inline `<script>` is not, so the page script runs first and cannot call the helper — auto-init inside the module. **The fragment swap also invalidates any node references a page script cached at load, so a scroll-spy / current-section / current-tab widget latches onto a detached node and highlights the wrong item permanently.** A script that resolves `document.getElementById(...)` for each section once at init and closes over that array is not "bound to an element inside the fragment", so it escapes the delegation rule above — yet after the first swap every cached node is detached, `getBoundingClientRect()` on a detached node returns all zeros, and a threshold comparison of the form `section.top - paneTop <= 8` is then true for **every** candidate, so the loop's last write wins and the widget is stuck on the final item forever while re-running the update function changes nothing. Fix by re-querying the DOM inside the update function on every call and never capturing nodes at init, then grep the whole template tree for the same script (`grep -rln 'getElementById' --include=*.html app/erp/templates/`) — a sibling page running identical code looks correct only because it does not yet use the in-place refresh, and it becomes a latent instance the moment it does. Prove it before editing: assert `node.isConnected === false` plus an all-zero rect on the cached node against a non-zero rect on the freshly-queried one, and drive the same scroll positions with and without a refresh in between — the without-refresh run is the control that shows the widget is fine and the swap is the cause.

**A fragment whose id exists only in the fresh response is dropped without an error, so a region whose id varies by state never appears on the first submit**: the live page has no node with that id, the swap skips it, and `pushState` has already updated the URL — the user reports 「点了查询没反应」 while the address bar looks correct. Give the empty state and the result state the **same** fragment id, and drive every transition (empty→populated, populated→populated, populated→empty) before calling it verified. **A container whose mere presence is conditional on having content — a selected-conditions chip row rendered inside `{% if chips %}` — is the same defect**: render the container always and hide the empty state with a class, or the first filter submit shows no chip and the user loses the one-click way to remove a condition.

Full recipe and the remaining pitfalls (popstate, re-deriving change-detection baselines, non-executing fragment scripts): [`references/in-place-fragment-refresh.md`](references/in-place-fragment-refresh.md).

- **Sidebar highlight must be derived from the route's owner, not from a URL path prefix.** A page that belongs to one module but is served under another module's URL prefix (a reconciliation screen living under `/analytics/...` while being reached from `/accounts/`) lights the wrong sidebar item forever, because the prefix test matches the serving namespace rather than the user's context. When the link carries a source parameter for its back action, that parameter must also decide the highlight — otherwise the back button says 返回账款管理 while the sidebar says 数据分析, and the user reads the mismatch as a navigation bug even though every route works. Prefer endpoint-based ownership (`orders.*` → 单据管理, `accounts.*` → 账款管理, `analytics.*` → 数据分析) with an explicit source override for cross-module pages over string prefix tests, which re-break on every page added outside its own namespace. While in the layout, assert that **only one** item can read as selected: a secondary "current/ancestor" class that reuses the active item's text colour makes two entries look chosen on the same page, which is easy to miss in a class-name-only check because the second one carries no background. Note the legitimate exception before "fixing" it: a parent entry and its sub-item (开单 → 销售单) are correctly lit **together** on that entry page, so the assertion is not "exactly one highlighted" but "the highlighted set equals the expected set for that route" — express the expectation as an array per route in the audit script, never a hardcoded count of 1. **A new template-global injection (the `nav` state, a theme value, any helper) must tolerate the absence of a request context.** A context processor runs for *every* `render_template`, including templates rendered with no request at all — print/PDF templates and the tests that render them directly. Reading `request.endpoint` / `request.args` / `request.path` in the processor body then raises `RuntimeError: Working outside of request context` and breaks the whole suite in one shot (it took out every PDF and watermark test at once here). Keep the processor body a bare call (`"nav": nav_state()`), and put the request lookup *inside* the helper behind `if has_request_context():`, returning a safe default ("nothing highlighted") when there is none. Any new injected global that depends on the request needs the same guard.

- **When the user says a table's action column has "不一致的标签", triage three different causes before answering.** (a) **Conditional presence** — the button set differs per row because a row-level predicate hides one action (a document state, or a side-effect record such as a stock posting). This is by design; the answer is the predicate plus a per-row show/hide table **recomputed from the served database**, since a screenshot cannot tell you which row is which. **When the user then asks to make the column uniform, prefer always-render-but-disabled over hide.** Render the action for every row, and when the predicate forbids it emit `<button type="button" disabled title="<reason>" aria-disabled="true">` instead of an `<a href>`; hiding it makes the user think the feature is gone, while a disabled control keeps "this can normally be changed" visible and the reason explains why not. Put the reason in **one helper next to the predicate** (`_document_edit_block_reason` beside `_document_editable`) so the two can never disagree, expose it as a field on the row/JSON payload, and update **both** the server-rendered markup and any client branch that rebuilds the same row (the JS branch needs the reason in the API payload, not just `editable`). Style `:disabled` explicitly (muted surface + `cursor:not-allowed`, `opacity:1`) — Bootstrap's default faded-blue still reads as a clickable primary button. Then flip the existing tests from "edit link absent" to "disabled button + reason present, and still exactly one 编辑 per row", and keep the guard that no `/edit` href is emitted for a blocked row. (b) **Naming drift across pages** — the same action is worded differently on the list, the workbench, the detail page, and each sibling document type's detail page (view as 回看 / 查看, edit as 编辑 / 重编辑 / 编辑草稿, print as 打印 / 查看PDF, plus 下载回看, 恢复, 确认删除). This *is* a real defect, and it is usually what the user means when they circle a column; fix it as one vocabulary decision — **one action, one word, on every surface** — rather than per page. The settled target vocabulary for this product is **查看 / 编辑 / 打印** — use those three on the detail page, the list action column, the entry-page same-day history panel, and each sibling document type's detail page; keep genuinely different actions distinct (回收站的 恢复 / 确认删除 and 设置页的 下载回看 are not this family). Apply it to both the server-rendered markup AND any client-side branch that rebuilds the same action links, or the JS-rendered rows drift back. When you lock the vocabulary with a template test, **seed the document state that makes each conditional action actually render** — a posted document hides 编辑 (use a product with inventory disabled so the order has no stock postings), and an empty bin/table renders no row buttons at all because the cell lives inside a `{% for %}`. A fixture that skips this asserts against an empty string and fails for a reason that has nothing to do with the wording. Extend the cross-page matrix from step 4a to cover the action-column vocabulary so the next added page inherits it. (c) A genuinely wrong word on a single row. Say which of the three you found; when (a) and (b) coexist, separate "works as designed" from "should be unified" and do not answer only the half you verified first. A control that exists but is hidden by state must be reported as hidden, never as absent.

- **An in-place row expansion must insert *below* the clicked row and must not re-render, re-order, or scroll the page.** When the user asks to click a document row and unfold its line items ("点这条单据展开商品明细"), the acceptance bar is their own words: the clicked row keeps its screen position and nothing flashes or jumps back to the top. Implement it as a detail `<tr>` (`<td colspan=N>`) inserted immediately **after** the clicked row, fetched lazily from a small JSON endpoint keyed by the row's `(source, source_id)` and cached per row; animate the wrapper with `grid-template-rows: 0fr → 1fr` plus `overflow:hidden` rather than toggling `display` (no transition) or reusing the whole-region fragment refresh for one row. Do not embed every row's items in the page HTML — it bloats the payload and freezes the in-place refresh. Row types with no line items (payments, adjustments) get no affordance at all; action buttons inside the row need `stopPropagation`, or clicking the row's own 作废 button also toggles the expansion. Give the row `aria-expanded`/`aria-controls` and keep it keyboard-reachable, and show only the fields the user asked for (line name/unit/quantity/price/amount) — not the header fields they explicitly excluded.

- **A list page missing a block its sibling page has was usually edited deliberately; find the removal reason before restoring it, and never ship a filter whose predicate no longer varies.** When the user asks why page A shows a 筛选/工具条 block and page B does not, read the shared layout's documented block contract plus the route/service comments: the usual cause is that the block's predicate became trivially true after an earlier field merge or column delete (a "model field is empty" facet once the model was merged into the name), so the whole row was removed on purpose rather than lost. Restoring it is a **new predicate decision** — propose a predicate that still varies, ask the user to pick, and refuse to add a facet that is always-on or always-empty. If the same request also asks to put those filter chips inside the batch-action bar next to 删除选中, say plainly that it conflicts with the sibling page's block layout and offer both placements instead of silently choosing one. And when a screenshot arrives with a hand-drawn box, decide which meaning it carries before answering: a box around a control means "fix this control", a box over blank space means "put new controls here" — zoom the crop and ask whether the box contains any element at all, rather than assuming it names an existing one.

- **A catalog `<select>` the user wants to be typeable is a value-contract change, not a widget swap.** "这个字段只能选、不能输入模糊找" almost always lands on a control whose options are the **whole table** rendered server-side, so classify it before proposing anything: grep the project for the shared suggestion controller and its endpoints first — when sibling pages (a list page's counterparty filter, master-data search boxes, the entry pages' pickers) already use them, the item is a **wiring gap on one page**, not a new feature, and saying so changes the cost from "design a control" to "port the existing one". Then read two things per field, because they decide the design: **(a) what the field submits and who else consumes it.** A filter carrying a record **id** that the same page's own forms, action links and PDF routes also read (accounts: payments, adjustments, void, reconciliation link, summary PDF) must keep the id in a hidden field with the visible input carrying only the label — switching the submitted value to a name silently re-points every downstream entry point. A filter carrying a **name** can stay a name. **(b) the backend's match mode for that field.** An exact `name = ?` filter behind a free-text box is the trap: the operator types a partial name, submits, the query matches nothing, and the page reports "no data" while the data exists — the most expensive class of false negative here, because it looks like a data problem. Fix it by requiring candidate selection (with an explicit message when the text does not match a candidate) or by validating and reporting; **do not** quietly widen the filter to the project's fuzzy `name_match_clause()`, because a single-item analysis filter silently becomes a multi-item merged aggregate — that is a 口径 change and needs the user's decision. Finish by deleting the now-dead whole-catalog render (the `<select>` option loop and any full-catalog JSON blob handed to the page — it was also a first-paint cost) and by keeping an explicit 全部/清除 path on optional filters and a "nothing selected" message on required ones.
