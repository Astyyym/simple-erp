# Surfacing action failures to the user

Use when an action (delete, purge, bulk operation, void, finalize, save) can be rejected by a server-side rule, and when adding or reviewing a guard clause that decides whether an action is allowed.

## Every rejection must reach the user with its reason

A server that rejects an action with `400` plus a readable reason has done its job; the failure is almost always in how the **frontend path** renders it. The same rejection reached the user three different ways in one page family, and all three were unusable:

| Path | Default behaviour | What the user gets |
|---|---|---|
| Bulk button calling `form.submit()` | Native form navigation | The browser navigates to the endpoint and renders the raw reason as a **bare text page** — app shell, list, and the user's selection are all gone |
| Row button on an `ajax-delete-form` handler | `if (!response.ok) alert('删除失败，请刷新页面后重试')` | A generic alert; **the real reason is discarded**, so the user cannot tell a permission problem from a business-rule refusal |
| Per-row form posting to a normal route | Native navigation | Same bare text page as the bulk path |

The user's report reads as three separate defects ("弹出一串看不懂的字", "只说删除失败", "点了没反应") when it is one missing presentation layer.

- **Route every rejected action through one presentation layer.** Submit with `fetch`, and on a non-OK response render the server's reason as an **in-page message list**, keeping the current page, the shell, and the user's selection intact. Reserve `alert` for client-side preconditions such as "nothing selected".
- **Never replace a server reason with a fixed client string.** The whole value of a guard clause is telling the user *which* rule blocked them and *which* row. A generic "operation failed, refresh and retry" actively misleads, because refreshing does not help.
- **Route every rejected action through one helper, so all paths get the same treatment.** A single function that takes the reason and the caller's expected shape is what keeps a new route from quietly reintroducing the bare-text page. Apply it to *every* rejection site on the delete/purge/void/bulk paths — a codebase easily has dozens of `return str(exc), 400` sites, and fixing only the one the user reported leaves the same defect one click away.
- Branch on the request's `Accept` header (or an explicit fetch marker): return JSON `{error: ...}` to fetch callers; for plain browser navigation render a **real error page that extends the app's base layout** — shell, sidebar, page title naming the operation, the reason, and a back link. Do **not** "keep the legacy text behaviour for plain navigations": that bare text page is precisely the defect in the table above, and a no-JS path still needs the shell so the user is not stranded. Keeping a legacy *redirect* for the success path is fine; keeping a legacy *error body* is not.
- **Pick the surface by how far the user's context would be lost.** Row-level action inside a list → an **inline message inserted above that table** (build it once, reuse it, give it a dismiss control), so the page, the filters, and the selection all survive. Whole-page form submission → the error page above. Do not send an AJAX row action to a full-page error, and do not leave a page-level action as a bare alert.
- **On the client, handle a non-JSON error body explicitly.** If the response is not parseable as JSON, surface the HTTP status rather than falling through to a silent no-op — an unhandled parse failure looks exactly like the original "点了没反应" complaint.
- For a bulk action, report **per-key failures** in one response (`<key>：<reason>`), listing every rejected key rather than stopping at the first. A partially applied bulk action must say which keys failed and why, and the accepted keys must still have been applied.
- Keep the document number or row key inside the reason text — it is what lets the user find the row.

## A guard clause must fail loudly, not silently

The dangerous shape is a conditional write that matches nothing:

```sql
DELETE FROM customers WHERE id=? AND <reference guard>
```

When the guard does not match, the statement affects **0 rows and raises nothing**, so the route continues as if it succeeded — redirect, success message, and an audit entry recording a purge that never happened. The user sees the page refresh, the record still present, and reports "点了删除没反应". Silent failure is worse than an error, because there is nothing to act on.

- **Check the affected-row count** (`cursor.rowcount`, `changes()`, or a pre-flight `SELECT`) and raise a readable reason when it is 0. Never infer success from the statement not raising.
- **Do not write a success/audit entry for an operation that did not occur.** A log recording the intent rather than the effect destroys the audit trail's value.
- Prefer an explicit pre-flight check when the rule is non-trivial: read the row, evaluate the guard, raise a specific reason. The same predicate then decides whether to render the control **disabled with a visible reason** instead of offering an action that will be refused — this is the pattern already used for recycle-bin rows that can never be purged.
- **A disabled control is a claim that the operation is impossible — verify it before trusting it.** Rendering the guard's verdict as a greyed-out "cannot delete" badge is only honest if the guard is *correct*. When the guard itself is wrong (a purge rule reading a state the delete path no longer produces), the disabled badge converts a bug into a permanent, plausible-looking UI state: the user asks "是不是你故意这样设计的？" and there is no error, no test failure, and nothing on screen that looks broken. Never treat "the row renders as not-purgeable" as evidence that it genuinely cannot be purged — assert against a real attempt on a copied data root, and if nothing in the bin is ever purgeable, suspect the predicate rather than the data.
- Guard clauses are **per type and must stay per type**: a record that is genuinely unreferenced may be purgeable while a referenced one is not. Never collapse them into one shared "can delete" rule. But do not let per-type dispatch become a hiding place for a predicate that refuses everything — a guard that blocks 100% of real rows is a defect regardless of how cleanly it is dispatched.

## Adding a new rejection site

- **Preserve each route's existing status code when you only change its presentation.** Converting `return str(exc), 400` to a structured error page must keep the code the route already returned. Do not reach for 404 because the record is absent if the route previously answered 400 (an unknown *kind* / bad request), and do not reach for 400 for a genuine missing record. A flipped code is not cosmetic: it breaks an existing assertion and mislabels a bad request as not-found. Reassign a status only when the plan or an explicit decision calls for it.
- **Reclassify a status by mechanism, not by editing each `return`.** When the decision *is* to correct the code (a record/snapshot/customer that genuinely does not exist should be 404, not 400), raise a **distinct exception** at the absent-record sites in the service layer and catch it *ahead of* the generic handler — do not hand-edit every route branch. Make the new type a **subclass** of the exception the untouched callers already catch (`class RecordNotFound(ValueError)`), so routes that only render a page or a JSON reason keep their current behaviour with zero edits, and only the routes that need the differentiated status add an `except RecordNotFound:` clause before `except ValueError:`. Draw the line explicitly: absent/expired/deleted resource → 404; malformed request, missing required parameter, guard rejection, disallowed state → 400. A single generator that raises one message for both cases (e.g. a purchase-PDF helper raising `ValueError` for "missing" and "wrong status" alike) needs the absent case split out before the route can answer two codes.
- **When you flip a status, split the tests that parametrized over the old code — do not weaken them.** A parametrized "every invalid reason → 400" test covers both genuinely-absent and bad-request inputs; reclassifying makes half of it wrong. Compute the expected code per case (`404 if invalid in ('deleted', 'missing') else 400`) so each row still asserts its own correct semantic, then add explicit cases for the newly-distinguished path. Loosening the assertion to "is an error page" would hide a regression in the very distinction you introduced.
- **Grep the frontend for the JSON key it reads before you touch the error contract, and add keys — never rename them.** One page family read two different keys for the same failure: the shared layout read `data.error` (row-delimited actions) while the order-entry fetch handlers read `result.message`. A server emitting only `error` silently swallowed the real reason behind a generic fallback. Emit **every** key existing consumers read (`{"error": text, "message": text, ...}`) so the change is zero-breakage on both, and assert in a test that each consumer still sees the real reason.
- **A catch-all error handler must re-raise `HTTPException`, or it converts every 404/403 into 500.** To replace English default pages with a Chinese app-shell error page, register `errorhandler(404)` and `errorhandler(500)` that render the shared error template (shell, sidebar, back link, no internal detail). If you also add `errorhandler(Exception)` as a catch-all, guard it with `if isinstance(error, HTTPException): return error` before falling through to the 500 renderer — without that branch every validation 404 and CSRF 403 becomes an opaque 500. Assert unknown-URL and record-not-found return 404 (not 500) and that the shell element is present.
- **A helper that receives a `conn` must be called *inside* the `with get_db() as conn:` block.** The context manager closes the connection on exit, so calling such a guard from below the block raises `sqlite3.ProgrammingError: Cannot operate on a closed database` — an unhandled 500 on a path that should have been a clean rejection. Compute every connection-dependent value (including the eligibility/guard query) inside the block and keep only plain values afterwards.
- **Make the *whole* rejection surface one presentation layer, including export/PDF routes.** `summary_pdf` / `ledger_pdf` / document-PDF endpoints return bare text on their guard branch too, and a fetch caller cannot render a bare page. Route them through the same error helper so a navigation gets the app-shell error page and a fetch caller gets JSON. A navigation-only UI can also be the reason the defect went unnoticed — check these endpoints even when the plan does not list them.

## Verification

- Reproduce the rejection through the **real UI path**, not only by calling the endpoint with `curl`. A `curl` showing the correct 400 proves the server; it does not prove the user sees anything usable. Drive the actual button in a headless browser and capture what the user would see — the rendered page text, or the JSON the fetch handler receives.
- Assert both halves: the reason text reaches a visible surface, **and** the page/shell/selection survived. Assert the shell survived structurally (the sidebar/nav element is still present) — that is what distinguishes an error *page* from the bare text *page* being replaced.
- Assert no `alert` fired for a server-side rejection: register a dialog handler that records dialogs, and assert the list is empty. A stray `alert` from a leftover handler is invisible in a DOM-only check.
- Check the message against the **original reported wording**, not against your own new copy. If the user complained the text was unreadable, assert the reason contains the specific rule name, not merely that some message rendered.
- When a guard blocks a write, assert the row is **unchanged** afterwards (not merely that the response was non-2xx), and that no audit row was written.
- Reproduce destructive paths on a **copied or throwaway data root**, never on the user's demo or live root. Read-only diagnosis against the running instance is fine; any write-path reproduction gets its own scratch root, because a guard that fails to guard is exactly the bug you are probing for. Copying the demo root is cheap and keeps the user's data untouched even when you only meant to probe.
