# Acceptance and Evidence

Read before reporting a defect, merging or renaming a section, bumping an asset token, or declaring a requirement met.

Split out of the `Always-On Rules` list in `SKILL.md`; each rule keeps its original wording.

- **The runtime behind the user's screenshot may not be the runtime your automation can drive.** A desktop shell renders in the OS webview (WebView2) while your probes open Chrome/Edge — same app, same version, different engine. When the user reports behaviour you cannot reproduce, do not answer "我这边是好的" as if that closed the item; identify which shell the screenshot came from (the template's own desktop-only wording, plus the listener PID's executable), say plainly that the two runtimes differ, and hand the user a small set of mutually exclusive options (nothing appeared at all / a box appeared saying "no match" / a box appeared and vanished on a scroll / only one field fails) so one answer localises the cause.

- **Never conclude a product defect from "my automation could not drive it".** Before reporting a native control (a `<datalist>` popup, an OS dialog, a file picker) as broken, run a minimal same-environment **control page** exercising the bare feature with the same method: if the control page fails too, the finding is about your harness, not the product, and must be reported as `unverified`.

- **Merging or renaming a section is a copy-drift change: sweep every cross-reference to the old name in the same edit.** A hint line that points the user at another panel by name ("拿货只影响流水热力图与下方「单据流水」") is invisible to any structural check and keeps naming a section that no longer exists after a merge, so the page explains a layout it does not have. Grep the template tree for the section's display name — not its id or class — and update or delete each hit, including the explanatory prose in an adjacent card's `help` text. Expect this to break tests that were **passing on the stale prose**: an assertion named for the section (`assert "单据流水" in html`) is satisfied by the hint sentence mentioning it, so the suite went green over a section that had been merged away. When that assertion fails after your copy fix, the assertion was never testing the section — rewrite it against the section's real hooks (its container class, its child labels) and say in the test's docstring what it used to match, rather than restoring the stale sentence.

- **Bump the static asset cache token when a stylesheet changes materially, and bump it in every template that loads it.** A stylesheet served under a fixed query string (`analytics-v4.css?v=3`) is served from the browser's disk cache, so a CSS-only fix reads as unapplied — and sibling templates frequently carry different literals (`?v=1` vs `?v=2`), so a partial bump leaves the others on cached old code. Grep every template that loads the asset for the current token and set them all to the same new value in one edit.

- **Distinguish "I implemented this" from "this meets the standard the user set".** When a batched feedback list mixes cheap and expensive items, finishing the cheap ones and marking the list done is the failure mode; report per item against the user's bar, and call out the ones where your verification was shallower than the request. **When the change is already implemented and verified, say that in the first line** — a report that leads with the design rationale, the measurements and the screenshot of a finished change reads as a proposal, and the user answers 「那就按照这个来修改吧」 to work that is already on disk. Open with "已改好，现在就能看到" plus the URL, then the evidence.
