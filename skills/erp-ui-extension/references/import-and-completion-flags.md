# Importer validation and "incomplete record" flags

For importers that sweep legacy data in, and for any flag whose job is to say "this record still needs work".

## The flag is a 口径 — one source, and everything derives from it

- One predicate module owns three things and nothing else may restate them: which **origins** count, which **fields** count as missing, and the human wording of *what* is missing. Shape it so the wording is derived, not duplicated: `*_missing_fields()` returns a list of human phrases, and `*_needs_completion()` / `*_completion_hint()` are thin wrappers over it. Three surfaces then cannot disagree.
- Export the SQL fragment from that same module (an origins constant, a ready-made `IN (...)` string) and have every route build its condition from it. The list filter, the chip/row count, and the badge must be the same rule; a second hand-written `WHERE` is how a count and a list drift apart, and the drift is reported as "数字对不上".
- Everything user-visible hangs off the predicate: list filter option, its count, the row badge **and its tooltip**, the edit-page "this record is incomplete" banner, and the importer's pre-check note. Add a new surface by calling the predicate, never by copying the condition.
- **Keep a user-authored record out of the flag only as an explicit decision, and write the reason into the predicate's docstring.** A record the user created by filling a form has already had its blanks chosen by them; records swept in from a document or an import are the ones worth chasing. State that rule in the code, or the next session reads the restriction as a bug and "fixes" it.

## Widening the flag to a new source — the checklist

1. Widen the origin scope in the predicate **and** in the exported SQL fragment in the same edit.
2. `grep` the old restriction string (e.g. `origin='order'`) across `app/` **and** `tests/`: routes, templates and any test that recomputes the expected count with its own SQL will keep asserting the old rule and stay green while the product changed.
3. Decide whether the new source adds a new *field* criterion, and if so put it in the predicate only (never in the SQL alone): a blank field that is tolerated on input (a price left empty, stored as 0) is exactly the case the flag should catch, because the record looks complete in the list while the next document computed from it is wrong.
4. Update the wording that named the old scope — the badge tooltip, the legend/help line next to the filter, the edit-page banner — and the count assertion in the tests.
5. Re-check the "everything derives from it" surfaces above; the flag now also appears on records the user did not create, which is what they asked for, so say that plainly in the handoff (a shop that imported earlier will see a one-time surge of flagged records, with no migration needed because the flag is computed at read time).

## Importer pattern: reject the row only when the value is unusable

- An **optional** field (brand, phone, address, price) should import blank with a safe default and flag the record, instead of rejecting the line. A rejected row costs the user a second file round-trip; a flagged row is fixed in the app afterwards. Reserve hard rejection for values that make the record unusable (empty identity, negative or unparseable money, a quantity without its cost).
- **Remind in three places, because each answers a different moment:**
  1. **Pre-check page** — a warning banner with the count, plus the per-row note saying *which field that row is missing*. Nothing is written yet; this is the cheap moment to fix the file.
  2. **Result summary** — the same count after the write, so "what did I just do" is answered where the user already is.
  3. **List badge + filter** — where the work is actually done later.
- **Count only the rows you can be sure about.** A same-name "update" row's target may be a manually created record that must not be flagged, and the pre-check stage cannot see the target's origin — report adds, say so in the plan, and prefer under-reporting to a count that later disagrees with the list.
- **Templates: the first row must stay a pure header.** Importers match the header row exactly, so a guidance row is either swallowed as data or rejects the whole file ("表头错误"). Put the guidance in a **second sheet** ("填写说明"), generated by the same template helper that both importers call, and keep the notes in the service module next to the header definitions so both routes pass the same list.

## Verification pitfalls

- **Write non-ASCII fixtures from a UTF-8 source file, not from a shell command line.** A small Python script (`urllib`) run by the project interpreter sends real UTF-8; a name typed into a Chinese Windows shell arrives in the local code page and lands in the database as mojibake, which surfaces later as unreadable rows and name-assertion failures that look like product bugs.
- **A pre-check page carries the whole parsed payload in a hidden JSON field**, so `html.split("<tr>")` finds rows *inside that JSON* before the real table and the assertion passes or fails on the wrong bytes. Scope the split to the table container (`html.split('<div class="table-responsive">', 1)[1]`).
- **Decoration inside a cell is part of its text.** A badge appended to the name cell ("名称" + "待补全") breaks every test helper that keys rows by the cell's raw text — the moment a new source becomes eligible for the badge, those lookups start raising `KeyError`. Strip the badge text (or key on a `data-` attribute) inside the helper, once, rather than patching each caller.
- **Restart the instance before re-verifying, and kill the right PID.** Templates (and the inline CSS inside them) are cached per process, so a template edit is invisible on a running dev server; when stopping it, kill the PID `netstat` reports as LISTENING on that port — killing the shell/launcher wrapper leaves the server alive, and two stale listeners on one port will keep answering with the old code while you re-test.
