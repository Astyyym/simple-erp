# Template styling and theming

Use when extending or restyling ERP entry/list/detail templates, or when a page looks unstyled, or when text/inputs are illegible in only one theme.

## Locate style definitions before restyling

- A class reused from a sibling template is frequently defined only in that sibling's page-scoped `<style>` block, so on any other page it silently renders unstyled. Before restyling, grep the whole template tree for the exact class name and note whether the definition sits in a page-scoped block or in a shared stylesheet / base layout.
- Fix by extracting the shared entry-page block (card/panel/table/section-title rules) into one common stylesheet or partial that every sibling page loads. Do not copy the block into each page, and do not rely on another template happening to render first.
- After extraction, re-check the page that originally owned the block; moving it is a shared change and can regress the source page.
- Entry/list/detail/print pages of the same document family drift apart one screen at a time; a cross-page convention matrix (header, return action, button hierarchy, min widths, no-wrap) is what keeps them aligned, and shared style extraction is how it stays enforced.

## Theme discipline

- Theme runs on a root attribute (e.g. `data-ui-theme="light|dark|system"`) plus a `--token` variable set redeclared for dark and for `prefers-color-scheme`. Components must consume `var(--token)`, never literals.
- "Dark-mode text or inputs are unreadable" is almost always a hardcoded literal or a light-only utility class that never switched. Grep templates and page `<style>` blocks for `#rrggbb`, `rgb(`/`rgba(`, and known light-only classes (Bootstrap `.table-light`, hardcoded `color:` on outline buttons) and route each through a theme token with both light and dark values.
- Check the interactive controls too: native date/input icons, placeholders, disabled and focus states, custom status badges/chips, and inline `background:transparent` inputs.
- **A single accent token used as BOTH text/border colour AND as a solid fill behind white text cannot serve both in dark mode, and this is the highest-yield theme defect.** The dark block legitimately *lightens* the accent so text and borders stay legible on a dark surface — but the same variable feeding `background` on a filled button turns it light-on-light. Signature to look for when a dark theme has "unreadable buttons": the filled button's ratio passes in light and lands around **2–4** in dark, while an `.btn-danger`/`.btn-success` white-on-light-accent is the worst (measured 2.77 and 1.92). Fix in the **token layer by splitting fill tokens from text tokens** (a darker fill for solid buttons, the light accent kept for text/border/icons) — do not add per-button overrides, which leave every button you did not look at broken. The same run usually exposes a second gap: **the outline/secondary button variants were never given a dark block at all**, so they keep the library's light-mode literals (`#0d6efd`, `#198754`, `#dc3545`) straight into dark. Enumerate the whole button vocabulary from the served pages rather than the ones in the screenshot.
- **A library `:focus` rule that declares only part of the state leaks the library's own theme variable into the field, so the control visibly changes colour while focused.** The app overrides input background/colour for its surface token, but its `:focus` rule restates only `box-shadow`/`border-color`; the library's `.form-control:focus{color:var(--bs-body-color);background-color:var(--bs-body-bg)}` then wins for the rest of the state, and `--bs-body-bg` (`#212529`) is not the app's surface token (`#171e2b`). In dark the field flashes a different black under the caret; in light the background is coincidentally identical so only the **text** shifts a step greyer — one cause, two symptoms, and the light one is easy to dismiss as "fine". Declare the full state (`background` + `color` + `border-color`) in the app's own `:focus` rule, pinned to the app's surface/ink tokens.
- **A shell-level border or background written as a literal survives into dark mode as a bright outline.** Grep the base layout for non-tokenised literals (`border:1px solid rgba(255,255,255,.88)`, `background:#fff`) on shell containers — the white border reads as a glaring frame around the whole content area in dark and in `system`-with-dark-OS, and is invisible in light so nobody notices it while working in light. Route it through a token with per-theme values.
- **`system` is not a subset of light+dark: it renders as whichever the OS prefers, so it must be measured twice.** A theme audit that runs only explicit `light` and `dark` understates impact: a dark-only defect becomes "every user whose OS goes dark in the evening", because the user's setting is the default `system`. Drive it with `Emulation.setEmulatedMedia` for both `prefers-color-scheme: dark` and `light`, and set the app theme through its **own config/settings route followed by a reload** — flipping the root attribute by hand does not re-run the theme-sync script, so you measure a half-applied state and invent a defect.
- Sync the component library's own theme switch to the app theme attribute. If the library keys dark styling off a separate root attribute (e.g. Bootstrap's `data-bs-theme`), set that attribute from an inline `<head>` script placed before the library stylesheet, deriving `light`/`dark` from the app attribute and `system` from `prefers-color-scheme` plus a change listener. Without it, every library default the app did not override keeps its light values and reads as black-on-dark.
- **A glass/backdrop-filter fallback re-declares the same surface colours, so a colour change applied only to the primary rule is silently overridden.** `@supports not ((-webkit-backdrop-filter:blur(1px)) or (backdrop-filter:blur(1px))){ .order-table thead th,.order-table tfoot th,.readonly-total{background:var(--erp-surface-soft)} }` ships the *same* selectors with a different background; change the header's normal-state background and the fallback still paints the old light surface on any engine without backdrop-filter. Grep the page block for `@supports` before concluding the change landed, and update every declaration of the property you are changing.
- **A component library can repaint a whole cell with an inset shadow, so a `background`-only change lands invisibly.** Bootstrap 5.3's `.table-light` sets `--bs-table-bg` and its cell rule paints `box-shadow: inset 0 0 0 9999px var(--bs-table-bg)`; that shadow covers the entire cell on top of `background-color`, so a solid header colour set only through `background` still renders as the library's light tint (measured: `#f8f9fa`, contrast 1.05 against white text). Put `box-shadow:none` in the same rule as the colour, and when reporting a contrast number read the **painted** background: if `getComputedStyle(th).boxShadow` carries that 9999px inset, take `--bs-table-bg` as the effective colour instead of `backgroundColor`. Removing the element from the no-blur `@supports` fallback's selector list is part of the same edit — that path repaints it, so leaving it there undoes the change on engines without backdrop-filter.
- **When a dark-mode override ties on specificity with the shared layout's rule, document order decides — so keep the page block after the layout's head styles.** `html[data-ui-theme="dark"] .table-light>:not(caption)>*>*` in the layout and `html[data-ui-theme="dark"] .order-table thead th` in the page both compute to (0,2,2); the page `<style>` inside the content block wins only because it renders after the head. Moving such a rule into the head, or adding a later competing rule, silently drops the dark treatment — verify by measuring the computed colour under `data-ui-theme="dark"` and under `system` + emulated `prefers-color-scheme:dark`, not just the light theme.
- **A repeated page-scoped block means the same rule exists N times; a "one-page" restyle is actually an N-page change.** When the entry pages each carry their own copy of `.order-table thead th { ... }` (sales/return, purchase, purchase-return), a request to darken the header is not one edit: count the copies with `grep -rn "<the-selector>" app/erp/templates/` and change every one, or the pages the user did not open keep the old treatment and the complaint returns. Prefer extracting the shared block (see the extraction rule above) over editing N copies, but if you edit in place, say in the report which files you touched and assert the same computed value on every affected page — never generalise from the one page you measured.
- Verify by emulating the theme attribute and the color scheme (headless `prefers-color-scheme`), then measuring computed foreground/background contrast across every page — a single screenshot or a single mode misses exactly the uncovered library defaults. Run the full **page × width × theme** matrix in one pass and post-process the JSON; a defect that exists on one page of a family usually exists on all of them, and one visible only at the user's real CSS width is invisible at your default probe width. Two traps when the numbers look impossible: a **real mouse click** (`Input.dispatchMouseEvent`) can read a different computed style than a scripted `.focus()` (one declared only part of the state), so probe state changes with dispatched input and always report the before/after **pair** — "changed" is only provable as a diff. And a scripted probe can contradict itself across runs; re-run twice to confirm the reproduction before reporting it.
- Canvas/graphic colors are not CSS tokens: read the active theme at draw time and pick a matching palette, and redraw on a color-scheme change.
- **A standalone page (print/PDF preview, error page, desktop-shell dialog) does not inherit the app shell's theme.** A template rendered outside `base.html` keeps whatever background/colour it hardcoded, so a light `#f3f5f7`/`#fff` preview stays light under a dark app theme and reads as a broken theme. Pass the resolved `ui_theme` into the standalone template's own context (the route already loads config) and give it a local token set with `dark` and `prefers-color-scheme` branches, exactly like the shell — do not assume it inherits.
- **For an offline/desktop build, vendor the CDN asset locally and verify no CDN domain survives.** A CDN `<link>`/`<script>` (Bootstrap, fonts) means the frozen build loses its layout with no network. Download the pinned version into a `static/vendor/` path, repoint the template through the app's static URL, keep the whole `static/` tree in the packaging spec's `datas`, and add a test that greps every template for the CDN domain and asserts the local static path returns 200.

## Cross-page layout parity

- **Never put `display:flex` (or `grid`) on a `<td>` that should stay a table cell.** The cell stops being a `table-cell`, so its height collapses to its content height and `vertical-align:middle` no longer applies — the row is tall, the cell is short, and the control sits flush to the top with a visible gap beneath. Put the flex container on an inner wrapper `<div>` and leave the cell a cell. Symptom to look for: a sibling cell in the same row measures the full row height while this one is visibly shorter. Confirm by measuring, not by eye: compare the cell's height against the row's and the child's top/bottom gaps.
- **A control must centre its own label; do not rely on the parent container to do it.** A component library's button is typically `display:inline-block` plus a `min-height`. When its parent is a flex or grid container the child gets **blockified** to `display:block`, so the `min-height` slack all lands *below* the content and the label rides visibly high. Worst on the tallest buttons, and on chip/toggle buttons whose `line-height` is smaller than their `min-height`. It reads to the user as "the text isn't vertically centred" and is invisible to a screenshot diff because nothing overflows or clips. Fix it once on the component, never per page: `display:inline-flex; align-items:center; justify-content:center` on the button class — a `label.btn` chip inherits it for free. Verify by reading `getComputedStyle(btn).display` for every button whose parent computes `flex`/`grid`: they must be `flex`/`inline-flex`, never `block`.
- **Measure text centring against the line box, not the glyph ink box.** Selecting a control's contents with a `Range` and comparing its `rect.top`/`rect.bottom` against the control's own rect measures the *glyph ink*, which for CJK text is legitimately asymmetric — a residual of under a pixel is normal, not a defect, and chasing it produces a false "still off-centre" report or a fix for a non-bug. Append a hidden inline marker (`<span>` with `font:inherit;line-height:inherit;visibility:hidden` containing `&nbsp;`), measure *its* rect as the line box, and compare `(markerTop - btnTop)` against `(btnBottom - markerBottom)`. A real centring defect shows as a constant offset that tracks the button's `min-height` minus its padding-plus-line-height; a glyph-only residual below a pixel is not a layout offset.
- **A table cell carrying `overflow:hidden` + `ellipsis` + `nowrap` will silently truncate an action column that is a few pixels too narrow.** The last button in the cell is partially or wholly invisible while the markup, the endpoint, and every test are correct — the user reports the button as "missing" and the DOM says it is there. This is invisible to a string assertion and to a screenshot taken at one width. Measure `scrollWidth` against `clientWidth` for the cell and each child's right edge against the cell's right edge, at several viewport widths: the clipped amount is a function of the table's column count and the card width, so a row that fits at one width loses a button at another. Fix with a `min-width` on the action column or by letting the action wrapper opt out of the ellipsis rule — never by shortening the label.
- Layout variants (a narrower sidebar, page-specific padding/insets) are often gated on a **path-conditional class set by the shared layout**, e.g. `<body class="{{ 'entry-page' if request.path in ('/a/new', '/a/return/new') else '' }}">`. Adding a new page to the family does not add it to that list, so the new page silently renders the default layout while its siblings render the compact one — the symptom is a subtly different sidebar width or content inset, not a visibly broken page. When a sibling page looks off by a few pixels of chrome, read the layout's path list first and add the new route there; do not duplicate the rule into the page.
- A layout rule must live in the layout, not in one page's `<style>`: a rule only the original page defines cannot apply to a page that never loaded that block, even after its class is set. Set the class *and* move the rule together.
- Verify parity by **measurement, not eyeballing**: load each page in a headless browser and read the real computed geometry (`getBoundingClientRect().width` / `getComputedStyle(...).flexBasis` on the layout region), asserting the whole family matches and that unrelated pages keep the default. Then lock it with a template test that asserts the class is present on every family route and absent elsewhere.
- When a vision model's description of a page disagrees with the measurement, **the measurement wins**. Visual models reliably misjudge layout: they read the empty space *inside* a component (the gap between two fields in one cell) as an empty grid column, and report a full-width row as "only 70% used". Re-derive the claim from computed geometry — walk the container's children, print each child's `x`/`width`, and check whether each row's right edge actually reaches the container's right edge — before changing any layout in response. If the model was wrong, say so rather than silently doing nothing.
- **To prove a visual separation exists, sample the rendered pixels — do not adjudicate it by eye or by a vision pass.** Whether two blocks read as one card or two is a question about the gap between them, and the gap has a colour: walk a single column between the two `getBoundingClientRect()` edges and print the RGB per row. Page background between the cards' own colours is proof of a real gap; card colour running continuously across the seam is proof the separation did not land. This is objective, reproducible, and survives a vision model timing out or misreading a crop — and a crop is exactly where it misreads, because the surrounding labels are gone. Pair it with a same-region before/after pixel diff count when you need to show the change actually altered the render.
- **Never put the candidate answers in a vision prompt.** Asking "是「查看」还是「回看」？" gets you the option you named — the model answers the question instead of reading the pixels — so a confident wrong answer can be used to tell the user they are mistaken about their own screen. Ask for a verbatim transcription with no interpretation ("照抄框内每个按钮上的字，不要解释"), and ask that same neutral question of *every* image you compare so the readings are commensurable.
- **When the user says a change did not land but your grep says it did, do not argue from a vision read — go to the served bytes and to the user's own evidence.** Pull the route's real output (`curl -s <route> | grep -oE '>(查看|回看|编辑|重编辑)<' | sort | uniq -c`), read the user's BEFORE and AFTER screenshots with the same neutral prompt and diff them, and check **which instance the user is looking at**: an older port, a stale process, or a packaged EXE all serve the pre-change markup while the file on disk is already correct. Present the discrepancy with the three readings and ask for the URL, rather than insisting the user misread.
- With the dev server's reloader off, restart it after template edits and re-check before reporting: a stale process keeps serving the old HTML and makes a correct fix look unapplied. **Confirm the served markup before trusting any measurement.** After a template edit, re-run the browser probe and get byte-identical numbers to the pre-fix run — the instinct is to doubt your CSS and widen it, but the usual cause is a long-running server whose template cache still holds the old file. Verify the *server's* output first: `curl -s <route> | grep -c '<new class>'` and compare against the same grep on disk; a served page still showing the old class names while the file on disk has the new ones means nothing you measure afterwards is about your change. `TEMPLATES_AUTO_RELOAD` set as an environment variable is **not** picked up — it needs `app.config['TEMPLATES_AUTO_RELOAD']` plus `app.jinja_env.auto_reload` on the app object, so the reliable move is to **restart the process** after template edits.
- **A running dev instance is stale in a second, less obvious way: it caches values it read at startup.** An app version string read once into app config, a config file loaded at boot, or any module-level constant will keep serving the pre-change value from a long-running process even though the template on disk is current — the `/health` endpoint reports the old version while the code is new, and it looks like the change did not land. Before trusting any value an instance reports, confirm the serving process **started after your last relevant edit**; if it did not, restart it (or start a fresh instance on a different port) rather than re-editing correct code.
- **A browser-automation probe must survive its own dialogs.** `alert()` and `confirm()` block the JS thread, so a probe that clicks a button which opens one appears to hang or returns nothing, and the next probe step reads a page stuck mid-action. Install the hooks *before* the first click (`window.alert`/`window.confirm` pushing into an array and returning a fixed answer, plus `Page.javascriptDialogOpening` if driving CDP), so a click either records the dialog or submits; a probe that never captures the dialog cannot tell "the button is dead" from "the button opened a confirm" — which is exactly the distinction the user's report turns on.
- **A note rendered only in one state, inside the same flex row as the controls it explains, moves those controls.** A hint emitted conditionally under the active filter chip joins a group that is right-aligned with `margin-left:auto`, so the group grows leftward and every chip shifts; the user reports it as "点完筛选按钮位置就变了". Move the text to a permanent slot outside the control row — a legend line that always renders, with wording identical in every state so the reserved line never changes height, placed outside the fragment the in-place refresh swaps. Then verify by measurement: read `getBoundingClientRect()` for every chip, the action bar, the legend, the table header and the first row in each state and require identical x/y (measured: chips at `1140/1196/1308,403` across 全部 / 待补全 / 待补全+按拼音排序, with bar `y=488`, legend `y=537`, thead `y=590`, first row `y=642` unchanged). When you retire the old container, delete its CSS rules too and assert the retired selector is gone from the served page (`assert ".list-facet{" not in html`) — a dead hook left in the stylesheet is what a later edit re-attaches to, and a page-scoped leftover silently restyles the next element that reuses the name. **Then measure it at the user's own viewport width, not only a wide one.** The same toolbar that measured pixel-identical at 1440 CSS px still shifted 15px at 1280 CSS px, from a second, independent mechanism: the inner scrolling pane gains or loses its vertical scrollbar when the row count crosses the pane height, which changes the pane's usable width by ~15px and drags every right-aligned control, the legend width and the table with it. The trigger is a state-dependent row count, so the fix is the pane's gutter, never a state-specific rule: `scrollbar-gutter:stable` on the scrolling pane, locked with `assert "scrollbar-gutter:stable" in html`. Derive the user's real width from the screenshots they sent (physical pixels ÷ display scale — 2559px on a 200%-scaled display is ≈1280 CSS px) and require identical x/y at that width too; when the two widths disagree, report both numbers instead of the one that passed.
- **A viewport-only screenshot cannot confirm a region that sits below the fold.** The toolbar, legend, or table you just changed is often not in the image at all, and a vision pass on that screenshot then reports the block as absent — you will "verify" a layout you never saw. Capture the whole page (`Page.captureScreenshot` with `captureBeyondViewport: true`, decoding the base64 yourself) before judging any region's appearance or handing a screenshot to the user as evidence.
- **Deleting a conditional-render block means deleting its Jinja tags too, not just the text between them.** Replacing only the visible string leaves a stray `{% endif %}` and the template stops compiling — `TemplateSyntaxError: Encountered unknown tag 'endif'` — which fails **every** page extending that layout, so a one-line edit reads as a catastrophic regression (one leftover tag produced 23 failing tests at once). Delete the whole `{% if %}…{% endif %}` span, then re-render the affected pages immediately (the template tests alone are enough) before touching anything else.
- **A backgrounded dev server can survive the kill you believe succeeded, and then serve a data root you have since deleted.** Killing the PID your launcher reported can leave the real child still LISTENING; relaunching then binds **two** listeners to the same port (measured), and requests land on whichever the OS hands them to. Delete or re-seed the scratch data root only after the listener list is empty — a surviving instance serving a deleted database returns `500` on every route including the health endpoint, which reads exactly like an application defect and sends you debugging correct code. Start the next instance on a **fresh port and a fresh data root** instead of reusing either.

## Fitting a requested arrangement into one row

- **Measure the budget before implementing a "put A next to B" request; `flex-wrap` turns an impossible one into "nothing changed".** Read the tier/filter container's real content width off the rendered page (`getBoundingClientRect().width`), then sum the groups' own widths plus the row's `gap` and compare. Measured example: a 1258px viewport left **835px** usable while the three groups needed **1096px** — so the last group wrapped and the page still showed the two-row layout the user had asked to replace. Deriving the budget from `window.innerWidth` minus the sidebar overshoots by the content margin, the scrolling pane's padding and the card's padding.
- Report the shortfall as a table, not a sentence: viewport → usable width → required width → one row / wrapped, at the user's own width **and** a wide one. "Why is it still on the second line" is answered by a number, and so is "what do I have to change for it to work".
- Cheap levers in the order to try them, with their floors: row `gap` → the date/select `min-width` → the text fields' `min-width`/`max-width`. Past roughly 120px a date field clips its own value and past ~130px a name field shows two or three characters; that is the floor, not a target. The segmented mode-button group is the largest single item on such a row — converting it to a `<select>` is the one lever that changes how the page is operated, so present it as an option rather than taking it.
- **Before offering the user a trade-off, look for the fat sub-block — and measure the sibling page they cite as already fitting.** When the user says "page B does it in one row", page B is a measurement, not an opinion: read both pages' block widths off the rendered DOM and diff them, because the shortfall is usually one fat sub-block rather than the whole row. Measured here: the sibling page's time block was **470px wide × 82px tall (two lines — label + mode buttons, then the date range)** while the target page's was **596px × 40px (everything on one line)**; that single difference held 126px of the shortfall, and replicating the sibling's internal stacking freed enough width for the third group **without narrowing any control and without changing how anything is operated**. Diff block-by-block, and check whether the reference page's own arrangement already answers the request before listing what the user would have to give up.
- **A wrapping flex container cannot be narrowed by making a child wrap: its max-content width is the sum of the children's unwrapped widths, so the parent keeps the wide measurement.** Putting `flex:1 1 100%` on the second-line child moved it onto its own line *and* left the container measuring 596px — the visual wrap and the container width are independent. Use `display:grid;grid-template-columns:auto auto` for the first line plus `grid-column:1 / -1` on the full-width child: an `auto`-column grid sizes to the **widest column**, so the container collapses to the label+buttons width (measured 596 → **296px**) while the dates still render on their own line. Grid also absorbs an extra child (a second mode group, a hidden panel) better than hand-tuned `flex-basis` arithmetic.
- **`align-items` on the row decides which sub-line the moved group lines up with, and the user's wording picks it.** With a two-line block on the left and a 40px group on the right, `flex-end` puts that group on the **second** line (measured `top` equal to the date range's) and `flex-start` puts it on the **first** (the sibling page's look, aligned with the label and buttons). "Put it to the right of the date field" means `flex-end`; "same row as the filters" usually means `flex-start`. State which you chose, because both read as "same row" in a summary and the difference is visible.
- **A layout you are reversing carries a comment asserting the previous intent.** These filter rows get asked to stack and then asked to sit side by side within days, so last round's rationale ("列方向下 flex-basis 作用在高度上…") becomes a lie the next reader trusts. Rewrite the comment in the same edit to say which round reversed the direction and why, and keep the old reasoning only where it still holds for the new direction.
- Verify by reading every group's `getBoundingClientRect()` in one pass: equal `top` (or equal vertical centres when the groups' heights differ) plus a right-edge check that the row stays inside the container, and re-measure after each `min-width` change instead of assuming the wrap threshold moved as predicted.

## Changing a container's children

- **When a container's children change, re-read the container's own layout properties and delete the stale ones — a leftover `display:grid`/`flex` plus track definitions silently re-parents the new children into tracks.** A summary block whose markup moved from "three cards directly in the container" to "one heading + one card grid" kept its old `display:grid;grid-template-columns:repeat(3,minmax(0,1fr))`, so the heading and the grid each became a grid item and took one column: the heading was squeezed to a third of the width and the six cards were compressed into that same third (measured: cards 90px wide, a `¥24012.03` value needing 110px inside 58px of usable space — overflow 52px with one value wrapping to two lines and a three-line footnote hitting the card floor). Every class in the new markup was correct, and a test asserting "the grid has 4 columns" passed. Before restyling a region you restructured, grep the container's selector in the stylesheet and check whether its `display` / `grid-template-*` / `flex-*` still match the child list you just changed; while you are there, delete sibling rules whose template no longer exists (a dead class is what a later edit re-attaches to).
- **`min-width:0` swallows a leaf's overflow, so "the page has no horizontal scroll" is a false acceptance criterion for a visibly broken layout.** The overflowing text wraps or clips *inside its own box*, so `document.documentElement.scrollWidth` stays equal to `clientWidth` and the page-level check reports clean while the user is looking at squeezed numbers. Measure the leaf against its own box — `valueEl.scrollWidth > valueEl.clientWidth`, plus the same on the card — and treat the user's stated outcome as the bar. Same trap as an `ellipsis` + `nowrap` table cell: the overflow lives inside the element, so only a per-element measurement sees it.
- **Wrapping an element in a new container moves its `position:sticky` containing block, which silently kills "stays visible while scrolling".** A sidebar nav declared `position:sticky` directly inside the grid area stuck correctly; adding a wrapper (a flex column whose height is just the two cards it holds) made that wrapper the containing block, so past the wrapper's own height the whole column scrolled away with the content — no error, no visual cue, and it looks fine at the top of the page. Move the sticky declaration **up to the wrapper** when you introduce one, and turn it off in the narrow breakpoint that re-lays the wrapper as a row. Verify by scrolling to two different offsets and requiring the element's `getBoundingClientRect().top` to be **identical** at both — a single reading at scroll 0 proves nothing (measured: 192 → −320 before the fix, a frozen 99 after).
- **Sticky sticks to the containing block's *padding* edge, so compare against the pane's content box, not its border box — otherwise a correct sticky reports as broken.** The scrolling pane carried `padding-top:20px`, so the frozen position measured 99 while `pane.getBoundingClientRect().top` read 73; a check written as `Math.abs(stuckTop - paneTop) <= tolerance` fails on a layout that is working. Compare the element's top across two scroll positions, or compare against the pane's padding edge.

## Believing a styling fix

- **Scope a variant's selectors before removing a box treatment.** When two components share the same class names (a horizontal bar row and a vertical bar chart both using `.rank-bar-track` / `.rank-bar-fill`), a generic rule on those names still applies every property your new rule does not restate — delete `background`/`border` from the chart's own rule and the horizontal variant's `background`/`border`/`border-radius` leak back in, so the box reads as never removed. Namespace the sibling's selectors (`.rank-bar-row .rank-bar-track`) and add explicit resets (`background:none;border:0;border-radius:0`) on the variant you changed.
- **Disable the browser cache before reading computed styles.** A versioned stylesheet URL (`styles.css?v=1`) is served from disk cache, so a correct CSS fix reads as unapplied and sends you chasing a bug that is not there. Set `Network.setCacheDisabled`, reload with `ignoreCache: true`, then re-read `getComputedStyle` before concluding anything — and when the computed value still shows the old treatment after a cache-disabled reload, suspect a cascade leak rather than more caching.
- **To assert two flex children share one row, compare vertical centres, not top edges.** Under `align-items:center`, children of different heights legitimately have different `y`, so a top-edge comparison reports a false negative on a layout that is correct. Compare `y + height/2` with a few-pixel tolerance, and measure the gap from the button group to the container's right edge as well — a gap that grows with viewport width is the evidence that the group sits adjacent to its chips rather than pushed to the far edge.

- **A de-stacking ("one layer only") fix must enumerate every nesting path; a structural test on the rule text cannot catch a missed one.** When the requirement is that each region show one container (one glass/border/shadow) instead of stacked ones, the rule set names known container selectors (`.table-responsive > table`, `.today-history`, `.order-details-card`, …) and the test asserts those selector strings are present — but a **glass card nested inside another glass card** is a second stacking path that repeats neither the container class nor the sibling page's structure, so the rule passes while the page still renders two layers. Example shape: a source-preview panel sits inside the order-info card on the purchase-return entry page but the rule set only covered `container > table`. Enumerate nesting by type — bare table, container-over-table, glass-card-over-container, **glass-card-over-glass-card** — rather than by the pages you happened to measure. Verify the outcome by **measuring computed layer depth per rendered page**: walk each table's ancestor chain and count elements whose computed `backdrop-filter`/`-webkit-backdrop-filter` is not `none`, across every page that renders the component; the fix is complete only when the maximum depth is 1 everywhere. A green structural assertion says the rule exists, not that the layering is gone.

- **Alpha-composite before comparing contrast on a glass UI; a naive probe reports false low-contrast.** Measuring `getComputedStyle(el).color` against the nearest non-transparent ancestor treats an `rgba(...)` glass panel as opaque, so a translucent-glass theme reports spurious failures (e.g. a red-tinted return row reading 1.9:1 when the real value clears the bar). Resolve the effective background by walking the ancestor chain and compositing each layer outermost-first, then composite the text's own alpha over that result, before computing the ratio. Before writing any hit up as a defect, read the element's real `color` and `backgroundColor` — the first pass is usually the scanner's bug, not the page's.

## Sidebar navigation ownership

- **Derive the active sidebar item from the route's owner (endpoint), not from `request.path.startswith(...)`.** A prefix test matches the *serving* namespace, so a page that is reached from module A but served under module B's prefix (a reconciliation screen under `/analytics/...` linked from `/accounts/`) highlights B forever. The tell in the template: the link already carries a source parameter used only for the back action's label and href, while the highlight ignores it — the back button and the sidebar then disagree on which module the user is in.
- Fix shape: map endpoints to owners (`orders.*` → 单据管理, `accounts.*` → 账款管理, `analytics.*` → 数据分析, …) and let an explicit source parameter override the owner for cross-module pages. Prefix strings re-break on every new page added outside its own namespace, so they are a maintenance debt even when they currently look right.
- **Audit the whole sidebar for double-highlighting, not just the item you are fixing.** A secondary "ancestor/current" class applied to a parent entry (e.g. 工作台 marked current on every child route) can reuse the active item's text colour while carrying no background, so two entries read as selected and a class-name-only check passes. Compare the **computed** `color` and `backgroundColor` of every sidebar entry on each page, not the class list.
- Recipe: enumerate the module's routes (one per sidebar entry plus the cross-module pages), load each, and print the entries whose computed colour differs from the muted default. Do this before and after the change; the assertion is "exactly one entry highlighted, and it is the one the user came from".

## Scroll position across a filter submit

- **A `method="get"` filter form is a full navigation: the scrolling pane resets to the top and the page visibly flashes.** With the app shell scrolling an inner pane (`.page-body`) rather than the document, the browser's own scroll restoration has nothing to restore, so `history.scrollRestoration` is irrelevant.
- Measure before theorising: for each affected page, read the pane's `scrollHeight`/`clientHeight` to confirm it scrolls at all, set `scrollTop` to a non-zero value, click the primary submit, wait for the load, and read `scrollTop` back. A return of `0` is the defect; record the before/after pair per page so the report names which pages are affected.
- The fix is the page's existing in-place fragment refresh, not a new mechanism: fetch the URL, replace only the result fragments, `history.replaceState` the URL so state stays linkable, and restore the pane's scroll anchor. Keep a real navigation as the fallback when the fetch fails.
- **When one page mixes both behaviours, that inconsistency is itself the finding.** A page where tab/day/view-selector switches already refresh in place while the main filter card still full-reloads is the common state of a partially migrated page, and the user experiences it as "有些操作会闪、有些不会". Enumerate every control that changes data on the page and classify it wired/un-wired before proposing the change, so the plan covers the whole page instead of the one button that was clicked.
- Watch the client scripts attached to the form: export links and preview URLs are often kept in sync with live field values on `input`/`change`. If the submit becomes a fetch, that sync must still run — otherwise the exports silently keep stale parameters.

## Running the audit scripts (install once, then prove detection power)

- **Install `ws` next to the skill, not in the project.** `audit-nav-and-scroll.mjs` needs `ws`, and a project may be pure Python with no `package.json` (adding one just for an audit tool pollutes the repo). Node resolves upward from the script's own directory, so `npm i ws` inside the skill directory works for every project, and `import('ws')` from `scripts/` finds it. A skill directory is usually outside any git repo, so this adds no repo noise either.
- **Prefer the packaged probe scripts over hand-rolling a new one, and start Chrome with `--remote-allow-origins=*` when you do hand-roll.** A CDP client that connects over a WebSocket is rejected with `403 Forbidden … Use the command line flag --remote-allow-origins=…` unless Chrome was launched with that flag, because the client's origin is not the DevTools page — the failure is at connect time and reads as "Chrome did not start". When a probe must read a value the bundled scripts do not cover, write a small throwaway probe that takes the URL, a JS expression file, and a viewport size, prints `window.innerWidth`/`devicePixelRatio` alongside the result, and terminates Chrome in a `finally`; keep it in scratch, not the repo. Always print `innerWidth` — headless Chrome's `--window-size` is a window size, not the CSS viewport, so the numbers you get are not the ones you asked for and you must record the real value next to every measurement.
- **A native Windows binary cannot open an MSYS-style path, so a `--screenshot=<path>` written as `/c/Users/...` silently writes nothing.** Bash builtins accept `/c/...` while a native executable receives the literal string, fails to resolve it, and reports `Failed to write file … 系统找不到指定的路径` with the process still exiting `0` — so "the command succeeded" and "the file exists" are two different checks. Pass native `C:/...` forward-slash paths to any Windows executable launched from bash, and assert the output file exists (non-zero size) rather than trusting the exit code.
- **"ALL CLEAR" on the first run proves nothing until you have seen it fail.** Deliberately break the thing it checks (remove the `data-inplace` marker from one filter form, or the owner mapping for one route), re-run, confirm the expected `FAIL` + non-zero exit, then restore and re-run for green. A script whose detection you have never observed failing can be silently matching nothing.
- **Restart the dev server after the deliberate break — a cached template keeps serving the old markup** and the script reports green on a page that no longer has the marker. Confirm the served HTML actually changed (`curl … | grep -c '<marker>'`) before trusting the run, exactly as for any other template edit.
- Two false-failure traps already fixed in the script; keep them fixed if you edit it:
  - **Do not target `form button[type=submit]`.** A plain `<button>` with no `type` is an implicit submit and matches no attribute selector, so the primary control is reported as `submit=none` and the page silently skips the scroll check. Match by behaviour instead — the first GET form's `button:not([type]), button[type=submit]`.
  - **Do not test a POST form's submit.** Saving settings (or any other POST) navigates by design and correctly lands back at the top; measuring it produces a permanent false failure. Only GET filter forms are in scope.
- The nav half must compare **computed colour/background**, never class names: a secondary "current/ancestor" class reuses the active text colour with no background, and a sidebar legitimately has two muted text levels (section entries vs indented sub-items), so a single hardcoded muted constant flags every sub-item. Expect a **set** per page, not "exactly one" — a parent entry and its sub-item are correctly lit together on an entry page.
