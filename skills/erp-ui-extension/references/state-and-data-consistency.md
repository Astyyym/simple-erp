# State and Data Consistency

Read before deriving a value from another field, adding a status flag, inserting a synthetic row, or surfacing a rejected action.

Split out of the `Always-On Rules` list in `SKILL.md`; each rule keeps its original wording.

## 1. First-use guidance predicates

- **A first-use guidance prompt must key on fields that are genuinely blank, and must be dismissible in both directions.** When you add an onboarding card ("finish setting up X"), compute "missing" from the fields that are actually empty in the shipped defaults — a field with a factory default is never blank on the printout, so counting it makes the condition true for every user forever and the card becomes permanent noise the user learns to ignore. Put that predicate in **one shared function** called by both the card's page and the owning settings page, so the two can never disagree. Give the card a dismiss action **and** a symmetric re-open action in settings (a one-way dismiss is a dead end the user cannot undo), store only a boolean flag, and **never let the dismiss write any of the business fields it is about** — assert that in a test. Verify the promise end to end: fill the fields through the real settings form and check the *rendered print/preview output* actually contains them, not just that config changed.

## 2. Clock is client-side; view switches refresh in place

- **A clock, timestamp, or any "current time" in the shell is a client-side element, never a server-rendered value.** A template-rendered `now` is frozen at page load: it looks like a live clock and is wrong within seconds, so it is worse than showing nothing. Render a placeholder and drive it from a `setInterval`-based client script; give the digits `font-variant-numeric: tabular-nums` or the seconds ticking reflow the whole line, and route colour/size through the theme and scale tokens (`--erp-muted`, `--erp-scale`) so it survives dark mode and 125%/150% zoom. Note that a top-bar slot is **shared by every page** — say so when the user circles it, because "add it here" reads as one page but ships everywhere. Re-read the shell's own layout contract before touching it: if the top bar is a pinned glass strip (`backdrop-filter`), add the element inside the existing flex row rather than introducing a wrapper that changes its height or stacking. Do not set the value from the server "just for the first paint" — it produces a visible jump from a stale time to the live one. Also flag the attention cost: a per-second clock on a working screen pulls the eye continuously;
offer the minute-precision variant as the cheaper default and let the user choose. Switching a tab, changing a display selector, or selecting a calendar day is a view change over data already fetched; a full navigation flashes the page and throws the reader back to the top, and the user reports it as "为什么要强制闪烁刷新". Wire such controls into the page's existing in-place fragment refresh (replace the result fragments, sync the URL with `history.replaceState` so the state stays linkable, restore the scroll anchor) instead of an `<a href>` or a plain form GET, and fall back to a normal navigation only when the fetch fails.

## 3. Derived values must re-derive on header change

- **A value derived from a header field must re-derive when that field changes, and a script-written hidden input fires no event — so "listen for `change`" is not the fix.** When a line's price (or any row default) comes from a header control such as the counterparty, resolving it only inside the row's own pick handler makes the feature order-dependent; wire the derivation to the header field too and re-run it over every already-filled row. Two mechanisms the naive attempt misses: assigning `input.value = …` from script (an autocomplete on-pick callback, a "sync from the linked document" helper) fires neither `input` nor `change`, and a `MutationObserver` will not see it either because `value` is an IDL property, not a content attribute — so detect the change with a **value fingerprint** polled on a short interval, committing only when the string differs, and also accept a custom event so a handler that just wrote the field can force an immediate commit. Then guard the re-derivation: (a) give each row a **sequence counter** so a slow response for the previous counterparty cannot land after the new one and overwrite it;
(b) query by the **canonical name from the embedded catalog**, not the row's live input text, which the operator may have edited into a form the server does not match; (c) **exempt rows whose value came from a linked source document** — a line brought in from an original sale must keep its original transaction price, so re-pricing it silently rewrites history and no longer matches the source preview. Decide and state whether an override the operator typed is preserved or replaced; never leave that implicit. Which side owns which price: [`references/document-scope-and-display-rules.md`](document-scope-and-display-rules.md).

## 4. Rejected actions must show the reason

- **A rejected action must show the server's reason on the page; a bare text page or a generic "failed, refresh and retry" is a defect.** When a delete/purge/bulk/void is refused by a business rule, the user must see *which* rule and *which* row, with the page and their selection intact. Route every rejected path through one presentation layer (fetch → in-page message list), never a native `form.submit()` navigation and never a fixed client string that discards the reason. A conditional write whose guard matches nothing affects 0 rows **without raising** — check the affected-row count and raise a specific reason, or the action reports success while doing nothing. See [`references/action-failure-surfacing.md`](action-failure-surfacing.md).

## 5. Synthetic rows must be excluded from traversals

- **A synthetic (non-data) row inserted into a live edit table must be excluded from every traversal, and the add-row helper must return the row it created.** Dropping a page-break/notice/divider row into the same `<tbody>` that the page re-numbers, clones, counts and submits has a wide blast radius: the renumber loop throws on a row with no number cell, add-row clones the wrong row, a caller that takes `tbody.rows[last]` receives the notice the repositioner just moved after its new row, and the delete/count logic treats the notice as a record (so "delete last row" removes the notice and the button's disabled state goes wrong). Give the row its own class, filter every `tr` traversal with `:not(.<that class>)`, make add-row `return` the new row instead of letting callers index the last one, and count data rows rather than `rows.length` for button state. It carries no `name` and no input control, so it never enters the payload — assert that rather than assuming it. Recipe and evidence: [`references/document-print-pagination.md`](document-print-pagination.md).

## 6. Order multi-item changes; delete removed blocks

- **Order a multi-item change so the tree is never left inconsistent, and never stub a removed block with a hidden placeholder.** When one request bundles several fixes, do the self-contained ones first (a CSS-only fix, a wiring fix) and the ones that invalidate existing assertions last, so a session cut short leaves a coherent tree. A removed UI block must be **deleted outright**, not replaced by a hidden or `d-none` placeholder "for now" — the placeholder survives into review, reads as intentional, and a hidden-but-present element is exactly the kind of thing a later test or CSS rule reattaches itself to. Likewise, widening a backend gate (e.g. making every row deletable) before updating the tests that assert the old gate leaves a red suite: sequence the assertion updates in the same change, and when the session must stop early, report precisely which assertions are now stale rather than leaving them to be discovered.

## 7. Explanatory text lives outside the row

- **State-dependent explanatory text must never be rendered inside the row it explains, and a pair of sibling list pages is one change, not two.** A note emitted only in one filter state (「仅显示…」 under the active chip) joins a group that is right-aligned with `margin-left:auto`, so the group grows leftward and every chip jumps the moment the state changes — the user reports it as "点完筛选按钮位置就变了" and asks you to move the text. Render the explanation in a **permanent slot outside the control row** (a legend line that always renders with state-independent wording, placed outside the fragment the in-place refresh replaces), never inside the chip container. Keep the sibling pages' toolbars structurally identical — same containers, same chip set, same order — and when the user says 两页要同步, change **both** pages in the same edit and assert parity in the tests;
one page left on the old structure is exactly the "为什么这一页和那一页不一样" report, and "we agreed the rule earlier" does not survive as an excuse. Once the user picks a placement for a shared block, apply it to every page of the family rather than offering the choice again. Verify by measurement, not by eye: read `getBoundingClientRect()` for every chip, the action bar, the legend and the table's first row in each state and require identical x/y (measured: chips at `1140/1196/1308,403` unchanged across 全部 / 待补全 / 待补全+按拼音排序). **Do not close it on one viewport width** — the same toolbar that was pixel-identical at 1440 CSS px still shifted 15px at the user's real 1280 CSS px, because the inner scrolling pane gains or loses its vertical scrollbar (and ~15px of usable width) the moment the row count crosses the pane height; reserve the gutter (`scrollbar-gutter:stable` on the scrolling pane) and assert the same x/y at the user's own width as well, which their screenshots give you (physical pixels ÷ display scale). Depth, plus the template-edit pitfalls that go with it: [`references/browser-audit-recipes.md`](browser-audit-recipes.md).

## 8. A status flag is one 口径

- **A status flag (待补全 / 需处理 / 待定价) is a 口径, and a 口径 must exist exactly once.** One predicate module owns the rule and exports the SQL fragment that the list query, the count, the row badge, the edit-page hint and any pre-check preview all use — a second hand-written `WHERE` is how the count says 3 while the list shows 4. When the user asks whether a case is already handled ("导入字段不完整会怎样？"), never answer from the code's intent: run that exact case against a real isolated instance and report what actually happens — imported, flagged, or rejected — as a short table **before** proposing anything, then read the predicate's **source restriction** first, because a flag scoped to one origin (records created from documents) silently excludes the origin the user is asking about (imported records) and that exclusion is usually the whole answer. Widening a flag to a new source is one change: widen the predicate and its exported SQL fragment together, grep the old restriction string across routes, templates and tests, and update the badge wording, the legend/help text and the count assertion in the same edit. Keep a user-authored record out of the flag only as an explicit,
written decision. Recipe, the importer pattern (allow the optional field blank with a safe default, then remind in three places) and the verification pitfalls: [`references/import-and-completion-flags.md`](import-and-completion-flags.md).
