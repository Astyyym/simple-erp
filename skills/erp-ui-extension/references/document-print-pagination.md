# Document print pagination

Use when a generated business document (ledger, statement, long order) must span more than one page, or when a user reports that a document was split, repeated, or left a blank page.

## Break by the layout engine, not by a guessed row count

- Do **not** chunk a document into fixed-size blocks (e.g. every 12 lines) to control pagination. A constant cannot know the real page capacity, so a document that fits on one page still gets cut into "continuation" segments while one that needs two pages gets cut into three. The user sees a single-page document labelled 第 1/2 段 and reads it as broken.
- Preferred: emit one block and let the layout engine break it naturally (`break-inside: auto`). This guarantees "no split unless it actually overflows". The trade-off is that a header repeated on each page is not available — the engine cannot inject a table header mid-flow.
- If a repeated header per page is genuinely required, chunk only when the content exceeds one page's measured capacity, and derive that capacity from measurement rather than from a row count chosen by eye.
- Print a document-level total **once** when you are emitting explicit segments. Repeating the same total on every continuation segment is what makes a reader mistake segment subtotals for separate documents.
- With the natural-break approach there are no segments, so the continuation page carries no document header at all. Compensate by printing the document amount on **every item row** rather than only the first: each row then identifies its own document, and the total still appears exactly once per document in aggregate. Do not combine the two — either explicit segments with the total on the first segment, or one block with the amount on every row.
- Derive the printed amount's **sign from the business direction**, not from the stored column. An inbound/purchase table commonly stores a positive total whose balance effect is negative, so printing the stored value puts a `+` on a document that the ledger and summary cards show as negative. Compute a display amount from the entry type (sale +, return −, purchase −, purchase-return +) and assert it against the ledger's own direction field. When only some types need flipping, flip those explicitly rather than re-deriving every sign from scratch.
- Continuation markers belong on the fields that identify the document (type, number, segment index); do not add a second copy of the money column to carry them.

## Share the per-page row constant with the entry page

- Keep rows-per-page in exactly one place, in the backend (a module constant in the config module, deliberately *not* a user-facing config key), and inject it into the template environment as a **Jinja global in the app factory**. Per-render-point context arguments are the trap: the print template is rendered from several call sites (order PDF, purchase PDF, settings sample), and at least one of them goes through `current_app.jinja_env.get_template(...).render(...)`, which bypasses context processors entirely — forget it there and nothing reports an error.
- **A template that lost its batch variable does not fail — it silently stops splitting.** `{% for chunk in items|batch(slip_size) %}` with an undefined `slip_size` never compares equal to a length, so every row lands in one chunk and the document prints as a single overflowing page with no exception anywhere. That is the reason to inject the value at the environment level rather than per call, and to assert in a test that the template contains no second literal for it. Bare `jinja2.Environment` fixtures in the test tree must set the same global themselves, or their page-count assertions go quietly wrong.
- The entry page does not inherit the print template, so it reads the same injected value — but its notice row is a *runtime* need (rows get added, removed, cleared, and pre-filled from a source document), so re-position it in JS on every row-count change instead of emitting it with Jinja `batch`. One mechanism then covers first paint and every later edit; two mechanisms drift the moment someone adds a row at runtime.
- Verify the shared source by changing the constant once and asserting both surfaces move: the rendered print document's batch size and notice wording, and the entry pages' injected value.

## Verify pagination by rendering, not by reading the template

- Render the PDF, count pages programmatically, and extract per-page text to confirm which segment markers and totals land on which page. A template that looks correct can still emit an extra blank page, and a "2 pages" claim based on source inspection is not evidence.
- Assert the document total appears exactly once across the whole PDF, not once per segment.
- Confirm the page box (e.g. A4 portrait 210×297mm) is unchanged by the pagination change, and assert the last page actually contains rows.
- A PDF text/renderer package is often absent from the project venv; install it into a throwaway environment rather than adding it to the project's dependencies, and put that environment on an ASCII-only path.
- **To decide whether a summary block below the table costs a page, measure the block's own height rather than its line count.** Render just that fragment on a very tall page of the same content width (A4 portrait with 11mm side margins = 188mm) and read the lowest content coordinate. Walk the box tree from the root `html` box, never from `page._page_box`: the page box also contains margin boxes, and a `@bottom-center` page counter sits at the page bottom, so measuring from the page box returns the full page height for every input. WeasyPrint lengths are CSS px (`mm = px * 25.4 / 96`), and its own `@page` rule must be stripped with a brace counter — the template's `@page` contains a nested `@bottom-center { ... }`, which a regex leaves half-parsed. Probe: `scripts/measure-print-block.py` in the `erp-analytics-delivery` skill. Report the block delta **and** the page-count change, plus the marginal cost per dynamic row (a per-payment detail table measured ≈6.7mm per row) — a block's fixed height is rarely what pushes a document onto another page, and a row-growing block is what makes a statement unpredictable.

## Engine pitfalls that force a workaround

- Some layout engines crash on backgrounds in table layout, but the trigger is narrower than "a splitting cell". Measured on WeasyPrint: a background on a `td` that splits across pages is **fine**, a background on an inline `span` inside the cell is **fine**, and a background on a **`<col>` element** crashes with `AttributeError: 'TableCellBox' object has no attribute 'border_top_left_radius'` (from `layout_backgrounds`). The trap is a bare class selector: `.col-amount{background:…}` matches both the `<td class="col-amount">` cells and the `<col class="col-amount">` in the `<colgroup>`, so a column tint silently routes through the crashing path. Scope column backgrounds to `td.class` / `th.class` and the tint works. Confirm with a minimal three-way probe (td / span / col) before redesigning the emphasis.
- Merged header cells (`rowspan`) combined with a chunked table body is a common crash trigger; repeating the full header on each block avoids it.
- A dead CSS rule left in a print template is still a hazard: a class defined but no longer referenced still carries a background that would crash the engine the moment someone applies it. Delete unused print rules rather than leaving them inert.
