# ERP UI Extension

## When to Use

Use when adding inventory, purchasing, returns, analytics, reconciliation, or other workflows to an existing ERP whose UI/UX has already been implemented or accepted.

## Procedure

1. **Freeze the baseline before designing.** Read the current PRD, real templates, shared layout/styles, existing interaction tests, and previously accepted prototypes for affected pages. Map navigation, page ownership, surfaces, controls, responsive rules, keyboard behavior, filters, pagination, and print/preview boundaries. When continuing a dirty cross-session worktree, inspect live source, tests, and uncommitted files before trusting the plan's phase labels; preserve unrelated partial slices and reconcile the plan only after fresh evidence. Reconcile the index and status lines as well as the plan body: an entry still saying a completed item was out of scope, or quoting a stale evidence count, misleads the next session into redoing or skipping work. Re-verify the count you are about to write by running the suite, never by copying the previous line.
1a. **Treat a batched UI-feedback list as an investigation, not a to-do list.** When the user sends several screenshots and a paragraph of observations and asks for "your understanding and suggestions", produce one section per item: the current implementation as it really is (read the template, route, and CSS — do not infer from the screenshot), the **root cause**, the proposed change, and the risk. Separate the items that are pure styling from the ones that are structural, because a structural one (different DOM nesting, a colliding identifier, a scope difference) cannot be fixed by restyling. Surface conflicts between items explicitly — a request that contradicts existing data or an existing rule must be raised, not silently implemented in a way that breaks it. Then ask only the **blocking** decisions (typically two: one naming/semantics collision, one scope question) and wait; do not open the implementation plan until they are answered. Grep the test tree for assertions on each control you plan to restructure and list the tests that will need updating in the same plan. Read the current behaviour from the template and the live rendered HTML, not from the screenshot: a vision pass readily misidentifies which page an image shows and misses controls that are actually present, and a cropped region is easily misread. Use the images only to locate *what the user is pointing at*, then confirm every claim about existing behaviour in the source before proposing a change. When the user states a rule change that collides with an existing invariant (e.g. a prefix that already belongs to a sibling document type), surface the collision and the alternatives in the same reply instead of picking one silently. Locate an annotation **programmatically, not by eye**: a box drawn on a screenshot is a saturated colour, so scan the image's pixels for that colour and compute the bounding box to learn exactly which region it covers, then map that region back to the owning container in the source (the shell's top bar, a specific card, a table cell). A zoomed vision pass over a crop loses the surrounding labels and readily misreads which container the box sits in, and a region with no text of its own is easy to attribute to the wrong element.
1b. **Classify every item into one of three kinds before proposing anything, because each needs a different reply.** The user's framing ("这个功能坏了" / "我记得之前设计过") is a hypothesis, not a finding, and the three kinds are routinely confused:
   - **Regression** — the behaviour existed and was removed. Prove it with history, not memory: `git log --oneline -S"<distinctive marker>" -- <path>` (the identifier, the CSS class, the function name — not the prose). The session that found a product picker had been replaced twice (custom combobox → two native `<select>`s → `datalist` + free text) could answer "你没记错，是被换掉了" with a commit and a version, which changes the fix from "design it" to "restore it".
   - **Never implemented** — say so plainly and show the zero: `grep -rn "<marker>" app/` returning nothing, plus `git log -S` finding no commit in the whole history, is conclusive. Do not let the user's recollection pull you into treating it as a bug.
   - **Misremembered surface** — the feature exists but on a *different* surface. An affordance designed into the **print/PDF** template (a per-slip continuation notice, a per-page subtotal) is easily recalled as belonging to the **entry page**; check the sibling surfaces before agreeing, and when the entry-page version is genuinely absent, re-frame it as a new feature with its own acceptance bar.
   - **Implemented but order-conditional** — the feature works, but only under one input sequence, so an operator who uses the other order concludes it does not exist at all and reports it as missing ("this field has no value for this record?"). The usual shape: a row-level value resolved from a form-level field **at the instant of one interaction** (a line price read when the product is picked) is never re-read when the header field changes afterwards. Prove it by driving both orders against seeded data and tabulating the result per order — that turns "no such feature" into a wiring gap with a number attached, and it is a real bug like the first kind.
   Only the first and the last are bug reports. Say which kind each item is in the first line of that item's section — the user's next decision depends on it.
1c. **When the item is "merge / split a field", scope it by grepping the symbol in both trees, then separate the data-model change from the UI change.** Count occurrences of the field name in `app/` and in `tests/` separately (a merge of two identity fields measured 273 vs 239 across 54 and 62 files) and enumerate what the change reaches: the unique index over the pair, every detail table carrying a snapshot of the field, the print template, the analysis filter that requires the first field before the second, the import header matrix, the "incomplete record" badge. Two things must be said in the reply: what the merge **fixes** (a merge of name+model dissolves the deadlock where auto-created records with an empty second field can never be given one because the pair is already taken) and what invariant it **loses**. Then offer a staged migration (data layer → surfaces → call sites/tests) with the field left in place but unused first, and ask the blocking question (the separator/format of the merged value) before opening a plan. Never open with "工程量比较大" — scope it with numbers, or the user cannot weigh it.
2. **Define extension points, not a replacement product.** Map each new workflow to an existing owner such as workbench, order entry, document management, master data, analytics, or accounts. Reuse the existing shell, topbar, sidebar hierarchy, glass panels, table density, button language, theme controls, and viewport controls.
2a. **Before deleting a control the user calls useless, find out whether it is the only writer of a state.** "把这个按钮/原因输入框删掉" is a request about the **UI**, and it is usually satisfiable without touching the underlying mechanism — but only if you first trace what the control actually does. Check whether the control is the sole entry point to a state transition or a reversal/compensation routine (a void that reverses stock postings, a refund that restores a balance, an approval that unlocks the next state), and whether other code reads the field it writes (`status='void'`, `void_reason`, a timestamp). When it is load-bearing, say so plainly with the mechanism and the blast radius (how many tests and requirement clauses assert it), then offer the shape the user actually wants: **remove the UI, keep the mechanism** — move the transition behind the action the user does want (deleting a document auto-reverses it first) with a fixed internal reason, so the ledger stays conserved and the user never fills a form. Only strip the mechanism itself if the user, after hearing the cost, still asks for that; then treat it as a correction-model redesign with its own plan, not a UI tidy-up. Note the ordering trap: if deletion is gated on the state the removed control produces ("must be voided before deleting"), deleting the control first makes every document permanently undeletable.
3. **Preserve accepted interactions explicitly.** Carry forward customer/product autocomplete with ArrowUp/ArrowDown/Enter/Escape, customer-price versus regular-price switching, one default line plus add-row and clear-all, date-mode filters, 50-row pagination, selection semantics, same-day history, and the existing workbench quick-action layout.
3a. **A two-level picker cannot bootstrap itself; check whether the control can express "not in the catalog yet".** A name→model picker built from the existing catalog is correct for a populated database and unusable on an empty one: with no products the dropdown has no options and the operator cannot issue the first document at all. Same for any control whose options come only from existing records. Before extending entry pages, determine whether the operator is expected to have master data already, or to grow it from documents; if the latter, the field must be free text with suggestions layered on top (a text input plus the existing autocomplete helper), where a hit binds the record id and a miss leaves plain text for the existing auto-create path. Two further checks when converting a picker to free text: give each identity field its **own** input rather than one combined box, because the unique key is the pair (name, model) and a single box forces the operator to merge variants or retype; and grep the form-parsing helper for every field name you add — these helpers typically read a **fixed list of keys**, so a field the service already consumes can still be missing from that list, leaving the new input decorative and silently dropping typed values. Assert the persisted value in a test rather than trusting the markup. When a page's document type rejects a not-yet-registered record (e.g. inbound requires inventory enabled), warn on the page before save instead of letting the server reject after the user has filled the form.
3b. **Before designing a "remember what I typed" feature, trace where that value actually lands — a submitted field can be silently discarded on one branch.** A request to remember a user-entered value (a unit, a remark, a price) presupposes the value persists today; verify that by reading the write service, not the form. The same form commonly has two branches — one that binds an existing record's id, one that creates a new record — and they can treat the submitted value **oppositely**: the id-bound branch returns the master record's own value and drops what the user typed, while the create branch adopts it and updates the master. The visible action is identical either way, so the user meets it as "I typed X and the saved document says Y" with no error surfaced anywhere; that dropped value is a defect, and the sibling page is usually worse still — its control may not submit at all (a read-only display element carrying no `name` attribute, so `name="<field>" ` does not appear in the served HTML). Establish which case you are in by grepping the rendered page for `name="<field>"` and by reading each branch's return value, then report it as a table (branch → what the submitted value does → what the master record does) **before** proposing the feature. Aligning the branches is part of the same change, not a follow-up. **When you convert that read-only element into an editable control, every JS site that wrote to the old element must be rewritten or it throws on null.** A read-only display node is typically written from several places per page — the row binder, the picker's on-pick callback, `clearRow`, `clearAllRows`, the add-row clone reset, and any import/prefill handler — and each `tr.querySelector('.unit-display').textContent = …` becomes a `TypeError: Cannot read properties of null` the moment the node is replaced, killing the rest of that handler (reset, recalc, focus) with no visible error. Grep the page for the **old class/module name** (`grep -n 'unit-display' <template>`) and rewrite every hit in the same edit, then re-run the extracted-JS check; a residual hit in a CSS block is harmless, one in a handler is not.
3c. **A "remember what I typed" field needs a candidate pool sourced from every table that can hold the value, and a two-control sync contract.** Once a free-text-or-pick field (a unit) is editable, the dropdown behind it must offer both the fixed defaults and every value already in the database. Source the pool as `defaults ∪ DISTINCT value` over **every** table that stores it — the master record *and* each document-line snapshot table — because the branch that must not write the master (document-type lock) keeps new values only in its own line table; a pool built from the master alone will never show them. Keep the pool in one server-side helper passed into every entry page's context (the template falls back to the default literal only for direct renders), render defaults **first in declaration order** then the rest sorted, and dedupe. Then wire the two controls: dropdown `change` → write the text input; text input `input` → set the dropdown value **and append the option first** if absent, so a value typed now is selectable without saving. Grep the templates for the hardcoded default list and delete every copy in the same change, or one sibling page silently ignores the pool.
4. **Design the vertical slice in the real task order.** For inventory ERP work, show: existing entry point → master data/product identity → opening inventory → purchase/inbound entry → sale/return entry → analytics → reconciliation/print. Each screen must expose the next meaningful state, not only a final result.
4a. **Map cross-page conventions before styling individual screens.** Create a matrix for list, detail, edit, and PDF-preview pages covering header placement, return action label/position, primary/secondary/danger button treatment, minimum button widths, and no-wrap behavior; implement one shared rule, with no return action on true top-level module pages.
4b. **Resolve counterparty and document direction before merging reconciliation records.** Classify every document as customer-side or supplier-side and as inflow, sale, return, or adjustment; only combine records that belong to the same ledger, otherwise provide separate customer and supplier reconciliation views.
4c. **Assign cost fields by business authority before adding them to forms.** Purchase/inbound entry accepts source cost; stock, product, and analytics pages show calculated moving-average cost and stock value; sale/return forms show the historical cost snapshot read-only; customer-facing PDFs and statements exclude internal cost unless explicitly allowlisted. Use separate fields or columns instead of stacking status, quantity, cost, and value in one cell.
4d. **Define display precision before changing templates.** Preserve stored precision, format quantity according to unit semantics, format money to two decimals, and never truncate numeric cost or amount with an ellipsis; verify both integer-count and fractional-measure units.
4e. **Find where a page's classes are actually defined before restyling.** A class reused from a sibling template is often defined only in that sibling's page-scoped `<style>` block and renders unstyled everywhere else; extract the shared entry-page card/table/section-title rules into one common stylesheet or partial instead of copying the block or depending on load order, and re-check the original owner page after moving it. Layout variants (narrower sidebar, page-specific insets) are usually gated on a path-conditional class set by the shared layout — a path list that a newly added sibling page is typically missing, so extend that list and keep the rule in the shared layout rather than in one page's `<style>`; confirm parity by measuring the rendered geometry of every page in the family, not by eye.
4f. **Verify theme adaptation from source, not one screenshot.** Themes run on a root theme attribute plus `--token` variables; grep templates for hardcoded `#rrggbb`/`rgba(` colors and light-only utility classes (e.g. Bootstrap `.table-light`) and route them through theme tokens with dark values, covering native input icons, placeholders, disabled/focus states, and custom badges across light/dark/system. When the component library carries its own theme attribute (e.g. Bootstrap `data-bs-theme`), sync it to the app theme attribute from an inline `<head>` script placed before the library stylesheet, so uncovered library defaults follow dark mode without a flash; drive `system` from `prefers-color-scheme` with a change listener.
4g. **Bring a second document type onto an accepted entry skeleton without regressing the first.** When aligning a sibling page (e.g. purchase / supplier-return) to an accepted sales/return entry page, reuse the same column matrix, free-text counterparty combobox, order-number preview, status select, same-day history, and async save-success panel. Keep the synchronous path intact: leave the existing non-fetch redirect submission unchanged and add an explicit async branch keyed on a fetch header plus the primary button's action value, so the accepted page's existing tests and the no-JS behavior both survive. Return JSON for validation failures on that branch too — a server that re-renders the form HTML on error must not let the client print the whole page into the error banner; parse the response by content-type and fall back to a generic message.
4h. **Consolidate per-type document lists into one table before adding type facets.** When several document types render as separate sections and the user asks for one list, merge them into a single paginated `UNION ALL` projection with a literal type discriminator and one uniform row shape computed in the route, convert the type filter to multi-select while still accepting the legacy single value, and key bulk actions by `type:id` dispatching each type's own rule. The per-type tables rarely share column names — build each side's condition string with its own aliases rather than one shared WHERE, or the query fails on an unknown column. Adding an optional link from a document back to its origin document is a separate decision: confirm **linkage-only** (prefill rows/limits/reference price, everything still editable, pricing and inventory rules unchanged) versus **constraint** (the source bounds and prices the lines) before building, because the latter reverts a prior decoupling and its schema migration. Recipe and pitfalls: [`references/document-list-and-cross-document-links.md`](references/document-list-and-cross-document-links.md). The same consolidation applies to the recycle bin: restore and permanent-purge eligibility differs per type (some posted or historically-referenced records can never be physically deleted), so keep per-type rule dispatch inside one merged table instead of one shared bulk action.
4i. **Unify a source-link control by comparing DOM nesting, not styling.** When two sibling entry pages render the same block at visibly different depths (one appearing to float on its own card, one sharing the row with the other fields), the cause is almost always template nesting rather than CSS: read both templates and compare which card/`row` wrapper the block sits in, and move the control to the **first row of the document-info card on every page** instead of restyling. On selection, show a **preview panel** (source number, counterparty, date, total, lines with quantity/price and remaining limits) between the info card and the detail card, then let the user apply those rows — a preview the user can read beats silently prefilling the grid and keeps the apply step explicit. Feed the preview from each page's existing read-only source endpoint; do not add a parallel one.
5. **Separate internal and external views in the prototype.** Internal forms may show cost, margin, stock, and source notes. Customer print/reconciliation previews must use an allowlisted field set and show that internal fields are excluded.
6. **Version rejected prototypes instead of overwriting them.** Preserve the rejected file, create a clearly versioned replacement, update the asset record, and point the plan/evidence document at the replacement as the acceptance target.
7. **Build each vertical slice red-to-green.** Add the smallest behavior tests first, implement the service/data rule, connect the existing route/template path when the slice is user-visible, run targeted tests, then run the regression suite before starting the next slice. Do not stop at a schema or service stub. For inventory master-data slices, advance the schema version explicitly, test migration-safe field creation, and verify the complete chain of service, route, template, backup/migration, and purge/restore behavior before marking the phase passed.
8. **Test idempotency through the route, not only the service.** When a form allocates a document number or other generated identifier, look up an existing request key before allocating a new identifier; otherwise a retry changes the payload and becomes a false conflict instead of returning the original result.
9. **Audit lifecycle edges with every inventory reference.** When a product gains inventory state, initialization, or immutable postings, inspect and test soft-delete, restore, permanent purge, and automatic cleanup in the same slice; immutable history must block physical deletion because foreign keys and traceability outlive the visible master record.
10. **Verify in layers before product acceptance.** Run JavaScript syntax, duplicate-ID, required-control, `git diff --check`, and HTTP-served load checks first. **A server-rendered template's inline JS is invisible to a linter, so extract it from the rendered HTML and check it — a helper you called but never defined renders fine, passes every template test, and dies at runtime.** A template test asserting `class="unit-cell"` or `name="unit"` is present says nothing about whether the handler can run. Recipe: render each affected page through the test client, regex out every `<script>` block **without** a `src` attribute, join them, and run `node --check` on the concatenated file per page; then grep each page's own JS for every helper name it calls and confirm exactly one `function <name>` definition exists in *that* page's output. Hold the same bar for the reference count, not just existence: a page that calls `ensureUnitOption(...)` twice and defines it once is correct, one that defines it zero times is the bug. Do this before the browser pass — the browser would surface it only as 'the dropdown does nothing', which is far slower to localise. Then attempt real browser interactions for primary paths and responsive/theme checks. Lower-layer success never upgrades a higher layer. When scripting a native two-level picker, choose options by label or explicit value: selecting the first option index picks the placeholder and silently clears the bound id, which later surfaces as a misleading server-side validation error. Before handing the user a preview URL, confirm the instance holds data rich enough to exhibit the change and name that dataset in the handoff — a preview seeded with one document renders a correct new layout as empty or degenerate and reads to the user as a broken feature. **When the change makes a destructive operation reachable for the first time (permanent purge, empty-the-bin, bulk delete), copy the database before handing over the URL and tell the user the backup path and that you will restore it.** Until now those actions may have been impossible or reversible, so the user previews freely; once they actually delete, an un-backed-up preview costs real data. Also confirm the data root the instance serves and say which one it is, so "I previewed and it's fine" refers to the copy rather than the live database. Serve the richer dataset through an explicit data-root/config override (an env var such as `ERP_DATA_ROOT` plus a config path) pointed at a copied database, and leave the user's real data root and its location file untouched; then confirm the override took effect by reading the root back from the app's own health/status endpoint rather than assuming it. **A fresh scratch config path must be seeded before the app factory runs** — pointing the config env var at a directory that has no config file yet aborts startup with a file-not-found, so write the shipped defaults into that path (and record the scratch data root) *before* calling the app factory, not after. Opening an older packaged database can silently upgrade its schema on first write, so copy it into a scratch data root first and never point the override at the user's live database. Also confirm *which* database the instance actually reads before describing its contents: a repo-local database file can be stale or unused while the effective root lives elsewhere, so read the resolved root from the app instead of inferring it from a file you found in the tree. **When the user's screenshot must be explained, identify the instance behind it from the app, not from the filesystem.** List the listening ports, hit each candidate's health/status endpoint (these typically return the resolved data root, database status, and version), and compare that instance's rows against what the screenshot shows. Walking the disk for database files is the slow path and often finds nothing that matches: a scratch preview instance seeded with synthetic data (a demo customer, a handful of documents) produces a screenshot that corresponds to no database in the repo tree, and its data root usually sits under the scratch/cache directory rather than in the project. Name the data root you concluded from in the answer, so "why does this row show X" is answered about the database the user was actually looking at. Confirm the serving process **postdates your last code change**: a long-running dev instance with template caching on keeps serving the pre-change HTML, and a user who closed the browser window has not stopped the service. Note the split that makes this trap hard to see: **static JS is re-read from disk per request while templates — and the inline CSS inside them — are cached**, so a JS-only edit takes effect immediately and a CSS/template edit does not. Restart the instance before re-verifying markup or styling, and never infer from "the JS change is live" that the whole edit is: an unchanged popup width or column width after you edited CSS is this trap, not a specificity bug. Check the port's listener and whether the page it returns actually contains the new markup rather than trusting that the port is free or a report that it was closed; when the running instance is stale, start a fresh one on a different port against the copied data root instead of reusing it. **When you hand a URL to the user for their own verification, the same staleness bites the other way: name the exact URL and warn that any other instance they open — an older port, their usual shortcut/launcher, the packaged EXE — serves pre-change markup.** A user who clicks their normal entry point instead of your URL verifies the old build and reports a correct change as "not applied"; when that happens, resolve it by comparing the served bytes on the URL you gave against what they are looking at, and ask for their address bar, rather than re-editing correct code or telling them they misread.
11. **Report the gate honestly.** Mark each layer `passed`, `failed`, `blocked`, or `unverified`. Keep the phase gate open when real interaction or visual review did not happen. An explicit instruction to continue may authorize the next plan-approved isolated implementation slice, but it does not convert an unverified prototype or manual review into acceptance. Before attributing a test failure to the product, reproduce it with the project's documented default invocation: a failure that appears only under an extra flag is an invocation artifact, because flags can disable plugins a test depends on (e.g. a no-logging flag removes the built-in log-capture fixture, so a green suite reports a setup error). **A bare "N passed, N skipped" from a backgrounded suite is not an evidence count — check the skip reason before recording it.** Some test modules gate on a binary resolved through `shutil.which`, and a background/detached run can start with a PATH missing that tool (a bundled `pdftotext`, `node`, a packager), so the file skips wholesale while the same command in the foreground runs every test. Treat any nonzero skip count as suspect: re-run in the foreground (or the project's documented default invocation here) and confirm `0 skipped` before quoting the number. Re-run that single test under the default command and quote the exact invocation beside any count you report — a bare "N passed, 1 error" that came from a non-default flag misrepresents the product.

## Always-On Rules

- Existing accepted UI/UX is a compatibility contract; do not replace it with a fresh conceptual dashboard.
- Read real templates and accepted prototypes before writing a new prototype; screenshots or memory are insufficient.
- Prefer extending real controls and states over explanatory prose, static metric cards, or buttons that only emit prototype toasts.
- Preserve old and new business meanings separately; label new net-sales analytics instead of silently changing old purchase-statistics semantics. When you repurpose an existing visualization or aggregate onto a different metric, rename its label, keep the previous metric still computed so the change stays auditable, and confirm the sign convention and which document types are in scope before implementing — a bare word like "flow" is ambiguous between gross turnover and direction-netted movement.
- Treat keyboard flows, filter modes, pagination, selection, same-day history, theme, and viewport behavior as first-class UX.
- Do not claim acceptance because a prototype loads or parses; acceptance needs real interaction evidence or an explicit user decision. A continuation instruction can authorize implementation behind an unverified prototype gate only when the plan explicitly permits that separation; keep the gate labeled `unverified`.
- Treat inventory history as an ownership boundary: soft-delete hides a product, while purge/cleanup must refuse products referenced by inventory state, initialization, or postings.
- Add a filter facet only when the backing data actually reaches the view: confirm the query/ledger already returns those document types before adding the option, or the options are permanently empty and the real change is a scope/口径 change, not a UI filter.
- When the user rejects a direction for missing baseline UX, acknowledge the root cause and rebuild from the baseline rather than defending the abstraction.
