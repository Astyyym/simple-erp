# 2026-10-05 四类开单解耦、商品两级选择器、账款类型筛选与深色适配 — 执行计划

## 目标

1. 让**销售单、退货单、拿货单、退拿货单四类开单互相独立**：退货单不再依赖销售单，退拿货单不再依赖拿货单。
2. 四类开单的商品选择统一为**"产品名称 → 型号"两级联动下拉**，替代现有的模糊搜索输入框 / 合并 option。
3. 四类开单页**视觉与交互风格统一**（补回采购页缺失的公共开单卡片样式）。
4. 账款管理在客户流水标题旁新增**"单据类型"筛选**（销售 / 退货 / 拿货 / 退拿货），并把**拿货、退拿货并入客户视图**（含余额口径）。
5. 移除数据分析页的**"进入往来对账"入口**（对账路由暂保留）。
6. 修复**深色模式下字体与输入框对比不足**的适配问题。

## 已确认决策（本轮用户拍板）

- 四类单据彻底解耦，**一次性全做完**，不先只做样式。
- 退货 / 退拿货改为**手工自由开单**：单价**手输**，可选**一键带入客户价 / 常规价**（同销售单逻辑）。
- 退货回冲库存 / 退拿货出库，成本按**当前移动平均成本**。
- 拿货 / 退拿货**并入客户视图**，影响余额统计（净额）。
- 数据分析"进入往来对账"入口**直接删除**（做完账款筛选后）。

## 现状事实（改前基线，来自源码）

- 退货单**依赖原销售单**：`accounting.py:_prepare_return_items` 要求 `source_order_id` + `source_item_id`，单价/成本按原销售行比例，校验"累计已退不超原售"、日期不早于原销售日期；`orders/new.html` 用 `returnSourceSelect` 载入只读明细。
- 退拿货单**依赖原拿货单**：`purchase_returns.py:_source/_allocations` 由 `source_order_id` 驱动；DB `purchase_return_orders.source_order_id NOT NULL`、`purchase_return_items.source_item_id NOT NULL` 且 `UNIQUE(purchase_return_id, source_item_id)`。
- 账款客户流水口径：`orders(sale/return) + payments + adjustments`；**拿货 / 退拿货当前不进客户流水**，也**不计入余额**（`accounts.py` 的 balance SQL、`accounting.py:get_customer_account_ledger`）。
- 深色：`base.html` 有 `--erp-*` 深色变量，但存在硬编码色（`.btn-outline-secondary{color:#475467}`、`.type-sale{#1d4ed8}`、`#9a6700` 等）与 `orders/new.html` 的 `thead class="table-light"`。

- **Stage 4｜退拿货单解耦**：同上，出库成本守恒；旧单兼容。

每阶段：`.venv\Scripts\python.exe -m pytest tests\ -q`（隔离临时库）+ 对应真实页面/桌面验收；分批实测后继续。

## 停止条件

- 任一阶段账务数字对不上、或既有销售/账款流程被改崩 → 停在该阶段先修。
- 迁移会破坏正式库或旧单可读性 → 停。
- 自动测试与真实页面结论冲突 → 以真实页面为准，暂停报告。

## 风险

1. 退货/退拿货解耦改变成本与库存口径，牵动对账、分析、回收站与大量测试。
2. 余额并入应付（拿货方向）后，"正数=客户尚欠"语义变化，卡片文案需同步。
3. DB 迁移涉及 NOT NULL/UNIQUE 变更，需保证旧库可启动、旧单可读。
4. 换掉销售页模糊搜索可能影响快速开单手感。
