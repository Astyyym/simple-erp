### 二之二、设计倾向（本计划定案，用户可改）

4. **补录范围首版只限销售单**（`order_type='sale'`）。退货单成本按契约应来自原销售分摊，人工填会破坏守恒语义；手工退货缺成本属边缘情况，登记为后续评估。
5. **逐行补录**：只允许对「无成本行」或「已人工补录行」填写；销售时真实快照行（有值且非补录）不可覆盖。
6. **填错可修正**：`cost_source='backfill'` 的行允许再次补录覆盖（每次留痕），不必作废重录。
7. **原因必填**：每次补录/修正必须填写原因，写审计。
8. **补录后该单禁止重编辑**：重编辑会重建明细行、无声清掉补录数据；改为禁用编辑并说明「如需更正请作废后重开」。
9. **新增 `order_items.cost_source` 标记**：`NULL`=销售时真实快照、`'backfill'`=人工补录；幂等加列，**不升** `CURRENT_SCHEMA_VERSION`（对齐 `origin`/`brand`/期初 `cost_source` 的既有惯例）。
10. **输入方式**：每行「单位成本（元）」为主，可选「总成本（元）」反推（与期初 C-2 一致）；金额校验：非负、有限、≤6 位小数，转 micro 整数。
11. **发现路径**：单据管理列表给缺成本销售单加「缺成本」徽标 + `cost=missing` 快速筛选。
12. **补录页必须在提交前披露「补录后禁编辑」**（复核必改 #2）：补录前该单恰恰**是**可编辑的（无库存流水），提交后才失去编辑能力；因此披露要写在补录页说明里，不能只写在「编辑」按钮置灰的原因里。
13. **已有有效退货时拒绝再修正**（复核必改 #3）：`cost_source='backfill'` 行可再修正，但若该单已产生有效退货，则拒绝再修正并给中文原因——原行成本改了、退货累计成本不会重算，**已全部退完的单会留下永久差额**（静默不一致）。保守取值：直接拒绝。**用户 2026-10-11 确认维持「拒绝」方案**（不放宽为「允许 + 警告」）。

## 三、问题与目标

**问题（白话）**：先卖后补的用户，早先卖出的单永远没有成本——毛利算不出、成本诊断一片「未覆盖」、客户退货时这些单连选都选不出来。唯一现成办法是「作废重录」，单号会变、打印要重打。

**目标**：给这类老销售单一个人工补录成本的入口。补上后：
- 分析页毛利 / 成本诊断立即变完整（该单进入已知成本范围）；
- 该单可被退货页选为来源（前提：商品已启用库存）；
- 全程留痕，界面明确标记「人工补录」，不冒充真实快照；
- 库存数量、库存金额、库存流水**完全不变**。

**非目标**：不改分析聚合口径；不写库存流水；不做退货单/拿货单补录；不做批量补录；不改打印。

### 4.2 服务层（新 `app/erp/services/cost_backfill.py`）

```python
def backfill_order_costs(order_id: int, entries: list[dict], reason: str) -> dict
```

- 入口校验：单据存在、`deleted_at IS NULL`、`order_type='sale'`、`status IN ('saved','printed')`、原因非空；
- 行校验（`BEGIN IMMEDIATE` 内重验）：`entry.item_id` 属于该单；行当前 `cost_total_micro IS NULL OR cost_source='backfill'`，否则拒绝「该行已有销售时成本，不能补录」；
- **退货保护（复核必改 #3）**：目标行 `cost_source='backfill'` 且该单已存在有效退货（非删除退货单、退货行引用该 `source_item_id`）→ 拒绝「该单已产生退货，不能再修正补录成本；如需更正请作废后重开」；
- 金额：单位成本 或 总成本（二选一）→ 统一转 `unit_cost_micro` / `cost_total_micro`（micro 整数、≤6 位小数、非负有限）；数量取行 `quantity`；
- 写入：`UPDATE order_items SET unit_cost_micro=?, cost_total_micro=?, cost_source='backfill' WHERE id=?`；
- 留痕：`log_action("backfill_order_cost", "order", order_id, "人工补录历史成本：<行摘要>；原因：<reason>", conn=conn)`——**必须传 `conn=conn`**，与 UPDATE 同一事务，避免「补录成功、审计丢失」（复核次要项 #6）；
- **绝不触碰** `inventory_postings` / `product_inventory_state` / `inventory_initializations`；
- 返回 `{"updated": n}`。

### 4.4 连锁效果（要写进补录页说明）

- 补录后该单出现在**退货来源下拉**（`_return_source_orders` 的 EXISTS 条件自动满足）；
- 关联退货时：商品**已启用库存** → 退货按补录成本入库（逻辑自洽：期初填的是启用时实际库存，退货是启用后真实回库）；商品**未启用** → 仍按既有规则拒绝（「商品尚未启用库存」）；
- 分析页：该单离开「未覆盖」范围，毛利参与计算。

## 六、验收标准（硬指标）

1. **库存零触碰**：补录前后 `product_inventory_state` 全表逐行一致、`inventory_postings` 行数不变（测试断言）。
2. **利润生效**：补录后 `summarize_analytics` / `summarize_profit` 对该单 `cost_complete=True`，毛利润 = 金额 − 补录成本。
3. **快照保护**：真实快照行不可被补录覆盖；补录行可再修正且每次留痕；**已有有效退货的单拒绝再修正**。
4. **状态保护**：草稿 / 作废 / 已删 / 退货单 / 拿货单不可补录（各自中文错误）。
5. **编辑保护**：已补录单的「编辑」置灰且原因准确；POST 编辑路由同样拒绝（不可绕过）。
6. **留痕**：`audit_logs` 每次补录一条，含行明细与原因，且与补录写入同事务。
7. **发现路径**：列表徽标与 `cost=missing` 筛选行为正确（非销售分支 `1=0`）。
8. 回归：全量 pytest 不低于 **855 passed / 0 skipped**；前端 **57 Node** 全绿；`git diff --check` 通过。

## 七、停止条件

1. 补录需要写库存流水或改 `product_inventory_state` → 停，回用户确认（违反已定取舍）。
2. 需要改分析/利润聚合口径才能生效 → 停（应零改动生效，否则设计有问题）。
3. 迁移在旧库上不可幂等或破坏 `order_items` → 停。
4. 全量测试基线下滑且无法定位 → 停在本阶段。
5. 出现与「快照不可变」冲突的真实使用场景（如用户要求改真实快照）→ 停，回用户。

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 补录值填错被当成真实成本 | `cost_source='backfill'` 标记 + 详情页/补录页明示「人工补录」 |
| 编辑路径无声清除补录 | 补录后禁编辑（编辑路由与服务双重拦截）+ 补录页提交前披露 |
| 已退货单再修正留下永久差额 | 已有有效退货时拒绝再修正（§4.2） |
| 退货连锁被误解 | 补录页说明「补录后可参与关联退货；商品未启用库存时退货仍会被拒」 |
| 列表 EXISTS 子查询影响性能 | 分页 50 条、本地 SQLite；与既有 `has_postings` 同款模式 |
| 用户想批量补 | 首版不做批量；登记后续评估 |
| 「清空所有数据」把补录痕迹一并清掉 | 属预期：该操作本就清空全部业务数据，补录数据随单据消失；`reset.py` 已保留 `backups/` 与 `legacy_archive/`，如需追溯走清空前自动备份。补录页/说明不承诺「清空后仍在」 |
