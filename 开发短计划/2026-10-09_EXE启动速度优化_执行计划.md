## 一、目标

把双击 `简单ERP.exe` 到**窗口可见**的时间从 **3.05–3.99s** 降到 **≤ 2.0s**，且不改变任何已有业务行为、不降低任何已有测试覆盖。

- **Batch A（惰性导入）**：让服务本身更快就绪（实测端口就绪 1.97–2.54s → 0.85–1.14s）。

- 不引入登录门、不改免登录决策。
- 不动 `dist/` 里的历史包、不动正式业务库。
- 不做档位 4（PyInstaller 原生 `--splash`）与档位 5（减体积）——见「明确排除」与「待确认」。

### 写法契约（必须照抄，不得简化）

**两张面孔：`pdf.py` 用 `None` 声明，`purchase_pdf.py` 必须用模块 `__getattr__`。** 这是 2026-10-09 实测的重要修正（原计划全用 `None` 声明是**错的**）。

**A. `pdf.py` 型（测试只 `setattr`，不读属性）——`None` 声明即可**：

```python
# 模块级声明保留注入点
HTML = None

def _html_class():
    global HTML
    if HTML is None:
        from weasyprint import HTML as _HTML
        HTML = _HTML
    return HTML
```

**为什么**：测试用 `monkeypatch.setattr(pdf, "HTML", CapturingHtml)` 捕获 HTML 并伪造 `%PDF`。若写成函数内 `from weasyprint import HTML`，模块上就没有 `HTML` 属性，`monkeypatch.setattr` 直接 `AttributeError`——实测 lazyapp2/3 各挂 9–10 个测试。

**B. `purchase_pdf.py` 型（测试会**读**模块属性当真实类用）——必须用 `__getattr__`**：

```python
def __getattr__(name):
    if name in ("CSS", "HTML"):
        from weasyprint import CSS as _CSS, HTML as _HTML
        return {"CSS": _CSS, "HTML": _HTML}[name]
    raise AttributeError(f"module {__name__!r} has no attribute {name!r}")


def _weasy():
    global CSS, HTML
    globals_css = globals().get("CSS")
    globals_html = globals().get("HTML")
    if globals_css is None:
        from weasyprint import CSS as _CSS
        CSS = globals_css = _CSS
    if globals_html is None:
        from weasyprint import HTML as _HTML
        HTML = globals_html = _HTML
    return globals_css, globals_html
```

**为什么**：`tests/test_purchase_printing.py:295` / `:334` 会 **读取** `purchase_pdf.HTML` 当真实类用（`original_html = purchase_pdf.HTML`），再包装成 spy/LayoutAndRealPdf。用 `HTML = None` 声明时，这次读取拿到 `None` → 调用时 `TypeError: 'NoneType' object is not callable`。

> ⚠️ **这个坑极隐蔽**：`None` 声明在**整个文件一起跑**时可能"看起来通过"——因为同文件靠前的测试先渲染过一次、把属性解析出来了，纯属**测试顺序运气**；**单独跑那 3 个测试就挂**（实测 `3 failed`）。所以验收必须包含"单独跑"这一层，不能只看全量绿。
>
> 上一轮报告里写的"lazyapp4 全绿"是个**假阳性**，本计划据此已修正为 `__getattr__`。`lazyapp5`（`__getattr__` 变体）单独跑 `3 passed`、全量 `789 passed`、启动四库全不加载——这才是经完整验证的写法。`purchase_pdf.py` 之外的其余 5 个文件测试只 `setattr`/只走路由，`None` 声明实测无问题。

## 五、Batch C — Splash 先行（品牌样式版，2026-10-09 用户确认）

> **定案依据**：2026-10-09 用户答复 Q1「做」、Q2「要品牌样式（图标 + 配色跟随浅色/深色主题）」。本条从「待确认」转为「已确认，纳入本次范围」，外观按**品牌样式版**实现。
> 依据报告档位 2；实测数据见 [`docs/复盘/2026-10-09_EXE启动速度调研.md`](../docs/复盘/2026-10-09_EXE启动速度调研.md) §五。

### 要解决什么

现状 `desktop_app.main()` 是**串行**的：

```
起服务线程 → 阻塞等端口就绪 → import webview → create_window → webview.start() → 再等 WebView2 起来
```

用户在**双击后的 2–4 秒里看不到任何窗口**，观感等同「软件卡住/没打开」。

改成**并行**：

```
起服务线程 ──┐
             ├─→ 立刻用内联 HTML splash 建窗口 + webview.start()（WebView2 冷启动开始）
             │
             └─→ 另起线程等端口就绪 → window.load_url(APP_URL) 切到主界面
```

### ⚠️ 前置阻塞：必须先解决 `desktop_app.py` 的模块级重依赖导入

**2026-10-09 取证发现（本批的关键前提，不解决则 splash 先行形同虚设）**：

`desktop_app.py` 第 26–27 行在**模块级**导入：

```python
from erp import create_app
from erp.config import load_config
```

由于 `erp/__init__.py` 会拉起整条重依赖链（实测源码模式 1.84s），**这段模块级导入发生在 `main()` 之前**。后果：

| 场景 | 双击后 splash 何时出现 |
|---|---|
| 不处理模块级导入 | **等 ~2–3s 重依赖导入跑完才出现**——splash 完全失去意义 |
| 处理之后（本批要求） | 立即出现（实测 1.41–2.38s 内窗口可见，其中 splash 本身在 ~1.5s 内） |

**所以本批必须同时做**：

1. 把 `from erp import create_app` 移入 `_run_server()` 函数内（服务线程里）。
2. `load_config` 已只被 `_window_title()` 使用，同样改为函数内导入。
3. **`waitress` 的 `from waitress import serve` 保留在模块级**——实测仅 0.11–0.29s，且服务线程需要它，收益不值得冒险。
4. `erp` 的惰性化本身由 **Batch A** 负责（同批成果，两批互补）。

> **顺序依赖**：Batch C 的"立即出现"依赖 Batch A 已完成。若只做 C 不做 A，splash 仍会等 `erp` 导入完才出现——**A 与 C 必须同批交付，不可拆开验收**。

| 文件 | 改动 |
|---|---|
| `desktop_app.py` | ① 模块级 `from erp import ...` → 移入 `_run_server()` / `_window_title()`；② `main()` 改为 splash 先行；③ 新增品牌样式内联 splash HTML；④ 新增等待线程调用 `load_url(APP_URL)` |

```html
</svg>
```

容器样式对齐 `.brand-mark`（`base.html:145`）：34×34（splash 可放大到 48–56px）、`border-radius:7px`、背景 `var(--erp-primary)`、图标白色、`box-shadow:inset 0 0 0 1px rgba(255,255,255,.18)`。

**② 配色跟随主题**：**splash 进程内不读 config**（读 config 会引入文件 IO 与 `erp.config` 依赖，破坏"立即出现"）。做法是**用 CSS 原生能力自动跟随**：

```css
:root{
  --splash-primary:#2563eb; --splash-bg:#f3f5f8; --splash-surface:#fff;
  --splash-ink:#172033; --splash-muted:#667085;
}
@media (prefers-color-scheme: dark){
  :root{
    --splash-primary:#3b82f6; --splash-bg:#0f141d; --splash-surface:#171e2b;
    --splash-ink:#e8eef9; --splash-muted:#9aa8c0;
  }
}
```

色值**直接取自 `base.html` 现有 token**（浅色 `:root` L29–31；深色 `data-ui-theme="dark"` L54–56），保证观感与主界面一致：

| token | 浅色 | 深色 |
|---|---|---|
| primary | `#2563eb` | `#3b82f6` |
| bg | `#f3f5f8` | `#0f141d` |
| surface | `#fff` | `#171e2b` |
| ink | `#172033` | `#e8eef9` |
| muted | `#667085` | `#9aa8c0` |

**③ 已知边界（必须如实报告）**：`ui_theme` 支持 `light` / `dark` / `system` 三档，其中 **`system` 用 `prefers-color-scheme` 跟随操作系统，与上表 `@media` 语义一致 ✓**。但**若用户把 `ui_theme` 显式设为 `dark` 而操作系统是浅色**，splash 会显示浅色、主界面是深色——**这是本方案的一个已知不一致**。原因：splash 阶段不读 config（见上）。若要求严格一致，需在 splash 前读一次 `config.json`（纯 `json.load`，不 import `erp.config`，实测可控制在毫秒级）——**列为 Q6 待确认**。

**④ 内容**：品牌图标 + 店铺名（或「简单ERP」）+ 「正在启动本地服务…」+ 轻量动画进度条。店铺名同理不读 config，用 `简单ERP`；主界面加载后 `base.html` 会同步真实店铺名（实测已确认标题切换正常）。

### 实现要点

1. **内联 splash HTML**，不引新依赖、不落外部文件（避免打包时多一个 data 条目）。
2. **端口已开的分支要保住**：现有 `if not _port_is_open(): 起服务` 逻辑必须保留——用户重复双击时不能起第二个服务。
3. **等待线程不得吞异常**：沿用现有 `startup_errors: queue.Queue` 机制，把服务启动失败的原始异常带出来（项目技能已记录「通用端口等待超时掩盖初始化失败」这个坑）。
4. **`load_url` 只调一次**：切到主界面后不得再回退到 splash。
5. **窗口标题**：splash 阶段与主界面阶段都应显示店铺名（现有 `_window_title()` 读 `config.shop_name`；页面加载后 `base.html` 会再同步一次，实测已确认正常）。

### ⚠️ 实现时发现的硬冲突与解法（2026-10-09 取证）

上一轮的 splash 实验稿（`splash_desktop_app.py` / `lazy_desktop_app.py`）是**「先开窗口 → webview.start() → 再等服务」**。这在真实测试下**挂死**：

```
test_main_reports_real_database_failure_before_opening_webview → exit 124（超时挂死）
```

原因：该测试要求 `main()` 在**真实数据库失败时先抛错、且还没开窗口**（`tests/test_desktop_startup.py:29`），而「先开窗口 + `webview.start()` 阻塞」永远走不到抛错那一步。**这正是本计划 §九 列为「高风险」的那一条。**

**采用的解法（与实验稿不同，已验证）**：

```
main()：
  1. 若端口未开 → 先同步 _create_app()（此时才会 import erp）
       └─ 失败立即 raise RuntimeError（不开窗口，保住契约）
  2. 起服务线程 → 立刻 create_window(html=SPLASH_HTML) → webview.start()
  3. 另起线程等端口就绪 → window.load_url(APP_URL)
       └─ 等待/切换失败 → load_html(错误页)，绝不永久停在 splash
```

**权衡说明**：与纯「先窗口」方案相比，此处把 `import erp + create_app`（Batch A 后仅 ~0.45–0.55s）留在窗口之前，换取「数据库失败必须先抛错」的既有契约。WebView2 冷启动（~1.5s）仍与**服务 bind + 首页加载**并行，实测仍达标（见 Batch B）。**这是与实验稿的有意差异，不是疏漏。**

### 🐞 用户实机反馈后的修复：splash 从没显示过（2026-10-09 晚）

**用户反馈**：双击新包「感觉和优化前没区别」，**没看到**计划里承诺的「点击后立马出现加载页/进度条」。

**复现取证**：用 `capture_window.py` 在冻结包启动过程抓 ERP 窗口矩形，帧序显示：

| 时刻 | 屏幕内容 |
|---|---|
| ~2.1s | `简单ERP` 窗口已出现，**客户区空白白屏**（WebView2 冷启动中） |
| ~2.6s | **splash 才画出来**（蓝图标 + 简单ERP + 进度条 + 「正在启动本地服务…」） |

**根因（实现 bug，非用户误判）**：Batch A 让服务 **~0.95s** 就绪，比窗口出现（~2.0s）还快。原实现里 `_swap_to_app()` 线程只等「端口就绪」就调 `load_url(APP_URL)`，于是 **~1.0s 就抢跑切主界面**——splash 那一步**根本没来得及绘制**，用户看到的从头到尾只是空白窗。

**修复**（`desktop_app.py`）：
1. `_window.events.loaded += _on_loaded`：记录 **splash 首次绘制** 的时刻到 `threading.Event`。
2. `_swap_to_app()` 改为**先 `splash_painted.wait(timeout=8.0)`**（等 splash 真画出来）**再** `load_url`；8s 兜底防个别 WebView2 不吃该事件而永久停住。
3. 新增 `SPLASH_MIN_SECONDS = 0.9`：splash 绘制后**至少停留 0.9s** 才切走，否则只是不足 0.1s 的一闪，用户仍读成「没反应」。
4. 新增 `background_color=SPLASH_BACKGROUND`（`#f3f5f8`）：窗口出现到 splash 绘制之间不再是一块刺眼纯白。

**修复后计时**：源码时间线 `splash PAINTED 2.88s → swap 3.78s → app 4.13s`（splash 可见 ~0.9s）；冻结包窗口可见 **~1.31s**（n=5）；必守测试 **15 passed**、全量 **789 passed**。

**这次修的教训**：**「窗口出现」与「splash 可见」是两回事**。只做「窗口先行」不够——必须在**内容真正绘制后**才切页，并给一个可感知的最小停留；否则快速就绪的服务会在首帧之前就把 splash 抢掉。已写入项目技能 `references/desktop-splash-first.md`。

### 已知边界（必须如实报告，不得当成达标）

- splash 只是把等待**可视化**，不缩短实际等待总时长（总时长由 Batch A 决定）。
