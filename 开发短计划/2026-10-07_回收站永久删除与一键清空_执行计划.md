## 关键设计

### 删除顺序（外键约束决定）

`order_items.source_item_id` 是**自引用**：退货单的明细可能指向销售单的明细。所以：

- **必须先删引用方**（退货 → 销售；退拿货 → 拿货），否则删被引用方会撞 `FOREIGN KEY constraint failed`。
- 实现为 `_purge_orders_in_safe_order`：**多趟扫描**，每趟只删「当前已无活引用」的记录，剩下的等引用方被删掉后下一趟通过。调用方不需要自己排序。
- 单条删除时若被仍在回收站的记录引用，抛 `PurgeBlockedByRecycledReference` → 转成可读的 400（**不是 500**），提示「还有回收站记录引用它的明细」。

### 删除内容（用户口径：不要了就清干净）

`purge_order_item` 依次删：明细 → 该单据自己的库存流水（含 `:void` 反向流水）→ 单据本体。
`purge_product_item` 依次删：解除明细引用 → 客户价 → 库存流水 → 库存状态 → 期初 → 商品。

### 保留的底线

- **有未删除单据引用时拒绝**（销售被活退货引用、商品被活单据使用）→ 保留并显示原因。
- **有历史账务的客户始终不物理删除**（账务追溯底线）。

## 修复过程中自己踩的坑（已修）

1. **单条删除抛 500**：`purge_order_item` 直接抛 `sqlite3.IntegrityError`，被仍在回收站的引用方挡住时页面 500。改为转成 `PurgeBlockedByRecycledReference` → 可读 400。
2. **批量 purge 被改坏**：我把 `bulk_purge` 里所有 kind 都送进单据专用的 `_purge_orders_in_safe_order`，商品/客户因此失效（测试抓到）。改为按类型分流。

## 风险与边界

- **永久删除不可逆**：会清掉明细与库存流水。确认框已写明「无法恢复」。
- **商品删除要求先删引用它的单据**：这是为了不让活单据失去商品指向（`void_order` 依赖库存流水做反向过账）。有活引用时会明确告知。
- **永久删除不会让已冲回的账款/库存复活**：只清历史痕迹，余额与库存状态不变（有测试锁定）。

## 取证过程里踩到的坑（记下来免得再犯）

**Flask 模板缓存让「改完没变化」**：改完 `recycle/index.html` 后重跑测量，数值与改前**一模一样**（仍是 128.3 / clip 14.7）。先怀疑 CSS 写法，实际是 Flask 进程的模板缓存——直接 `curl` 该页对比才发现服务端仍吐 24 个 `action-wrap`，而磁盘已是 4 个 `action-cell`。

**教训**：UI 改动后要改的是「**服务端实际吐出的 HTML**」，不是磁盘文件。验证顺序应为：① `curl` 该路由 grep 关键类名，确认服务端已更新；② 再跑浏览器测量。否则会拿旧页面的数据去否定一个正确的改动（本轮差点把 CSS 改成「更宽」来掩盖其实没生效的问题）。另：起服务时带 `TEMPLATES_AUTO_RELOAD=True` **不生效**（需在 app 上同时设 `app.config['TEMPLATES_AUTO_RELOAD']` 与 `app.jinja_env.auto_reload`），最稳的是改完重启进程。
