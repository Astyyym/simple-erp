# 2026-10-10 config.json 出厂默认对齐（取消跟踪 + 源码回退）— 执行计划

> 状态：`已完成（源码 + 自动测试）`。
> 用户指令（2026-10-10）：「你可以单开一轮，把它对齐」，并在选项中确认 **方案 A**：把 `config.json` 从 git 取消跟踪并加进 `.gitignore`，同时让源码运行在文件缺失时回退到 `packaging/default_config.json`。
> 相关：上一轮 [v3.6.0 安装包交付](./2026-10-10_v3.6.0安装包交付_执行计划.md)。

## 问题

根 `config.json` 被 git 跟踪，而它同时是**每台机器的可写配置**（店铺名、打印偏移、主题、界面缩放）。后果：

1. 开发机一在设置页改设置，工作区就出现「待提交」的配置改动，容易误提交进仓库。
2. 索引里的版本与 `packaging/default_config.json`（构建打包实际用的那份）**持续漂移**——本轮开始时已差 4 处：`ui_scale 125` vs `100`、`print_main_business` 末尾句号、`print_offset_*` 的 `0.0` vs `0`、多出的 `print_info_prompt_dismissed`。
3. 旧规矩靠「发版时保证索引里是厂默认、工作区那份保持未暂存」这种**人为纪律**兜着，迟早会破。

## 取证

| 项 | 事实 |
|---|---|
| 构建是否读根 `config.json` | **否**。`简单ERP.spec` 只打 `packaging/default_config.json` 并把 TOC 条目重命名为 `config.json`；`tests/test_windows_packaging.py` 已锁定该契约 |
| 运行时是否读它 | **是**。`config_file_path()` = `ERP_CONFIG_PATH` 或 `runtime_root()/config.json`；源码运行 = 项目根 |
| 是否含敏感信息 | 否。`shop_name` 仍是「简单ERP」，电话/地址/经手人为空串 |
| 其它引用 | `tests/conftest.py` 用 `ERP_CONFIG_PATH` 指向临时目录；测试断言的是「备份 zip 内含 config.json」这类，与是否跟踪无关 |

## 改动

**代码（唯一一处运行时改动）**
- `app/erp/config.py`：新增 `factory_config_path()` 返回 `packaging/default_config.json`；`load_config()` 在可写配置不存在时回退——**冻结版先查 `bundled_root()/config.json`（_MEIPASS），源码模式不查 `bundled_root()`**（它等于项目根，会把工作区那份当成"内置配置"），直接回退到出厂模板。

**仓库配置**
- `.gitignore`：新增 `config.json`（附注释说明出厂默认真源是 `packaging/default_config.json`）。
- `git rm --cached config.json`：取消跟踪，**本地文件与其中的 `ui_scale=125` 原样保留**。

**测试**
- 新增 `tests/test_config_fallback.py`（7 条）：源码首次运行回退到厂模板、回退源就是构建那份（不是第二份副本）、已有配置优先于模板、冻结版仍优先包内配置、保存后落到可写路径（回退只发生在首次）、`.gitignore` 排除根配置且模板仍被跟踪、模板无私有/绝对路径。

**文档**
- `skills/.../references/versioning-github-backup.md`：把「根 config.json 是跟踪文件、发版时保证索引是厂默认」这条**过时且危险**的规矩改成「不进 git，出厂默认真源是 `packaging/default_config.json`」，并注明不要再回到旧做法。
