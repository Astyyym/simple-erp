# Phase 0 设计证据：库存、拿货单与数据分析中心

> 状态：Phase 0 设计证据已完成；已进入 Phase 1 隔离实现，正式业务库尚未迁移或启用库存写入。
> 日期：2026-10-01
> 关联计划：[库存、拿货单与数据分析中心执行计划](./2026-09-30_库存拿货与数据分析中心_执行计划.md)
> 业务规则：[库存、成本与客户对账业务契约](../docs/需求/库存成本与对账业务契约.md)

## 1. 证据范围与结论

本轮依据当前 Windows 唯一源码目录、当前工作区源码和测试静态盘点，不把历史文档或候选设计当成已实现事实。盘点结论如下：

- 当前数据库只有 `schema_version` 的初始记录和启动时的 `CREATE TABLE IF NOT EXISTS`/补列逻辑，没有可回滚的版本迁移链、数据库版本拒绝或一致性备份门。
- `products` 以 `name/spec` 保存资料和订单快照，但没有“规范化名称 + 型号”覆盖软删除商品的唯一约束，也没有安全库存、图片相对路径、期初启用、当前库存和当前成本字段。
- `order_items.id` 虽然存在，但重编辑路径会删除该订单全部明细后重新插入，因此不能作为正式业务行的稳定来源 ID。
- `orders` 只支持客户销售/退货两类单据，`customer_id` 为必填；不能承载无客户的独立拿货单。销售/退货金额和账款已有实现，但没有库存流水、销售成本快照或原销售行退货关联。
- 当前 typed-row 保存路径会按商品名称/型号自动创建或更新商品并学习客户价；这与新契约“新库存单据必须选择稳定商品 ID、拿货和退货不改变客户价”冲突，必须在统一切换门封闭旧写路径后改为明确的 ID 校验。
- 回收站支持销售/退货、商品、客户的软删除/恢复/永久删除；七天清理会删除符合条件的订单明细、订单、商品客户价及无引用客户。目前没有库存历史引用保护，不能直接复用到新库存单据。
- 客户销售单打印模板目前接收订单备注并输出。引入内部字段后，必须新增独立对外白名单上下文，不能用 CSS 隐藏成本、毛利、库存或货源。
- 旧客户采购统计在 `orders.py` 中只查询有效销售单、不扣退货，必须保留为兼容入口；新净销售分析不能悄悄替换旧口径。

结论：Phase 0 可以进入数据模型、迁移和交互原型设计；不能跳过结构迁移与统一过账服务，不能直接在正式库启用库存入口。

## 3. 目标数据模型与迁移边界

### 3.1 结构分层

目标结构分为四层，不能把库存余额直接当作商品资料可编辑字段：

1. **主数据层**：`products` 增加规范化身份、图片、启用状态、安全库存和当前状态展示所需的派生字段；身份仍由稳定 `product_id` 引用。
2. **业务单据层**：保留旧 `orders` 供旧账只读和销售/退货兼容；新正式销售/退货逐步接入统一过账字段。拿货使用独立表及明细，避免伪造客户。
3. **库存事实层**：新增库存流水、库存余额/版本和成本快照。流水只追加，不通过重编辑覆盖；当前余额是流水服务维护并可重算核对的结果。
4. **审计与一致性层**：初始化/修订、正式过账、作废、恢复、幂等请求和冲突均留审计；请求摘要、版本号和过账序号用于拒绝重复或过期写入。

### 3.2 表与索引候选

准确名称可在实现阶段按现有命名核对，但语义和约束固定如下：

| 候选表 | 核心字段/约束 | 用途 |
|---|---|---|
| `product_inventory_state` | `product_id UNIQUE`、`enabled`、`quantity_3dp`、`cost_total_micro`、`avg_cost_micro`、`version`、`last_posting_seq` | 当前库存状态；未启用与零库存不同 | 
| `inventory_postings` | `posting_seq UNIQUE`、`product_id`、`source_type/id/line_id`、数量增减、成本总额增减、业务日期、过账时间、状态 | 不可变过账事实，来源引用不能丢 | 
| `inventory_initializations` | `product_id UNIQUE`、期初日期、数量、成本总额、来源类型、修订原因、锁定标记 | 一次性期初及首笔流水前修订 | 
| `purchase_orders` | `purchase_no UNIQUE`、业务日期、状态、货源备注、请求幂等键/摘要、软删除字段 | 独立拿货单，不关联客户账款 | 
| `purchase_order_items` | 稳定 `id`、`purchase_order_id`、`product_id`、数量、单价、金额、单位快照 | 拿货明细；正式后经济字段锁定 | 
| `sales_order_costs` 或订单明细扩展 | 稳定销售行 ID、成本总额/单位快照、成本完整性 | 保存销售时成本，不随后来拿货变化 | 
| `return_allocations` | `return_item_id`、`source_sale_item_id`、数量、金额分摊、成本分摊、版本 | 原销售行部分退货累计分摊与尾差守恒 | 
| `posting_requests` | 幂等键、内容摘要、原结果、状态 | 响应丢失重试和同键不同内容冲突 | 

必须建立的索引包括：产品业务唯一键、库存流水来源唯一键、按 `posting_seq` 的产品流水、单据业务日期/类型/状态、退货来源行、拿货编号日流水、对账快照单据集合。所有唯一性都要覆盖软删除规则，不能用恢复后才发现冲突的普通唯一索引替代业务校验。

### 3.3 过账服务接口候选

实现阶段优先新增深模块 `app/erp/services/inventory.py`，由它隐藏锁、精度、库存和成本规则；订单路由只负责输入转换和页面反馈。

- `initialize_product(product_id, quantity, cost, business_date, source, request_key)`
- `revise_initialization(product_id, quantity, cost, reason, expected_version)`
- `post_purchase(purchase_payload, request_key)`
- `post_sale(order_id, expected_versions, request_key)`
- `post_return(return_payload, expected_versions, request_key)`
- `void_posted_document(document_type, document_id, reason, expected_version)`
- `get_inventory_snapshot(product_ids=None)`
- `get_posting_trace(document_type, document_id)`

所有正式写接口必须在一个 SQLite 事务内完成：验证请求摘要/版本 → 分配不复用编号 → 锁定并重验库存/退货额度 → 写单据和稳定明细 → 写库存流水/成本快照 → 更新状态 → 写审计 → 提交。失败整单回滚。

## 4. 迁移与存量商品启用方案

### 4.1 迁移原则

- 不从旧销售数量推断期初库存，不从旧售价推断成本，不生成虚假拿货单。
- 迁移只做结构和兼容标记；旧保存/已打印单据标记为旧账，只读经济字段，金额、编号、日期、客户余额和打印快照不改。
- 迁移前使用 SQLite 一致性备份机制，同时备份数据根中的商品图片目录；运行中的主库不能只复制 `erp.db` 而忽略 WAL/SHM。
- 启动时检查数据库版本，旧程序不能在新结构上继续写；恢复时停止新程序，恢复一致性备份并使用兼容旧程序。
- 迁移脚本必须可重复执行，按版本事务推进；中断时能够从备份恢复或继续，不允许半迁移状态被当成可用。

### 4.2 存量商品启用

1. 扫描 `products`，名称和型号只做首尾空白规范化；报告规范化后重复项、软删除同键、断开引用和异常数量，不自动合并。
2. 先添加兼容字段和迁移标记，再为每个商品提供“启用期初”操作；商品可以零期初，但必须明确确认。
3. 数量大于零必须录入明确成本；未知成本阻止启用。零数量成本总额必须为零，零成本需要显式确认并审计。
4. 初始化成功后，同一请求重试返回原结果；首笔后续库存事件前可带原因修订，之后锁定。
5. 未启用商品展示“未启用/未知”，不计入库存金额、缺货和告急；汇总同时显示已启用覆盖范围与未启用数量。
6. Phase 1–3 全部通过前，新旧写路径不能在真实库并存；实际切换另需授权、备份、停旧实例、封闭旧销售/退货/删除恢复写路径。

### 4.3 失败、恢复与重复执行测试

- 构造旧版数据库，分别测试正常升级、重复升级、迁移中断、约束冲突、外键失败、恢复后旧账金额/编号/日期/余额不变。
- 构造名称+型号重复、软删除同键、旧明细 `product_id` 断开、超精度数量、缺成本等阻塞库；迁移只输出脱敏定位，不擅自清洗。
- 每次迁移后运行 `PRAGMA foreign_key_check`、`PRAGMA integrity_check`、版本检查及核心旧账查询。
- 业务测试 fixture 通过临时 `ERP_DATA_ROOT` 或现有 pytest 隔离 fixture，绝不从正式 `data/erp.db` 造数据。

## 5. 状态转换与业务不变量

| 状态/动作 | 允许 | 不变量与副作用 |
|---|---|---|
| 草稿新建/编辑 | 改客户、商品、数量、价格、日期、备注 | 不占库存、不占退货额度、不进分析/账款；编号一旦分配不复用规则另行处理 |
| 草稿转正式 | 通过一次事务过账 | 所有商品已启用、日期合法、库存足够、来源/成本完整；失败无部分写入 |
| 正式/已打印编辑 | 只改非经济备注（版本匹配） | 明细、客户、数量、价格、日期、类型、成本锁定 |
| 打印/补打 | 有效销售/退货 | 只增加打印计数；不产生库存效果 |
| 作废 | 必须原因且满足全单末笔条件 | 用原流水数量/成本精确反向；有后续依赖、有效退货或任一行不满足则整单拒绝 |
| 软删除 | 草稿或已满足作废规则的记录 | 生效历史和来源引用不能消失；删除不额外冲库存 |
| 恢复 | 恢复可见性 | 草稿保持草稿，作废保持作废，不能恢复为正式生效 |
| 永久删除/七天清理 | 无生效历史、无来源引用的草稿 | 不删稳定来源行、成本快照、库存流水或仍被引用的商品/客户 |

关键不变量：库存数量不得为负；库存成本归零时总成本必须为零；正式单据一条明细对应稳定行 ID；拿货不改变客户价/客户余额；退货累计量不超过原销售行可退量；对账打印不写资金记录；未知成本不能当零计入利润。

## 6. 精度、时间、编号、幂等与并发

- 数量使用 `Decimal`，最多 3 位小数，拒绝 NaN、无穷、超范围和多余精度。
- 售价/拿货价/交易金额以分保存；库存成本总额以元的百万分之一保存；平均成本内部计算至少 28 位精度，落库按 6 位小数 ROUND_HALF_UP。
- 业务日期含首尾用于报表；过账顺序由事务内不可变 `posting_seq` 决定。同日不使用可重复时间戳猜顺序；补录不重算既有销售成本。
- 销售/退货使用 `MDYYYYMMDDNNNN`，拿货使用独立 `NHYYYYMMDDNNNN`；到 9999 明确阻止，已分配编号不复用，刷新预览号不占用。
- 相同幂等键和相同请求摘要返回原结果；同键不同摘要返回冲突；响应丢失重试不得双扣库存、重复学习客户价或新增编号。
- 两窗口并发正式保存时，在写事务内重验版本和库存；数据库忙/锁等待返回可理解的重试提示，不绕过业务校验。

## 7. 页面、统计和打印边界

### 7.1 原型已经表达的新增交互

原型路径：`designs/simple-erp-inventory-analytics/inventory-analytics-prototype-v2.html`。旧版 `inventory-analytics-prototype.html` 保留作本轮问题对照，不作为验收对象。

- 商品资料：名称/型号具体身份、当前库存/成本/安全库存、期初未启用提示和一次性初始化/修订入口。
- 开单：销售、拿货、退货三种入口；拿货显示入库成本/货源内部备注，退货要求选择原销售单和可退量。
- 分析中心：统一日期/客户/商品名称/型号/指标筛选，净销售热力图，利润汇总，具体产品明细和当前库存状态分栏。
- 客户对账：单客户必选、默认全选、取消全选、逐单取消、交易对账净额；明确不等于收款。
- 打印隔离提示：内部字段显示在内部面板，对外预览只保留客户、单号、商品、数量、售价、金额和签字区域。

### 7.2 统计服务契约映射

| 页面结果 | 服务端口径 |
|---|---|
| 热力图 | 有效销售与客户退货按各自 `order_date` 聚合；净数量/净金额分别为销售减退货 |
| 利润汇总 | 销售成本快照减退货冲回成本；成本缺失单列，不把未知当零 |
| 商品明细 | 按稳定 `product_id` 聚合；名称筛选展开全部型号；型号筛选只取目标 ID |
| 库存状态 | 只读当前库存状态，不因历史日期倒推；缺货优先，告急包含缺货 |
| 对账 | 单客户、有效销售/退货完整订单集合；订单总额只计一次；结果快照打印前复验 |
| 旧采购统计 | 继续只统计有效销售、不扣退货，显式使用旧口径标签 |
