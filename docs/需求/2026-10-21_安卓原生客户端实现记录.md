# 安卓原生客户端（Compose）· 实现与验收记录

> 日期：2026-10-21　状态：**可运行，已在模拟器上逐页实测**<br>
> 取代关系：本文**补充** `2026-10-17_安卓只读端架构决策.md`，不取代它。架构决策里的只读约束、配对门、口径规则全部继续有效。

## 1. 做了什么

把原来的「WebView 壳」换成一个**真正的原生 Compose 客户端**，同时**保留**服务端渲染的 HTML 页面（`/m/*`）不删。

两个客户端并存不是过渡态，是有意的退路：HTML 那条路继续可用，原生端出问题时可以让人先用浏览器顶一阵。

```
┌──────────────────────────┐   ┌──────────────────────────┐
│ 原生 Compose 客户端        │   │ 浏览器（HTML 页面）        │
│ native/                  │   │ /m/*                     │
│  · 零业务计算              │   │  · 服务端渲染，保留不动     │
│  · 离线缓存               │   │  · 无需安装                │
└───────────┬──────────────┘   └───────────┬──────────────┘
            │  JSON  /m/api/*              │  HTML
            └───────────┬──────────────────┘
                        ↓
        第二监听 5001（独立 Flask app）
          ├─ mobile_bp      → HTML 页面（原有）
          └─ mobile_api_bp  → JSON 接口（本次新增）
                        ↓
        services/readonly_queries.py（唯一口径来源，mode=ro 只读连接）
                        ↓
                  data/erp.db
```

**关键设计：口径只有一份。** 原生端**不做任何业务计算** —— 余额、退货负数、状态过滤、四类分组全部由服务端算好；连金额字符串（`¥3,980` / `-¥300.00`）都是服务端排好版发过来的。安卓只负责画。

这不是为了省事，是为了防分叉：这些口径在 `readonly_queries.py` 里有对拍测试，如果安卓自己算一遍，两套实现迟早不一致，而且分叉时**不会有任何测试失败**。

## 4. 离线缓存怎么做的

这是原生端相对 WebView 壳的**真正收益**（不是「更好看」）。

- 每次成功响应落盘到 `files/api-cache/`，格式是 `时间戳` + 换行 + JSON。
- **只有「连不上」才回落缓存**。服务端明确返回 500 时必须显示错误 —— 否则店主会拿着昨天的价去报价，而界面看不出异常。
- 回落时页面顶部显示黄条：`离线 · 连不上电脑，显示的是 10月21日 14:23 的数据`。
- 恢复联网后黄条自动消失。

## 6. 实测踩出来的 6 个 bug（都已修）

这部分是本文最值钱的地方 —— 每一个都只有在真机上跑才会暴露。

### 6.1 Enter 键误触「换个地址」，把地址清空

**症状**：输入 6 位码按「完成」，界面莫名回到「连接电脑」，地址被清空。

**原因**：`Modifier.clickable` 会注册键盘事件处理。输入框的 Enter/Done 键冒泡到「换个地址」这个 Text 上，**激活了它**。调用栈实测：

```
AbstractClickableNode.onKeyEvent ← AppRoot.kt:105 (onChangeAddress)
```

**修法**：那个 Text 改用 `pointerInput` + `detectTapGestures`，只响应触摸，不参与键盘事件。

### 6.2 键盘挡住「配对」按钮

**症状**：键盘弹出后点按钮没反应，请求根本没发出。

**修法**：页面加 `imePadding()`；同时给输入框加 `keyboardActions(onDone)`，按「完成」直接提交 —— 键盘挡着按钮时这是唯一可靠路径。

### 6.3 错误信息显示成 Unicode 转义

**症状**：配对失败时界面显示一串 `\u914d\u5bf9\u7801...`。

**原因**：我用正则从响应体里抠 `error` 字段，而 Flask 的 `jsonify` 默认把中文转成 `\uXXXX`。

**修法**：走 JSON 解析，取 `jsonPrimitive.content`。

### 6.4 冷启动后地址丢失

**症状**：杀掉 App 重开，回到「连接电脑」。

**原因**：`bootstrap()` 曾经写成「内存值优先、空了才读 DataStore」。Activity 重建时 ViewModel 跟着重建，新实例内存是空的。

**修法**：地址一律以 DataStore 为准，内存值只用于「刚写入还没落盘」的极短窗口。

### 6.5 清 cookie 清错了对象

**症状**：换电脑地址后一直 401，重新配对也没用。

**原因**：`AppViewModel` 自己 new 了一个 `PersistentCookieStore`，和 `ApiClient` 内部那个是**两个实例**。清的是前者，真正发请求用的是后者。

**修法**：`ApiClient` 暴露 `cookieStore`，外部统一用同一个。

### 6.6 两个显示问题

- **`📅` 渲染成豆腐块**：部分字体把 emoji 显示成「17」。日期文案本身已足够，去掉 emoji。
- **缓存时间显示成 UTC**：`SimpleDateFormat` 不显式设时区时按 JVM 默认走。改成 `TimeZone.getDefault()`。

## 8. 怎么构建

```bash
cd native
export JAVA_HOME=/d/app/Android/jdk21   # Gradle 需要 JDK 17+
./gradlew assembleDebug                  # 产物 app/build/outputs/apk/debug/
./gradlew assembleRelease                # 用 keystore/simple-erp.jks 签名
```

工具链实测可用：**Gradle 9.3.0 + AGP 8.11.0 + Kotlin 2.1.0 + Compose BOM 2025.01.00**。

打包给门店用 `打包手机APK.bat`（已指向 `native/`，产物 `dist\simple-erp-mobile-v<版本>.apk`）：

```bash
打包手机APK.bat          # 内部调用 native\gradlew.bat assembleRelease
```

脚本里有两个坑，都是实测踩出来的：

1. **必须用工程自带的 `gradlew.bat`，不能用 `gradle-cache` 里那个 8.14.3**。Kotlin 2.1 插件在 Gradle 8.x 上解析不到，报错是 `Plugin [id: 'org.jetbrains.kotlin.android'] was not found` —— 看着像网络问题或仓库配错，其实是 Gradle 版本不对。
2. **构建前若有 Gradle daemon 在跑，`mergeDexRelease` 会因文件占用失败**（`Unable to delete directory ... classes.dex`）。脚本用 `--no-daemon` 规避；手工构建遇到就先 `./gradlew --stop`。

> 包名不能用 `com.simpleerp.native`：`native` 是 Java 关键字，AGP 直接拒绝构建。

## 9. 扫码配对与设备区分（2026-10-21 晚补做）

这两项原本列在「没做的事」里，当天补完了。

### 9.1 扫码配对：解决「地址不该硬编码」

**问题**：任何写死地址的方案都是错的。写 IP 会在路由器换租约后失效（当天就发生了，见 §10）；写主机名（`asty`）换台电脑就废，而且用户 IP 网段各不相同，没有通用值。

**正确答案是扫码**：电脑端设置页早就在生成二维码（`utils/mobile_qr.py`），里面编的是**电脑当前的完整地址**。IP 变了就重扫一次，用户永远不需要知道 IP 是什么。

实现：

| 文件 | 作用 |
|---|---|
| `net/ServerAddress.kt` | **纯函数**的地址归一化（补协议、去路径、补端口） |
| `net/PairingQr.kt` | 二维码内容 → 服务器地址，含合法性校验 |
| `ui/screens/ScanQrButton.kt` | 扫码按钮 + 相机权限申请 + `CaptureActivity` 拉起 |

扫码是**主路径**，放在手输地址上方；手输保留为备选（二维码扫不出来时用）。

**为什么要校验主机名**：只判断「非空」的话，扫到一段普通中文（别人家二维码的说明文字）会被归一化成 `http://这是一段普通文字:5001` —— 一个永远连不上的地址，而用户看到的错误是「连不上电脑」，排查方向完全错。这条是实测踩出来的，已修。

**依赖**：`com.journeyapps:zxing-android-embedded:4.3.0`。选它而不是 CameraX + ML Kit 的理由：不依赖 Google Play 服务（店主手机可能没有 GMS，ML Kit 会直接不可用）。

#### 9.1b 默认扫码界面没有退出口（真机反馈，已修）

第一版直接用库自带的 `CaptureActivity`，结果是一个**全屏相机，上面一个控件都没有**：

- 没有返回按钮。手势导航的手机没有实体返回键，用户**进去就出不来**。
- 没有「从相册选」。二维码在另一台手机上、或者是别人发来的截图时，完全没法扫。

这是典型的「功能做完了但不好用」——技术上能扫，实际用起来是死路。

修法：自己写 `ErpCaptureActivity` 继承 `CaptureActivity`，用 `addContentView` 在相机预览上叠两个控件：

| 控件 | 位置 | 行为 |
|---|---|---|
| `✕` | 左上角（48dp，含状态栏安全区） | 取消扫码，回到填地址页 |
| 「从相册选一张」 | 底部居中 | 打开系统图片选择器，解码后识别 |

相册识别用 zxing 的 `MultiFormatReader` + `RGBLuminanceSource`。**必须先降采样**：相册原图动辄 4000×3000，直接 `getPixels` 会吃掉几十 MB 并卡住，而二维码在 1600px 内完全够识别。

#### 9.1c 三个实现细节（都是必须做对的）

**1. 基类必须用 `ComponentActivity`，不能用库的 `CaptureActivity`**

`CaptureActivity` 继承的是 `android.app.Activity`（不是 `ComponentActivity`），拿不到 `registerForActivityResult` —— 相册只能走已废弃的 `startActivityForResult` + `onActivityResult`。那套 API 在配置变化、进程被回收时容易丢回调。

所以第一版我用废弃 API 绕过去了，后来改成**自己组装**：

```
ComponentActivity（现代 Activity Result API）
  + DecoratedBarcodeView（库的相机预览）
  + CaptureManager（库的生命周期与解码回调）
```

这样既拿到现代 API，又不用重写相机层。代价是多写 30 行布局代码，换来没有技术债。

**2. 相册图片必须降采样**

相册原图动辄 4000×3000，`getPixels` 要分配 `w*h*4` 字节（约 **48MB**），中低端机上会直接 OOM 或卡住几百毫秒。二维码在 1600px 以内完全够识别。

实现是**分两趟读**：第一趟 `inJustDecodeBounds = true` 只取尺寸（不分配像素内存），算出 `inSampleSize`；第二趟才真正解码。

**3. 图片里没二维码时必须给提示**

否则用户会以为按钮点坏了，反复点同一张图。用 Toast 明确说「这张图片里没找到二维码，换一张试试」。

> 这三条我在第一版回复里写成了「三个问题」，其实第 2、3 条当时已经实现了，只是位置写在「实现细节」里容易读成待办。真正没解决的只有第 1 条，现已修。

**实测**（模拟器）：生成真实二维码 PNG → 推到相册 → 扫码 → 从相册选 → 自动解析出 `http://10.0.2.2:5001` → 直接进配对页。整条链路闭合。

### 9.2 设备区分：设置页能分清 App 和浏览器

**问题**：原生端的 UA 里同样带 `android`，所以一个 App 和一个浏览器在设置页会显示成两条一模一样的「Android 手机」，撤销设备时没法判断该撤哪条。

**做法**：配对记录加 `platform` 字段。

- JSON 接口（`/m/api/pair`）默认 `app` —— 只有原生客户端会调
- HTML 页面（`/m/pair`）固定 `browser`
- 服务端只认 `app` 一个字面值，其余一律归到 `browser`（`normalize_platform`）。这样即使有人伪造，也只能伪造出「浏览器」，不会伪造出「这是店主的手机 App」这种更危险的身份
- **老记录没有这个字段**，按浏览器算 —— 那时唯一的客户端就是浏览器，猜成 App 会给出错误信息

设置页表格新增「接入方式」列，显示为徽章。

### 做了什么

| 改动 | 说明 |
|---|---|

响应头 `Content-Disposition: attachment` 正确。

### 卡在哪：Chrome 的两道强制拦截

手机 Chrome 133 上实际点「下载并安装」，走了两道拦截：

1. `File can't be downloaded securely`（点 Keep 继续）
2. `File might be harmful` → `Do you want to download simple-erp-mobile (1).apk anyway?`

两次都确认之后，文件下到 7,955,586 字节（**完整**），但一直停在
`.pending-1793194230-simple-erp-mobile (1).apk` 这个临时态，
`/sdcard/Download/` 里翻不到正式 APK，装不上。

**根因**：Chrome 对「非 HTTPS + 可执行文件」的安全策略。局域网没有证书，
必然是 HTTP，所以没有绕法。这不是代码问题，换写法也不会变。

### 最终方案（用户 2026-10-21 定案）

**传一次文件安装，之后扫码配对**：

1. `打包手机APK.bat` 出 `dist\simple-erp-mobile-v<版本>.apk`
2. 用微信 / QQ 文件传输助手把 APK 传到手机，点开安装（一次即可）
3. 打开 App → 点「扫二维码」→ 扫电脑设置页那张码 → 输 6 位配对码

二维码内容保持 `http://<ip>:5001/m/`：App 扫它拿主机地址（App 侧会去掉路径），
浏览器扫它开只读端。**两种用法都成立，不要改成下载页。**

### 备选方案（当时评估过，未采用）

- **引导用其他浏览器打开**（夸克 / UC / 自带浏览器）：对局域网 APK 下载通常不拦，
  但失败模式是随机的 —— 取决于用户手机装了哪个浏览器。不如「传文件」这种
  失败模式明确的方式。
- **本地起 HTTPS（自签证书）**：能根治，但要让手机装证书，比传文件还麻烦。

## 10. 还没做的事（明确边界）

- **离线缓存的写盘时机**：每次成功都写，没有做「只缓存变化的数据」，数据量大时会有冗余写。当前数据规模下无感。
- **摄像头实扫没验**：模拟器的虚拟相机是彩条测试图，没法对准真实二维码。但「从相册选一张」这条路已经端到端验通（生成 PNG → 推相册 → 识别 → 进配对页），而两条路走的是同一个解析器，所以只剩「相机取景」这一环没验。
- **DHCP 保留仍未配**：需要路由器管理员密码，见 §10。

## 11. 局域网 IP 漂移：预言发生了（2026-10-21 实测）

架构决策 §2.4 早就写了「`192.168.10.5` 是否是 DHCP 保留地址**未验证**，路由器重启或租约到期都可能换成另一个值，症状与『电脑没开』一模一样」。

**2026-10-21 当天就发生了**：

| 项目 | 架构文档记录（2026-10-17） | 实测（2026-10-21 14:40） |
|---|---|---|
| 局域网 IP | `192.168.10.5` | **`192.168.1.129`** |

网段都换了（`192.168.10.x` → `192.168.1.x`），不只是末位漂移。

### 这件事的实际影响

1. **手机里存的旧地址立刻失效**。表现是「打开就转圈，最后说连不上」，而电脑端一切正常 —— 正是 §2.4 描述的同形故障。
2. **浏览器快捷方式同样失效**（地址是扫码/手输存进去的，不会自己更新）。
3. **原生端的应对是正确的**：地址存 DataStore、设置页有「改地址」，改完不用重装。这条设计从「理论上需要」变成了「当天就被验证需要」。

### 仍然没做的事

**路由器上的 DHCP 保留至今没配**。这不是遗漏，是 §2.4 里已经定过的取舍：进不去路由器、或它没有 DHCP 保留功能时，直接放弃这一步。当前是靠「设置页显示当前 IP + 手机端可改地址」兜底。

> 结论：**每次发现手机连不上，第一件事是去电脑设置页看当前 IP 是不是变了**，而不是怀疑服务挂了。

回来提了一批问题；每一个都对应一处真实设计缺陷，而不是「样式不好看」这种主观项。

## 12. 本轮修的四类问题

| # | 用户原话 | 实际根因 | 性质 |
|---|---|---|---|
| 1 | 「桌面端没有刷新出来已配对的设备信息」 | 设置页是服务端渲染，不轮询 | 桌面端缺陷 |
| 2 | 「实时扫描配对码还是失败了，我还是扫描的照片」 | zxing 只对焦一次 | **客户端硬伤** |
| 3 | 「三级页面大部分打不开」 | 缓存按接口逐条落，详情未预缓存 | 设计取舍失误 |
| 4 | 「加载时间也有点长」 | `connectTimeout` 2.5s 干等 | 参数问题 |

## 13. 扫码扫不出来：真正的原因是相机对焦（最值钱的一条）

### 13.1 症状

用户原话：**「扫码只能从相册里选出来的能扫出来，直接对着电脑扫，扫不出来」**。

这条信息量极大：**同一个解析器，相册能过、相机不能过** → 问题一定在「拿到图像」这一步，
不在解析。

### 13.2 排查

1. 先排除了二维码本身：`qr_png_data_uri()` 生成的 `http://<ip>:5001/m/` 用 `qrcode` 库生成，内容合法。
2. 再排除了解析器：`PairingQr.parse()` 有单测，16 条用例全过。
3. 反编译 zxing 库看 `CameraSettings` 的默认值：

```
$ javap -p -c -classpath cls com.journeyapps.barcodescanner.camera.CameraSettings
  ...
  25: iconst_1
  26: putfield  // Field autoFocusEnabled:Z      ← true
  29: iconst_0
  31: putfield  // Field continuousFocusEnabled:Z ← false ！！！
```

**根因确认**：`autoFocusEnabled=true` 但 `continuousFocusEnabled=false` ——
**只对焦一次就停了**。

手机对着电脑屏幕时，第一次对焦往往落在背景（键盘、桌面、背后的墙）上。
之后画面里出现了二维码，相机**也不会重新对焦**，于是永远解不出码。
而相册里是清晰原图，所以那条路一直好使 —— 完美解释用户的观察。

### 13.3 修法

```kotlin
cameraSettings = CameraSettings().apply {
    isContinuousFocusEnabled = true
    isAutoFocusEnabled = false      // 一次性对焦和连续对焦同时开会互相打架
    isBarcodeSceneModeEnabled = true // 场景模式会拉高锐度、降噪，磨掉二维码方块边缘
    isMeteringEnabled = true         // 屏幕自发光，不测光可能曝成一片白
}
```

### 13.4 顺带：照片解码也加固了

用户后来又说「照片也扫不出来了」，说明解码环节也不够稳。

原实现用 `MultiFormatReader()` **不带 hints** —— 那是「所有格式都试」，
在没有 `TRY_HARDER` 的情况下反而容易在噪声上失败。改成多轮升级：

| 轮次 | hints | 什么时候救得回来 |
|---|---|---|
| 1 | `POSSIBLE_FORMATS=[QR_CODE]` | 绝大多数情况，也最快 |
| 2 | 同上 + `TRY_HARDER` | 反光、轻微变形、码偏小 |
| 3 | 全格式 + `TRY_HARDER` | 别人家 App 生成的码 / 条码 |
| 4 | 图放大 2 倍再试 | 截图缩放过、码只有 100px 宽 |

### 13.5 边界：这条修了但我验不了

**模拟器相机是彩条测试图**，无法对准真实二维码。我能验的只有「从相册选一张」，
那条路端到端通了（生成 PNG → 推相册 → 识别 → 进配对页）。

「连续对焦是否真的解决了对着屏幕扫不出来」**必须真机实测**。这一条已登记在
`docs/当前遗留问题与效果待验收清单.md`。

## 14. 断网时三级页面打不开：缓存的粒度问题

### 14.1 症状

「一级页面能看到，但是二级三级就看不到了」「三级页面大部分打不开，除非是我在联网的情况下打开过的」。

### 14.2 根因

`ResponseCache` 是**按接口逐条**落的：

```kotlin
cacheKey = "document:$orderType:$documentId"
```

列表页缓存了，**不代表列表里每一张单据的详情也缓存了**。
用户从「最近单据」点进去那张单，如果从来没联网打开过 → 没有缓存 → 断网必然失败。

这不是 bug，是**设计时的取舍没想到使用路径**：我假设「用户会先点开再看」，
但真实场景是「在客户详情里看到单号，随手点进去核对金额」。

### 14.3 修法：用列表摘要降级渲染

失败时不显示「连不上电脑」，而是从**已加载的列表**里捞摘要拼一份简版详情：

```kotlin
private fun fallbackDocumentDetail(orderType: String, documentId: Int): UiState<DocumentDetail>? {
    val summary = findDocumentSummary(orderType, documentId) ?: return null
    // 单号/日期/客户/金额/类型全在摘要里，只缺 items
    return UiState.Ready(DocumentDetail(..., items = emptyList()), fromCache = true, ...)
}
```

`findDocumentSummary` 查两处：当前单据列表 → 各客户详情里的「最近单据」。
后者很关键：从「客户详情 → 点最近单据」进来时，单据列表根本没加载过。

页面上明确写「明细需要联网才能看」——**不假装这单没商品，也不假装明细是空的**。

### 14.4 顺带：超时从 2.5s 收到 1.5s

用户说「加载时间也有点长」。缓存是瞬间出的，那点延迟**全是 `connectTimeout`** ——
断网时要干等它放弃才回落。局域网正常 20~80ms，1.5s 已经很宽松。

## 15. 设置页不显示已配对设备：服务端记了，页面没刷

### 15.1 排查过程（差点误判）

用户报「桌面端这里没有刷新出来已配对的设备信息」，截图显示「已配对设备 0 台」。

**第一步先查服务端**（这一步很关键，避免了走弯路）：

```json
{"devices": [{"id": "a6ec21af777abeaf", "paired_at": "2026-10-22T14:48:27",
              "last_seen_at": "2026-10-22T14:59:45", "last_ip": "192.168.1.41"}]}
```

**记录完全正确**：设备在、配对时间在、最后访问在。所以问题 100% 在页面。

### 15.2 根因

设置页是**服务端渲染**（Flask + Jinja），HTML 只在打开那一刻生成一次。
店主开着这个页面、拿手机扫码配对 —— 服务端写进去了，但那个页面不会自己变。

### 15.3 修法

新增 `GET /settings/mobile/devices` 返回 JSON，前端每 4 秒拉一次：

```javascript
function poll() {
  fetch('/settings/mobile/devices').then(...).then(payload => {
    var sig = signature(payload);
    if (sig === lastSignature) return;   // ← 关键：没变就不重绘
    lastSignature = sig;
    renderDevices(payload);
  });
}
```

**为什么必须做「没变就不重绘」**：否则每 4 秒重建整张表，
用户鼠标选中的文字会被清掉、正在读的内容会闪。

### 15.4 踩坑：漏了 `jsonify` 导入，接口 500

第一版打包后我实际运行验证，接口返回 **500**：

```
NameError: name 'jsonify' is not defined
```

**这个 bug 的可怕之处**：它的表现是「页面不刷新」，跟「功能没做」**一模一样**。
如果我只看「编译成功」就交付，用户会以为自动刷新又没生效，双方又要绕一圈。

修完后加回归测试：

```python
def test_devices_json_endpoint_returns_devices():
    response = client.get("/settings/mobile/devices", ...)
    assert response.status_code == 200
    assert payload["ok"] is True
```

## 16. 客户详情页：三个信息层级问题

用户一次提了四条，其中三条是「主次不分」的具体表现：

| 问题 | 判断 | 修法 |
|---|---|---|
| 「看全部」和「展开全部 8 条」功能重复 | **用户是对的** | 删掉「看全部」，保留原地展开（不跳页、不丢上下文） |
| 顶部返回栏和余额应该固定 | 对 | `LazyColumn` 改成 `Column(固定头 + 可滚内容)` |
| 「当前欠款」和数字要压成一行 | 对 | 大卡（约 120dp）压成一行（约 56dp） |
| 欠款绿色、多付红色 | **语义反转，但正确** | 显式给 tint，不沿用 AmountText 的「负数红」 |

### 16.1 颜色语义值得单独说

原来的逻辑是「负数红、正数黑」，但在这个业务里：

- **欠款 = 别人欠我的 = 钱要进来 = 绿色**
- **多付 = 我欠别人的 = 钱要出去 = 红色**

这跟「金额正负」的直觉**相反**（正数才是欠款）。所以不能用 `AmountText` 的默认配色，
必须显式传 `tint`。这是个典型的「通用组件默认值不适用于本业务语义」的例子。

### 16.2 为什么不用 `stickyHeader`

`LazyColumn` 有 `stickyHeader`，但它只吸顶到**内容区顶部**，而这里要的是
「两个块都不参与滚动」——语义不同。而且 `stickyHeader` 在快速滑动时有贴图抖动。

## 17. 配对码输入框：六格但只有一个输入控件

用户要求「改成六个独立的圆角矩形」。

**没有做成六个各自持焦点的输入框**，理由：

- 那需要手写「输满自动跳下一格、退格跳回上一格、粘贴 6 位要分发、删中间一位要补位」
  一整套逻辑；
- 各家输入法（尤其国产的联想、自动填充）上行为不一致；
- 代码量多一个数量级。

**实际做法**：一个透明 `BasicTextField` 铺在六个格子**之上**，格子是纯展示。
键盘行为跟普通输入框完全一样，稳定。

额外加了两点体验：进页面自动聚焦（键盘直接弹出）、当前待输入格蓝色高亮。

## 18. 扫码界面的定位计算：我踩了一个数学坑

### 18.1 需求

提示文字「对准电脑设置页上的二维码」原本贴在屏幕最底边 —— 那是 zxing 库自带的
`zxing_status_view`，在它的布局里 `layout_gravity="bottom|center_horizontal"` 硬编码。
用户要求挪到扫描框下方。

### 18.2 踩坑：多乘了一次比例

第一版我这样算：

```kotlin
val scale = viewHeight / preview.height.toFloat()
val bottomInView = (frame.bottom * scale).toInt()   // ← 错
```

结果提示被推到屏幕中间，和「从相册选一张」按钮**重叠**了。

**原因**：`getFramingRect()` 返回的**已经是 View 坐标系**
（`ViewfinderView` 直接拿它去 `canvas.drawRect`，而 canvas 用的是 View 自己的坐标）。
再乘一次预览比例就翻倍了。

**正确做法**：`topMargin = frame.bottom + dp(18)`，不需要换算。

### 18.3 另一个坑：framingRect 什么时候才有值

相机是异步初始化的，`onCreate` 那一刻 `framingRect` 还是 `null`。
必须等 `onGlobalLayout`：

```kotlin
overlay.doOnLayout { placeHintBelowFrame() }
overlay.viewTreeObserver.addOnGlobalLayoutListener { placeHintBelowFrame() }
```

同时加了兜底：框底部已经很低时，把提示夹在相册按钮上方，否则两者会重叠。

## 19. 「断开连接」：一个故意不做的东西现在做了

架构决策里明确写过「解除本机配对」这个按钮**故意不做** —— 那会变成第二个写端。

但用户要的是**本机的「我不用这台电脑了」**，不是「撤销设备」。
两者区别：

| 动作 | 在哪做 | 影响范围 |
|---|---|---|
| 撤销设备 | 电脑端 | 服务端删记录，这台手机立刻失去访问 |
| 断开连接 | 手机端 | 只清本机 cookie + 地址，**服务端不动** |

所以这个功能**不违反「单一写端」约束**：它不写服务端任何东西。
实现上带二次确认，并明确告知「电脑上的数据和其他设备都不受影响」——
用户最怕的是「我点一下会不会把店里的数据搞坏」。

**缓存不清**：断开是「不再连这台电脑」，不是「忘掉看过的数据」。
