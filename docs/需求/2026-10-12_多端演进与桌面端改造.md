> 决策日期：2026-10-12<br>

## 1. 文档目的与适用范围

本记录服务于一个具体决策：**是否让"简单ERP"走向多端（Android），以及若走，桌面端需要改什么。**

触发背景：用户提出希望有"可以独立使用、可以和电脑同步"的 Android 版。该诉求在任何仓库文档中均无记录（见 §3），属于本次讨论的新输入。两个 agent 就此进行了 10 轮交叉核验，本记录固化结论与证据，供后续接手者共用。

**仓库惯例与命名说明。** 本项目没有 ADR（Architecture Decision Record）目录，但已有"决策记录"先例：`docs/需求/2026-07-26_永久免登录.md`。因此本文件沿用该惯例：

- 位置：`docs/需求/`。依据根目录 `AGENTS.md` 的文档分工表，"专题需求/已确认决策"归入 `docs/需求/`。
- 命名：`YYYY-MM-DD_主题.md`。既有样本 `2026-07-26_永久免登录.md`、`2026-07-10_初始需求文档_v0.6.md` 均为日期前缀。
- 原拟名 `docs/多端演进与桌面端改造_决策记录.md` 不符合上述两点（位于 `docs/` 根、缺日期前缀），故改为 `docs/需求/2026-10-12_多端演进与桌面端改造.md`。

**谁该读它：** 后续接手桌面端改造或 Android 客户端开发的 agent；需要做产品取舍的用户本人；任何要理解"为什么做/不做什么"的人。

**不适用：** 本记录不含业务数据、密钥、个人联系信息，也不替代 `docs/需求/消防器材店ERP系统-需求文档.md`（当前产品事实主文档）。

## 2. 结论摘要

1. **Android 方向在本项目从未被评估过**，既没被批准，也没被否决。仓库里被暂缓的只有"窄屏 Web 改版"，不是原生客户端。
2. **多端的真正闸门不是分层，而是部署/认证/并发/打印这四条单机前提**：服务硬绑 `127.0.0.1`（有测试钉死）、永久免登录、单 SQLite 文件、单据号依赖中心单调取号。这四条没有一条能靠"分层"解决。
3. **读层抽取值得做，但理由与 Android 无关**。它是消除同一概念的多处实现分散；这些口径是否本应一致，需求文档尚未定义（见 §4 与 §9）。
4. **"独立使用"必须拆成两档**：档一（数据独立、单据回店打印）不动任何已验收契约；档二（手机独立开正式单）至少动单号契约，且躲不掉。
5. **档一总量与方案甲几乎重叠**（28.5–44 人日 vs 28–50 人日），两者只差钱花在哪，不差量级。"档一明显便宜"这一直觉是错的。

## 4. 被推翻的假设清单

本章是本次讨论最重要的产出。10 轮里有多条看似有力的判断被证据推翻。逐条记录**原假设 → 推翻它的证据 → 教训**，以便后来人理解这些弯路为什么会发生。

### 4.1 Android 工具链 agent 侧被推翻的判断

**A1. "orders.py 一个文件里塞了 52 条 SQL"**
- 原假设：单文件 orders.py 含 52 条 SQL，是"业务与 HTTP 缠绕"的核心证据。
- 推翻证据：52 是**全 routes 目录**的 SQL 关键字聚合数（SELECT 43 / UPDATE 6 / DELETE 2 / INSERT 1）。orders.py 单文件是 41 次 `conn.execute` + 19 次 `get_db()`。行数类结论（routes 4387 / services 3855 / orders.py 1454）则完全准确。
- 教训：聚合数与单文件数不能混用。数字正确但口径错误，比数字错误更难被发现，因为它会以"很精确"的外观取得信任。

**A2. "业务逻辑和 HTTP 层缠在一起了"（暗含写路径也没分层）**
- 原假设：整个业务层与路由层纠缠，所以要重做分层。
- 推翻证据：写路径**已经分层**——create / update / void / delete / cost_backfill / 过账全部在 `services/accounting.py` 与 `services/inventory.py`，路由只是薄壳。真正未分层的是读路径。
- 教训："某处没分层"要先问"哪一半"。整体印象会掩盖局部事实，而修复方案完全取决于这个区分。

**A3. "最大技术债是分层不干净"**
- 原假设：分层是当前最大技术债，也是通往 Android 的主要障碍。
- 推翻证据：通往多端的真正障碍是四条单机前提（§2 第 2 条）。分层再干净，也解决不了 `127.0.0.1` 硬绑、免登录、单文件数据库、中心取号。
- 教训：把"我能看见的代码问题"等同于"最大的问题"。可见性偏差会让技术债排序偏离真实阻塞点。

**A4. "档一（数据独立）明显便宜"**
- 原假设：不联机、不同步冲突的档一，应显著低于联机方案。
- 推翻证据：桌面端 13.5–19 人日 + Android 15–25 人日 = **28.5–44**，与方案甲 28–50 几乎重叠。省下的是认证与网络，付出的是导入通道与客户端精度镜像。
- 教训：方案对比要看总账。把"少了某块"当成"整体更便宜"，忽略了新方案自己引入的等量成本。

### 4.2 桌面端开发 agent 侧被推翻的判断

**B1. "Android 是被用户明确搁置过的方向"**
- 原假设：用户此前否决过 Android，所以拿它当既定前提是错的。
- 推翻证据：文档里的"暂缓"只针对**窄屏 Web 改版**。原文两处：`docs/当前遗留问题与效果待验收清单.md` 第 28 行"用户接受现状，暂不改移动端……移动端改版暂不纳入当前重点"；`docs/需求/消防器材店ERP系统-需求文档.md:224`"用户接受现状，暂不做移动端改版"。归档的 `2026-07-10_初始需求文档_v0.6.md` 第 672–679 行"MVP 阶段不得实现……6. 云同步、手机端、小程序"也只是 MVP 范围，不是否决 Android 原生。**Android 原生方向在仓库里是空白，既非批准也非否决。**
- 教训：**把"暂缓 A"外推成"否决 B"**。文档没写的事，不能当成写了。这一条后来演变成更严重的形态（见 B2）。

**B2. "用户没提需求 = 用户不需要"**
- 原假设：需求侧证据不支持必须原生，故推荐不联机不可行的方案丙。
- 推翻证据：用户原话是"安卓版我想可以独立使用，可以和电脑同步"。仓库文档只能支持"窄屏 Web 改版暂缓"，对"独立 Android"是空白——**空白不等于否，更不等于不需要**。且对话中的用户原话是**当下证据**，强度高于任何历史文档。
- 教训：这是 B1 的升级形态——用弱证据（历史文档）去推翻强证据（用户刚说的话）。**证据强度必须排序：用户当下陈述 > 仓库文档 > 推断。**

**B3. "ImportPreview 的预览/确认模式可直接复用到单据导入"**
- 原假设：主数据导入已有的 `ImportPreview` 模式可复用到单据导入，省掉预览开发。
- 推翻证据：可复用的只是**外壳**（约 1 天），不是**模式**。四处结构性差异使实际工作是全新的：① 粒度不匹配（主数据一行一实体，单据是单头 + N 行明细，`ImportPreview.rows` 是平铺的、无分组键）；② `action` 词表不够（现有 add/skip/error/update，单据还需单号冲突、客户未匹配、商品未匹配等）；③ 事务边界不同（主数据导入逐行 INSERT、无整批回滚；单据导入必须整批一个事务，半张单入库会毁对账）；④ 匹配性质不同（主数据是确定性匹配，单据面对模糊匹配 + 人工裁决）。
- 教训：**"外壳可复用"被表述成"能复用"**，会系统性低估工作量。复用判断必须以"省掉多少天"为单位，而不是以"像不像"为单位。

**B4. "MD 取号缺并发保护是真 bug"**
- 原假设：MD 取号在写事务外进行，会导致并发撞号、数据损坏，是"0.5–1 人日就能修的真 bug"。
- 推翻证据：机制描述正确，但**后果定性错误**。`orders.order_no` 有 UNIQUE 约束（`app/erp/db.py:777`），并发第二个 INSERT 会抛 IntegrityError（用户看到 500），**不会静默写坏数据**。且当前为单人单机场景，触发概率极低。
- 教训：**"机制缺口"不等于"数据正确性 bug"**。严重性判断必须落到"最坏后果是什么"，不能停在"有没有保护"。把它捧成"唯一真 bug"是过度定价。

**B5. "S1（日期区间口径不一致）是唯一一个既能复现、又没人反驳过的现存缺陷"**
- 原假设：列表用三表 UNION、导出/汇总用单表，是明确的缺陷，可直接开工修。
- 推翻证据：需求文档**从未定义**单据列表与导出的日期范围口径必须一致；唯一写"使用相同日期范围"的条文（`:251`）对象是**账款页**。而 `:72` 明写导出**故意**与列表口径不同（汇总忽略列表订单类型，Excel 各自固定类型）。此外，该边界只是 `fallback_start/fallback_end`，仅在"未填日期 + range 模式"生效（`app/erp/routes/orders.py:143-216`），暴露面很窄。因此现有行为可能是**正确的**。
- 教训：**"能复现"不等于"是缺陷"**。在需求未定义的地方，"不一致"可能是未定义口径，也可能是刻意设计。定性错误会让工作量、风险、验收标准全部错位——S1 因此从"开发切片"降级为"口径确认动作"。

**B6. "备份工具没有恢复代码"（源自编写方既有记忆）**
- 原假设：`create_backup` 只备份，仓库无恢复实现。
- 推翻证据：`app/erp/utils/backup.py:235` 存在 `restore_backup`，含 zip 成员校验与原子替换。
- 教训：记忆与笔记会过期。涉及"有没有某功能"的判断，必须回代码核对，不能用既有印象。

### 4.3 为什么会反复走错：一个共同的失效模式

上述 6 条中，B1、B2、B3、B4、B5 与 A3 共享同一个失效模式：**在证据不足处，用"看起来合理"完成推理跳跃**。具体形态有四种：

1. **外推范围**（B1）：把"暂缓窄屏改版"读成"否决 Android"。
2. **以弱证强**（B2）：用历史文档否定用户当下陈述。
3. **以形似代量**（B3）：把"结构相似"当成"可复用"，不折算成工作量。
4. **以机制代后果**（B4、B5）：把"缺保护"、"可复现"直接升格为"是缺陷、要修"，跳过"最坏后果是什么"这一步。

对应的纪律（后续讨论与派活都应遵守）：

- 区分 **"未定义"** 与 **"错误"**。需求没写的口径，先确认，再动手。
- 区分 **"可复现"** 与 **"已确认为缺陷"**。复现只是缺陷的必要条件。
- 区分 **"机制缺口"** 与 **"后果严重"**。严重性必须落到最坏后果。
- 证据强度排序：**用户当下陈述 > 仓库文档 > 推断**。低强度证据不能推翻高强度证据。
- 每个判断标注"已实测"或"推断"，并允许被推翻——本次 10 轮里，被推翻的判断远多于成立的。

## 5. 四条语义决定 + 第五条

以下为导入通道（档一核心）必须定义的语义。四条已定，第五条为本次新增的必要配套。

### 5.1 a. 客户名匹配不上（手机端输入的名字，店里档案没有）

**决定：标冲突，等人工裁决；不自动建档。**

- 理由（修正版）：原理由"复用既有运营习惯"不成立——"待补全"视图是**纯筛选**（`app/erp/templates/customers/list.html:50-51`、每行仅 [编辑][删除]），语义是"补联系方式"，与"选客户"不同。正确理由是：**复用两个现成组件**——预览页骨架（`templates/import_preview.html` + `ImportPreview`）与开单页联想选择器（`templates/orders/new.html:425`）。
- 界面**必须新写**（缺的只是"把联想选择器嵌进预览行的冲突格"），约 1–2 天。
- 若改为自动建档：`origin` 若沿用 `'order'` 会污染"待补全"视图（`routes/customers.py:59`、`:84` 精确匹配 `origin='order'`）；若改用新值（如 `'order_mobile'`），则该视图**不会**被污染，但手机建档且无联系方式的客户会**永远不会出现在待补全里**——从"污染"变成"隐藏"。用新值必须同时改三处：`routes/customers.py:59`、`:84` 的 SQL，以及 `services/master_data_quality.py` 的判定与标签表。

### 5.2 b. 商品名匹配不上

**决定：标冲突；并且手机端限制为"只选不建"，不允许手输新商品。**

**本条必须按"故意与桌面端不一致的产品差异"记录，不能表述为"消除了一个边缘语义"。** 因为桌面端**明确支持**手输自动建档，有三层证据：

- 代码：`app/erp/services/accounting.py`，商品名称未命中即 `INSERT INTO products(..., origin='order')` 并留痕（v14：商品身份只剩名称）。
- 界面：`app/erp/templates/orders/new.html:112`"没有匹配则会新建商品档案，之后可到商品页补全"。
- 需求文档：`docs/需求/消防器材店ERP系统-需求文档.md:12`"开单手输自动建档留痕"。

差异的理由：离线场景 + 主数据快照陈旧时，手机端新建的商品名**不可逆**——它立刻成为正式商品档案（v14 起名称即身份，没有可后补的「型号」维度），回店改名时撞唯一索引 `idx_products_business_identity`（`app/erp/db.py`，含软删除行），报「商品名称已存在」，而该商品已被单据引用、删不掉，店主卡死。

注意：该风险桌面端**同样存在**，只是桌面端用户在电脑前可当场改名，手机端不能。故这是"手机端更尖锐"，不是"手机端独有"。

落地必须补三个防护：

1. **`product_id` 一致性校验**：`product_id` 是店铺本地自增 id，手机端清单里的 id 是导出时的快照；店里删后重建会漂移，导致静默错单。手机端应以**规范化商品名称** `name` 为身份（v14 起型号已并入名称，没有 `spec` 维度），`product_id` 仅作校验，不一致即标冲突。
2. **客户价写脏防护**：`_select_existing_product` 在单价 **> 0** 时会 upsert 客户专属价（`accounting.py:359` 起；2026-10-15 起条件不再是「≠默认价」，档案默认价已下线）；手机离线拿到的旧价会被固化成客户专属价。导入时须区分"手机端显式设定的客户价"与"手机端当时读到的旧价"。
3. **新商品暂存通道**：只选不建意味着"门店遇到没卖过的商品"在手机上无法开单。需一个暂存机制（手机记下名字，回店提示"有 N 个新商品需先建档"）。

### 5.3 c. 同名但在回收站

**决定：继承开单路径——命中软删除即复用并恢复可见性。**

- 依据：该答案代码里已存在，只是未正式写下。开单路径 `app/erp/routes/orders.py:846-859` 故意不过滤 `deleted_at`，命中即恢复并留痕。
- "新建"被物理挡死：客户 `name TEXT NOT NULL UNIQUE`（`app/erp/db.py:755`）、商品唯一索引 `idx_products_business_identity`（`app/erp/db.py:209`），两者**均含软删除行**。故实际只有"复用恢复"与"报错"两条路，而报错会让整张单走不通。
- 现存不一致：导入侧对同名软删除记录是**报错**（`routes/customers.py:159-161`，文案在 `:160`），与开单侧不同。导入通道必须二选一，不得两条路径各一套。
- **风险降低措施（建议采纳，约 1 天）**：恢复时**不清空** `delete_reason`，改将其保留到可见处（如写入备注），使店主能看见"这条曾被删除及原因"。现状是恢复即清空（`routes/orders.py:845`），且 `audit_logs` **无界面**（全仓 routes/ 与 templates/ 无读取方），所以"曾删过"这一信息当前完全不可见。这是四条里唯一**不可逆**的一条（一旦被单据引用，被复活的档案就删不掉），故这 1 天是本次性价比最高的改动。

### 5.4 d. 手机端单据合计 ≠ 明细行合计

**决定：忽略文件里的合计，桌面端按明细重算；预览页显示"文件合计 X / 系统重算 Y"，且仅在差异非零时渲染。**

- 依据：`orders.total_amount_cents` 恒为算出来的（`accounting.py:398`、`:403`），无任何外部入口，且 orders 表无折扣字段（`app/erp/db.py:775-794`）。因此**结构上不存在"不一致"状态**——这不是"缺校验"，而是不存在该状态。
- 因此"以明细为准"**不是新增校验**，是沿用现有不变式：导入时根本不读取文件里的合计。
- 保留显示的价值：若手机端按浮点算（如 0.1+0.2），会与桌面端按分重算产生 1 分差异；桌面端存的是自己的数，两边都以为自己正确，且**导入那一刻是唯一能发现它的时机**。显示（不阻断）零成本地保住这个时机。
- 参考先例（反向）：`app/erp/services/purchase_returns.py:34` 用"对不上就报错"保护退拿货合计一致性。

### 5.5 第五条（本次新增）：主数据快照有效期

a/b/c 三条全部依赖同一前提：**手机端持有店铺主数据的最新快照**。a 要选客户、b 要选商品、c 要认出回收站。而档一的形态是"手机离线数天 → 回店导入"，手机端可能拿着过期清单，于是：

- 手机选了客户，回店时该客户已被软删 → 落入 c；
- 手机选了商品，回店时该商品名称已被修改 → `product_id` 漂移（见 5.2 防护 1）。

**故必须定义：手机端主数据快照的有效期，以及超期后的处理（强制重拉 / 警告 / 拒绝导入）。** 这不是新决策，而是上述四条落地的必要配套。阈值与处理方式待用户定（§9）。

## 9. 仍需用户拍板的点

以下为真正需要决策、且无法由技术推断替代的事项：

1. **档一还是档二。** 手机开的单是否算正式单？只作草稿、回店过账打印（档一），单号/成本/打印三条契约一条都不用动；要手机独立开正式单（档二），单号契约至少动，躲不掉。这一个选择决定几周还是几个月。
2. **S1 口径确认。** 不填日期时，导出与汇总的默认窗口应按销售数据算，还是按四类全部数据算？（需求文档未定义。）
3. **是否接受手机端"只选不建"作为与桌面端不同的产品差异。** 桌面端明确允许手输自动建档，手机端禁止是**故意不一致**，需写入需求文档。
4. **主数据快照的有效期与超期处理方式。** 超过多少天视为过期？过期是强制重拉、警告还是拒绝导入？
5. **（仅当选择方案甲或丙时）是否松绑"永久免登录"。** 联机方案必须重新决策该条；它是用户对风险的偏好，不是工程量问题。决策记录见 `docs/需求/2026-07-26_永久免登录.md`。
