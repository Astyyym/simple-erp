1. **客户问价格** → 商品价格、某客户的专属价

### 2.2 为什么是「第二个监听」而不是「改 host」

用户已授权修改 `127.0.0.1`，但**本方案主动不使用这个授权**。

理由（已实测）：

- `desktop_app.py:217` 是硬编码 `serve(app, host="127.0.0.1", port=resolve_port(), threads=8)`
- **waitress 的 host 是启动时绑定的 socket，运行中改不了**
- 要改 host 只能重启服务 → 桌面窗口闪一下 → 用户会以为程序崩了

**改用第二个监听后，净收益全是正的：**

| 收益 | 说明 |
|---|---|
| 主应用物理上不可能被局域网访问 | 安全边界从"靠门挡"变成"不在这条路上" |
| `tests/test_config_fallback.py:43` 断言不用改 | `host == "127.0.0.1"` 仍然成立 |
| 开关可热切换 | 不重启、不闪窗 |
| 回滚极简 | 关开关即回滚 |

> **这一条是本项目最值得记录的一次决定：用户授权了，我们查完发现不用改、也不该改，于是主动退回授权。**

### 2.3 端口规则：固定 5001，不漂移

| 情况 | 行为 |
|---|---|
| 5001 可用 | 正常启动 |
| 5001 被占 | **开关自动回弹到关** + 设置页明确报错（"端口 5001 被占用，可能是上次没退干净"） |
| 用户手动改端口 | 允许，但**必须先撤销所有已配对设备**，再启用新端口 |

**为什么不能自动回退到 5002**：端口是配对 base_url 的一部分。自动回退会导致已配对手机静默失联，且防火墙规则可能重复弹窗。**漂移的失败是静默的，报错的失败是可诊断的。**

退出时必须 `server.close()` + 等线程结束，否则下次启动端口仍被占。

### 2.4 局域网 IP 会漂移（新增，2026-10-17）

`192.168.10.5` 是否是 DHCP 保留地址**未验证**。若不是，路由器重启或租约到期都可能换成 `192.168.10.x` 里的另一个值，症状与「电脑没开」一模一样：手机打开就是连不上，而电脑端一切正常。

三条必须做：

1. **路由器上把该 MAC 绑定为固定 IP**（DHCP 保留）——做了最彻底，但这**不是开工前置**：
   - 本机实况（2026-10-17 查到）：WLAN 网卡 MAC `C8-5E-A9-F1-9A-3C`，地址 `192.168.10.5`，网关与 DHCP 服务器同为 `192.168.10.1`。绑定时认准 WLAN 这一张，不是以太网的 `BC-EC-A0-05-BF-A6`。
   - **进不去路由器、或它没有 DHCP 保留功能时，直接放弃这一步**，用地 2 条兜底即可——DHCP 租约本来就会把同一地址优先续给同一台机器，这是降低偶发故障，不是消除必需项。
2. 设置页始终显示**当前局域网 IP + 端口 + 可访问性自检结果**。IP 变了店主能看见，而不是只能问「为什么手机又连不上」。
3. 浏览器方案下地址是用户扫码/手输存进快捷方式的，**IP 一变旧快捷方式即失效**，所以页面顶部要显示当前地址方便他重存；第二步的 APK 必须支持「重新扫码改地址」，不得把 base_url 编译进包里（见 §3.1b）。

## 4. 不可动的约束（写进 `routes/mobile.py` 顶部注释 + 本文档）

1. **不调 `customer_balance_cents()`。** 它在 `app/` 内**零调用**（已实测，只有 `tests/` 里 18 处断言在调），是孤儿函数。余额只用 `get_customer_account_ledger()`（`accounting.py:962`），那是桌面端在用、有测试覆盖的权威实现。
2. **`mobile_bp` 外一律返回 404，不是 403。** 403 会告诉扫描者"这里有个东西"。
3. **`mobile_bp` 只允许 GET；唯一例外是配对提交本身（`POST /m/pair`）。** 除此之外永不添加写接口，包括「记录一次查看」这类看似无害的写。
   - 这个例外**必须存在**：配对要用户提交 6 位码，只能 POST；用 GET 带查询参数会把配对码写进浏览器历史与访问日志。
   - 例外的作用域是安全边界：**它只写 `data/mobile_devices.json`，绝不写 `erp.db`**；除它之外，手机端所有查询走只读连接（约束 9）。
   - 它也**不能经过** `reject_cross_origin_mutations`（`__init__.py:142`，对 GET 是 no-op、对 POST 生效）——这正是第二监听必须用独立 app 的原因（约束 8）：独立 app 不注册该 hook，配对 POST 就不会收到「跨站写请求已拒绝」这种误导性报错。
   - 反过来，若把 `mobile_bp` 注册进主 app，本约束就自相矛盾：配对 POST 必然被那个 hook 拦下。
   - **设置页同样没有写端。** 主题切换只是本地 `data-theme`，"重新配对"是跳到配对页，**没有"解除本机配对"按钮**——那会变成第二个写端。彻底断开只能在桌面端撤销设备（§6 第 19 条）。
4. **第二监听端口固定 5001，不自动漂移。**
5. **主应用 5000 永绑 `127.0.0.1`。**
6. **阶段一移动端不落本地数据。** 撤销设备即彻底失联——这是"手机丢失风险低"的依据。将来有人加缓存就悄悄破掉这条，必须在代码注释里注明。
7. **"只读"必须由测试保证，不能只靠代码里的 `if`。** 至少 6 条 pytest：

| 测试 | 断言 |
|---|---|
| 蓝图外 404 | 用**独立 app** 的 test client 访问 `/customers/` → **404**（不是 200） |
| 非 GET 拒绝 | `POST /m/customers` → **405**；`POST /m/pair` 是唯一例外，且不写 `erp.db` |
| 未配对跳转 | 无 cookie 访问 `/m/customers` → **302 到配对页** |
| 已配对放行 | 有效 cookie → **200**，且 HTML 里不含删除/作废按钮 |
| 余额对拍 | 同一批客户，`customer_balances(ids)` 与 `get_customer_account_ledger()` 的 `current_balance_cents` **逐个相等** |
| 物理只读 | 手机端连接 `PRAGMA query_only` = 1，或对 `orders` 执行 `INSERT` 抛 `OperationalError` |

> 不写这 5 条，"只读"就只是口头承诺：任何人一次重构就能破掉，而且破掉之后不会有任何测试失败。

8. **第二监听必须是独立的 Flask app，不得复用 `create_app()`。** 两条理由都是硬的：
   - `create_app()`（`__init__.py:81`）注册了全部 9 个蓝图并执行 `init_db()`（含迁移）。复用它，`/customers/` 就是 200，约束 2 的「蓝图外 404」直接失效——而更容易发生的是有人把那条 404 测试删掉。
   - 独立 app 只需：注册 `mobile_bp`、挂 `static`、按需注入 jinja 全局（移动端不打印，`slip_size` 那一套**不需要**）。它**不得**调用 `init_db()`——迁移只由主应用跑一次。
   - 数据根不必另传：`db_path()` 走 `project_path()`（`config.py:159`），同一进程内天然与主应用一致。**禁止**为第二监听新起进程或另指定 `ERP_DATA_ROOT`。
9. **手机端所有查询走只读连接**：`sqlite3.connect(f"file:{db_path()}?mode=ro", uri=True)` + `PRAGMA busy_timeout`。理由：`get_db()` 没有 `busy_timeout`，主应用 `threads=8`（`desktop_app.py:217`）正在写（`BEGIN IMMEDIATE`）时，手机端读会撞 `database is locked`；而 `mode=ro` 让「只读」成为**数据库层的物理保证**——代码写错也写不进去。这比约束 7 的测试约束更强，两者都要有。
10. **局域网 IP 必须在路由器上做 DHCP 保留**，且设置页始终显示当前 IP + 端口 + 自检结果（见 §2.4）。IP 漂移的症状与「电脑没开」完全同形，不显示地址就无法排查。
11. **新增依赖只有 `qrcode`（纯 Python），且必须同步进两处**：`requirements.txt`，以及 `简单ERP.spec` / `简单ERP-demo.spec` 的 `hiddenimports`；`templates/mobile/`、`static/css/mobile.css`、`static/js/mobile/` 必须进 spec 的 `datas`。漏了这一步，源码运行一切正常、装出来的 EXE 上手机永远 404/500，而且**没有任何测试会失败**。

## 5. 产品口径与已定案事项

### 5.1 「今天开了多少单」的口径（**已定：4 种开单类型全算**）

**2026-10-17 用户定案：算 4 种开单类型**——销售单、退货单、拿货单、退拿货单。

但这四种类型**不在同一张表**（已实测）：

| 类型 | 标签 | 表 |
|---|---|---|
| `sale` | 销售单 | `orders` |
| `return` | 退货单 | `orders` |
| `purchase` | 拿货单 | `purchase_orders` |
| `purchase_return` | 退拿货单 | `purchase_return_orders` |

而现成的今日历史是**两个函数，合起来正好覆盖 4 类**（2026-10-17 复核，第一版只找到了前一个）：

| 函数 | 位置 | 覆盖 | 日期列 | 状态过滤 |
|---|---|---|---|---|
| `_today_history()` | `routes/orders.py:672` | 销售 / 退货 | `order_date` | `IN ('saved','printed')` |
| `_purchase_today_history()` | `routes/purchases.py:118` | 拿货 / 退拿货 | `business_date` | `='saved'` |

**所以 S6 不是「从零写跨三表 UNION」，而是「合并这两个函数的返回值，再按类型分组求和」。** 这不是在说省事——第一版写「必须做跨三表 UNION」是错的，照它做会重写一遍已经在用的 SQL，并引入新的口径偏差。

**三条必须照抄、不许自创的口径：**

1. **状态过滤逐表照抄**：`orders` 用 `IN ('saved','printed')`，而 `purchase_orders` / `purchase_return_orders` 用的是 `status='saved'`（`accounting.py:956-957`）。假设三张表一致会出错。
2. **日期列名不同**：`orders.order_date` vs 另两表的 `business_date`。合并时要用别名统一（`orders.py:372` 已示范 `o.order_date AS business_date`）。
3. **金额符号照抄**：退货单库里已是负数，拿货/退拿货是正数、符号只在余额口径里加（详见下面「符号不需要自创」）。

成本由 1–1.5 上调至 **1.5–2.2 人日**（+0.5–0.7）：主要工作从「写 UNION」变成「两处返回值归一 + 两段小计 + 对拍测试」，跨表口径仍要逐表确认。详细实现要求与对拍测试见开发短计划 §2.1。

**呈现方式已定（2026-10-17，二次修订）**：按 4 类分组 + **两段小计，不显示单行总计**。

```
今天  10月17日  周六

卖货
  销售单      5 单   ¥3,980
  退货单      1 单   ¥  -300
  卖货净额             ¥3,680

进货
  拿货单      2 单   ¥1,200
  退拿货单    0 单   ¥    0
  进货净额             ¥1,200
```

四条约束：

1. **顺序固定**为销售 → 退货 → 拿货 → 退拿货（同 `filter_chips.py:19` 的 `ORDER_TYPE_ORDER`），不自定义。
2. **某类为 0 仍显示该行**（显示 `0 单 ¥0`），否则"今天进过货吗"无法从界面回答。
3. **不显示任何成本或利润数字**——v15 已删成本链，且手机是移动设备，进价泄露风险高于桌面。
4. **不做四类相加的总计。** 第一版曾写「合计 8 单 ¥4,880」，那是把卖货净收入（3,680）与进货支出（1,200）相加；4,880 既不等于今天收到的钱、也不等于今天的利润，符号还与余额口径相反（余额里拿货是**减项**，`accounting.py:1044` `-po.total_amount_cents`）。桌面端也从来没有这个数：开单页与拿货页各自显示各自的「今天已开单」，两条路都不产生四类合计——所以「照抄桌面端」在这条上**无源可抄**，它本身就是自创。

**符号不需要自创**（第一版没写清，实现者只能自己发明）：`orders.total_amount_cents` 的退货单**库里存的已经是负数**（`accounting.py:382` `sign = -1 if order_type == "return"`，`:427` `total += subtotal * sign`）；拿货/退拿货存正数，符号只在余额口径里加。所以：

- 显示销售 / 退货：直接 `cents_to_yuan(total_amount_cents)`，退货自然是负号；
- 显示拿货 / 退拿货：直接显示原值；
- **两个「净额」是唯一需要在手机端做减法的地方**：卖货净额 = 销售 + 退货（退货已是负数，即相加）；进货净额 = 拿货 − 退拿货。

### 5.1b 为什么选分组而不是一个总数

四类单据性质不同（卖货 vs 进货），混成一个总数无法回答"今天做了什么"。分组后每行可点击跳转对应类型的单据列表，成本为 0（只是传 `order_type` 参数）。

合并实现上的两个细节：**单数用 `len(rows)` 统计，不要为计数再查一次库**；两函数的排序都是 `id DESC`，合并后需按「类型顺序 → id」重排，否则四类会交错。

### 5.2 金额显示（**2026-10-17 晚修订：列表也显示精确金额**）

**原定案（同日早）：列表分档、详情精确。** 理由是柜台前手机/平板会被隔壁客户看到，精确欠款会得罪人。

**2026-10-17 晚用户看到实物后改口**：「标签不要写小于一千、一千到1万，直接把它具体数字写出来」。

- 客户列表、单据列表、客户详情头部都显示精确金额，不再出现 `无欠款 / <1千 / 1千–1万 / >1万` 分档。
- 隐私顾虑由用户自行承担（柜台展示角度）；将来若要恢复分档，必须重新征得用户同意。

### 5.3 客户详情「半详情」（**已定：做**）

**2026-10-17 用户定案：做。** 内容 = 余额三段 + 最近 10 笔流水（不做日期筛选、不做全量分页）。成本 0.8–1，已计入 S5（5.3–6.5）。

不做的话，埋点测不出"用户要不要详情"，阶段二就是盲做。

### 5.4 商品价页（**2026-10-17 晚二次修订：商品优先**）

**原定案（同日早）：1 屏。** 商品列表内联「该客户专属价」与「最近成交价」，不拆详情页。

**第一次修订：加商品详情。** 卡片可点进 `/m/products/<id>`，看这个商品在每个客户处的专属价。

**第二次修订（2026-10-17 晚真机反馈，最终形态）：**
- 商品价页**不再先选客户**：直接搜商品名/拼音，列表卡片显示「N 个客户 + 价格区间」；点进商品详情看每个客户的具体价格、更新时间与差额。

- 客户优先只作为从属入口（从客户详情进入商品视角），不再是商品价 tab 的前置条件。

理由：店主核对价格是双向的（客户 → 有哪些商品价 / 商品 → 每个客户什么价），只给客户优先就把另一半藏起来了。手机端仍只读，不改 `mode=ro` 与现有路由只放 GET 的约束。执行记录见 `开发短计划/2026-10-17_手机端功能补齐与壳手感_执行计划.md`。

### 5.5 改成浏览器直连后，兜底页大面积失效（新增，2026-10-17）

第一版的 S8 是「兜底页 + 诊断」，前提是**我们自己的壳**能在连不上时渲染页面。浏览器方案下这个前提不成立：

| 场景 | 用户实际看到 | 我们能做什么 |
|---|---|---|
| 电脑关机 / 手机不在同一 WiFi | **Chrome 自己的 `ERR_CONNECTION_REFUSED` / `ERR_ADDRESS_UNREACHABLE`** | 什么也做不了——请求根本没到服务器 |
| 端口被占、服务没起来 | 同上 | 什么也做不了 |
| 能连上但查询慢 | 我们自己的骨架屏，5 秒后转成明确失败提示 | 可以做，且必须做 |

所以：

1. **「三种空状态可区分」这条验收要改写**：浏览器方案下只剩两种可区分——「能连上但没数据」和「能连上但还在加载」。第三种（连不上）由浏览器负责，我们无法定制。
2. **诊断信息必须搬到桌面端设置页**，而不是手机页面：显示监听地址、端口、是否在监听、防火墙提示、最后一次手机成功请求的时间。店主发现手机打不开时，先在电脑上看一眼。
3. 包了 APK 壳之后兜底页才真正有用（那时它才可能拦截失败请求）。所以「手机端兜底页」应写成**第二步的前置**，本步只做超时降级。
4. **微信扫码会进微信内置浏览器**，cookie 行为与系统浏览器不同，通常也无法「添加到主屏幕」。交付说明必须写明：**用系统相机或 Chrome 扫码，不要用微信扫一扫**。这条要真机验（见 §8.2）。
5. **三态已补齐（2026-10-17）**：骨架屏、空数据、连不上三张都已画（设计稿 `designs/simple-erp-mobile-readonly/`）。其中「连不上」页**只覆盖「服务在但超时」**——电脑关机、不同 WiFi 时请求根本到不了服务端，浏览器自己接管错误页，看不到这张。它的完整价值要等第二步包了 APK 壳之后。

### 5.6 单据页的日期筛选（新增，2026-10-17 用户补充）

**不是只能看当天。** 单据页要有日期筛选，粒度：年 / 月 / 日，并能清空成「全部时间」。

**不要自己发明换算规则**——桌面端已有现成的：`routes/orders.py:300` 起调 `_resolve_date_range()`，接受 `date_mode` / `start_date` / `end_date` / `start_year` / `start_month` / `end_year` / `end_month`，统一产出 `start_date`、`end_date` 两个边界。

| 手机端选择 | 等价区间 |
|---|---|
| 2026 年 | `2026-01-01` ~ `2026-12-31` |
| 2026 年 10 月 | `2026-10-01` ~ `2026-10-31` |
| 按日，起止选同一天 | 该日 ~ 该日 |
| 按日，起止不同 | 起 ~ 止（**两端都含**） |
| 全部时间 | 不加日期条件 |

**按日档有两个独立日期：开始日期、截止日期**（2026-10-17 用户补充）。默认两者都是今天。它对应的是 `start_date` / `end_date` 两个边界，不是"单一某天"——桌面端本来就是区间查询，手机端不必降级。

SQL 条件照抄桌面端：`orders` 用 `o.order_date >= ? AND o.order_date <= ?`（`orders.py:335-336`），拿货/退拿货用 `business_date`（`:351-352`）。

**默认落在「今天」**，与今日概览一致；右上角日期按钮打开底部 sheet，三档（年/月/日）+ 四个快捷（今天/本月/今年/全部）。

**年份从左到右递增：2024 → 2025 → 2026**（2026-10-17 用户要求）。理由：用户是右撇子，拇指主要活动区在右下；把最新的 2026 放最左，等于每次选当前年份都要让拇指横穿整个面板。这条同样适用于「按年」网格和「按月」上方的年份切换条。

**滚动条不得占位**：`.body` 与 `.sheet` 都用 `scrollbar-width: none` + `::-webkit-scrollbar { width: 0; display: none }`，隐藏滚动条但保留滚动。Windows 经典滚动条约 15px 宽，一出现列表卡片就横向缩 15px、所有行跟着跳一下——这是移动端最不该有的廉价感。实测四张列表截图（今天/本月/全部/时间轴）卡片宽度恒为 **354px**（390 − 2×18），无挤压。

**类型筛选与日期筛选可叠加**，互不覆盖。列表按「日期 + 时间」倒序，同一天内按时间倒序。

### 5.7 动效口径（新增，2026-10-17）

**先记住：这是服务端渲染的多页应用，不是 SPA。** 页面之间是浏览器整页导航，所以：

- **没有页面转场动画**——不存在「从今日滑到客户」这种交互。要做得启用 View Transitions API（跨页需同源 + Chrome 111+，且失败静默），为一个过场给全部服务端路由加实验性依赖，不划算。
- **不做数字滚动 / 金额跳动**：柜台场景要一眼读准数，动画只会让读数变慢。**这条要写死，别被当成"待优化"加进来。**
- **不做列表入场 stagger**：长列表在千元机上掉帧，且每次翻页都重播。

**只做四处**（设计稿已实现）：

| 位置 | 动效 | 理由 |
|---|---|---|
| 骨架屏 | 1.4s shimmer 循环 | 让「在加载」和「卡死」可区分 |
| 日期 sheet | 0.18s 上滑 | 交代它从哪来 |
| 按钮 / 行 | `:active` 轻微缩放 | 触屏没有 hover，按下需要反馈 |
| 主题切换 | 0.18s 背景与文字过渡 | 避免切深色时闪白 |

**骨架屏延迟 150ms 再出现**（实现规则，不是视觉参数）：局域网正常请求常 100ms 内返回，立刻挂骨架会闪一下再消失，比不显示更烦。规则是——请求发出后 150ms 内返回就直接渲染内容，超过 150ms 才显示骨架。

全部动效在 `prefers-reduced-motion: reduce` 下关闭。

## 7. 工作纪律（写给后来人）

### 7.1 「新增 vs 已有」检查项

> **任何"这个数是新增的 / 这个功能是新做的"结论，必须同时回答两件事：**
> 1. 这个数/功能在**桌面端别处**有没有？（查页面、查 API、查 service 调用者）
> 2. 如果有，手机端的**显示口径**和它一致吗？

**依据**：本次讨论中，同一个错误出现了三次——整库拷贝列清单不全、聚合范围未列全、`customer_balance_cents` 零调用者被当成权威实现。

### 7.2 「临时实现」检查项

> **任何"为了兼容/为了快"的临时实现，必须在独立目录，且写明删除日期。** 不允许"在正式实现上打补丁升级"——补丁会留下简化版的痕迹（如明文 token 字段）。

### 7.3 「先问什么时候用」

> **在讨论"怎么做"之前，先问"什么时候用"。**

本次讨论花了 13 轮设计手机 App，到第 13 轮才发现没人问过用户"什么时候会打开它"。这个错误不会报错，只会安静地交付一个没人用的东西。

### 8.2b 真机实测（2026-10-17，源码模式，安卓手机 + Chrome，同一 WiFi）

以下 §8.2 里的推断条目已被真机验掉，结论以此为准：

| 项 | 实测结果 |
|---|---|
| Chrome 在 http（非 secure context）站点上「添加到主屏幕」并保留 cookie 会话 | **可以**。添加到主屏幕后从桌面图标点开，**不需要重新配对**（cookie 保留） |
| 微信内置浏览器能否打开同一 http 站点 | **能打开**（各页可浏览）。微信内「添加到主屏幕」与 cookie 是否与系统浏览器共享：**按已知限制关闭**（2026-10-17 用户判断）——微信内置浏览器没有「添加到主屏幕」入口，cookie 容器隔离也不是本项目能改的；要像 App 一样用（桌面图标、免重配对）仍须**系统相机或 Chrome 扫码** |
| 手机切 4G / 断开 WiFi | 打不开，浏览器原生错误页接管（与 §5.5 预期一致，不是缺陷） |
| 手机端今日单据与金额是否与桌面一致 | **一致**（用户逐项对拍） |
| 局域网能连通（手机 → 电脑的 5001 端口） | 通；服务端设备记录正常（配对时间、最后访问、来源 IP 均可查） |

**防火墙（2026-10-17 已用安装出来的程序验掉）**：

- **安装与启动都不弹窗**；只有在设置页点「打开手机访问」、让 `简单ERP.exe` **首次监听 `0.0.0.0:5001`** 时，
  Windows 弹一次「网络」提示。点「允许」后系统写入两条入站 Allow 规则（TCP/UDP，规则名「简单ERP Windows …」），
  手机随即连上。
- **源码模式看不到这个弹窗**：socket 实际由 venv 背后的基础解释器持有，那条路径早就有允许规则——
  所以「源码自测没弹窗」不能当成「不会弹」的证据，这一条只能靠装出来的程序验。
- **重装/升级不丢配对**：设备记录在数据根 `data/mobile_devices.json`（卸载不删数据），手机 cookie 在浏览器里，
  重装后扫码直接进、不再要配对码是**预期行为**。要断开只能在桌面端撤销设备。
- **同一台手机重复配对会多出记录**（无设备指纹）：设置页出现两条「Android 手机」属正常，撤销多余的那条即可。

### 8.3 已知的产品边界（必须告知用户）

- **第一步电脑关机 = 手机看不了，且看到的是浏览器自己的错误页**（用户已接受；那一页我们无法加任何文案，见 §5.5）
- **手机不在同一 WiFi = 看不了**（如用 4G 在外）
- **手机丢失**：撤销设备后彻底失联（数据不在本地，这是阶段一的安全优势）；阶段二加缓存后此优势消失，必须配缓存加密
- **两台无法自愈的故障**（用户需人工介入）：TUN 代理、端口被占。兜底页必须写"如果以上都不行，把诊断信息发给 ___"，那个空要填真人
