# 2026-07-11 ERP功能开发延误复盘与改进方法

> 项目：简单ERP
> 项目路径：`本地 Windows 仓库根目录`<br>
> 复盘日期：2026-07-11

---

## 一、事件概述

> 当前权威源码位置已更名为 `本地 Windows 仓库根目录`。本文保留 2026-07-11 复盘当时的事件语境；排查和交付原则仍适用，但其中的旧路径、旧服务状态不是当前运行证据。


本次任务原本是为ERP增加以下功能：

- 客户采购日历热力图；
- 日期悬停、单击和拖动区间查询；
- 客户商品购买排行；
- 单据查询中的全部／销售单／退货单筛选；
- 商品和客户Excel、CSV导入及模板下载。

用户已经较完整地说明了业务规则和交互方式。实际开发过程中，却因为任务状态判断、子代理管理、运行环境确认和真实页面验收连续出现问题，导致用户等待接近一个小时，且多次重启、刷新和查找实际没有显示在其页面中的功能。

本次延误的主要责任不在需求表达，而在AI没有正确区分：

```text
代码写入工作区
≠ 子代理任务完成
≠ 自动测试通过
≠ 当前服务已加载新代码
≠ Windows浏览器访问的是新服务
≠ 功能已完成并可以交付
```

---

## 二、主要问题与根本原因

### 2.1 把“代码正在写”错误地表达为“功能已经完成”

子代理只是在工作区中陆续写入代码，尚未完成：

- 独立审核；
- 全量测试；
- 实际页面验收；
- 运行服务确认；
- 用户端访问路径确认。

但AI在沟通过程中多次使用了“已经加载”“可以测试”“功能确实存在”等确定性表达，让用户误以为功能已经正式完成。

#### 根本原因

没有建立统一的交付状态标准，把“文件已修改”误当成“功能已交付”。

#### 改进方法

以后使用明确的五阶段状态：

| 状态 | 含义 | 是否可以通知用户验收 |
|---|---|---|
| 开发中 | 代码正在修改 | 否 |
| 已实现 | 功能代码已写入 | 否 |
| 已测试 | 专项及全量测试通过 | 否 |
| 已运行验证 | 真实服务和页面验证通过 | 否 |
| 可验收 | 从用户实际访问环境验证完成 | 是 |

只有达到“可验收”状态，才能通知用户打开页面测试。

---

### 2.2 过度依赖子代理完成通知，没有及时主动接管

两个子代理实际上较早就把代码写入了工作区，但异步完成通知没有正常返回。AI却一直认为任务仍在后台运行，没有主动判断其真实状态。

本可以通过以下信息及时判断：

- 文件最后修改时间；
- Git工作区状态；
- 是否仍有活跃任务或进程；
- 测试文件是否生成；
- 专项测试是否可以运行；
- 代码是否仍持续变化。

#### 根本原因

把任务控制权交给了异步通知机制，没有承担主控和超时接管责任。

#### 改进方法

子代理任务必须设置人工接管检查点：

1. 派发后记录任务目标和允许修改的文件；
2. 超过合理时间未返回时，立即检查文件、Git状态和修改时间；
3. 如果代码已经停止变化，则主代理直接接管；
4. 不继续空等异步完成通知；
5. 接管后自行运行测试和审核；
6. 子代理回传只能作为辅助信息，不能作为唯一完成依据。

---

### 2.3 验证了错误的服务

WSL内部访问：

```text
http://127.0.0.1:5000
```

能够看到新代码页面，但用户在Windows浏览器中访问相同地址时，实际连接的是旧的Waitress桌面版服务，并通过WSL转发进程处理。

因此出现了：

```text
AI工具看到新版页面
用户浏览器看到旧版页面
```

AI却没有在第一次出现矛盾时立即确认服务来源，而是继续让用户刷新和重启。

#### 根本原因

只验证了WSL内部网络路径，没有验证Windows用户实际访问路径，也没有检查端口对应的进程和响应服务器。

#### 改进方法

任何WSL Web项目在通知用户测试前，必须完成以下检查：

1. 检查WSL端口监听进程及PID；
2. 检查Windows端同一端口的监听进程；
3. 查看HTTP响应头，确认是Werkzeug、Waitress还是其他服务；
4. 从Windows侧请求页面；
5. 检查Windows侧返回的HTML是否包含本次新增功能标记；
6. 明确告诉用户应访问哪个地址和端口；
7. 如旧EXE与开发服务冲突，开发服务改用独立端口；
8. 不允许新旧服务共享一个容易混淆的入口。

推荐开发端口约定：

```text
正式桌面版：127.0.0.1:5000
WSL开发预览：WSL_IP:5001
```

### 2.4 面对用户截图，没有立即彻底推翻原判断

用户提供的截图已经明确显示：

- 商品管理页没有“下载Excel模板”；
- 没有文件选择框；
- 没有“批量导入”。

这已经证明AI之前关于“功能已加载”的判断不成立。但AI最初只解释为“开发中的半成品”，没有立即检查Windows侧真实服务。

#### 根本原因

没有把用户截图作为最高优先级的真实证据，仍然试图用已有判断解释矛盾。

#### 改进方法

当用户提供截图、视频或真实操作结果，与自动测试或工具结果冲突时：

1. 立即以用户侧证据为准；
2. 停止要求用户继续刷新或重复操作；
3. 撤回原来的确定性结论；
4. 检查运行实例、端口、进程、缓存和构建版本；
5. 找到根因后再提供新的测试入口；
6. 不将问题归因于用户“可能没找到”或“可能操作错误”，除非有明确证据。

---

### 2.5 用自动测试通过代替真实用户路径验收

自动测试曾显示：

```text
53 passed
```

但这只能证明测试客户端中的代码逻辑通过，不能证明用户浏览器正在运行同一份代码。

模板下载接口、路由和HTML测试通过，也不能替代以下验证：

```text
用户的Windows浏览器
→ 实际连接到哪个进程
→ 该进程加载哪套代码
→ 页面是否真实显示并可以操作
```

#### 根本原因

把代码正确性验证放在了运行环境一致性验证之前。

#### 改进方法

验收必须分为四层：

1. **代码层**：语法、静态检查、单元测试；
2. **服务层**：路由、数据库、接口和模板响应；
3. **浏览器层**：真实页面显示、JavaScript、布局和交互；
4. **用户环境层**：从用户实际使用的Windows浏览器或桌面EXE完成验证。

四层全部通过后，才能使用“已完成”或“可以测试”。

---

### 2.6 在证据不足时反复给出确定性结论

本次过程中出现了多次过早结论，例如：

- “功能确实已经加载出来”；
- “直接打开这些地址就能看到”；
- “可以开始测试了”；
- “当前进程已经加载新代码”。

但当时并没有Windows侧真实证据。

#### 根本原因

为了快速回应而过早收束判断，没有保留必要的不确定性。

#### 改进方法

结论必须与证据等级匹配：

- 只看到代码时：说“代码已写入”；
- 只通过测试时：说“自动测试已通过”；
- 只在WSL看到页面时：说“WSL内部预览正常”；
- Windows侧也验证后：说“Windows浏览器可以验收”；
- 用户确认后：说“功能验收完成”。

禁止跨级表达。

---

### 2.7 让用户承担了本应由AI完成的排查工作

用户被多次要求：

- 重启Flask；
- 强制刷新；
- 检查是否停留在首页；
- 输入完整客户名称；
- 反复打开不同链接。

这些操作大多建立在AI错误的服务判断上。

#### 根本原因

没有先完成端口和运行实例排查，就将验证任务转移给用户。

#### 改进方法

用户测试前，AI必须先自行完成：

- 进程检查；
- 端口检查；
- 页面抓取；
- HTML标记检查；
- 浏览器视觉检查；
- 控制台错误检查；
- 测试数据准备。

用户只负责最终业务体验反馈，不负责帮助AI定位基本运行环境问题。

---

### 2.8 没有守住“先完成，再通知验收”的边界

正确流程应该是：

```text
需求确认
→ 写失败测试
→ 完成功能
→ 专项测试
→ 合并检查
→ 全量测试
→ 启动唯一且明确的开发服务
→ 从Windows浏览器真实验收
→ 通知用户测试
```

本次实际流程却是：

```text
需求确认
→ 子代理写入部分代码
→ 提前通知用户查看
→ 用户看不到
→ 猜测缓存或用户操作问题
→ 继续等待子代理
→ 再次提前通知测试
→ 仍然看不到
→ 最后才发现端口连接的是旧服务
```

#### 改进方法

以后建立强制“验收门”：

- 子代理完成不是验收门；
- 测试通过不是验收门；
- WSL内部页面可见也不是验收门；
- 只有用户实际环境验证通过，才允许进入“通知用户测试”阶段。

本次需求表达是清楚的，已经明确包括：

- 热力图颜色只由当天拿货总额决定；
- 悬停显示金额、次数和商品类型；
- 单击日期查询当天单据；
- 拖动选择时间段；
- 复用现有单据查询页；
- 前5／前10商品排行；
- 数量和金额双指标图表；
- 商品与客户Excel、CSV导入；
- 同名数据跳过；

- 日期格子查询后继续适用订单类型筛选。

因此，本次延误不能归因于用户表达不清楚。

## 四、今后ERP开发的标准执行流程

### 4.1 开发前

- 将需求写成Markdown并确认；
- 列出验收条件；
- 检查Git分支和工作区；
- 确认正式数据库和测试数据库隔离；
- 明确开发服务和正式服务端口。

### 4.2 开发中

- 按功能拆分任务；
- 子代理不得修改重叠文件；
- 新行为先写失败测试；
- 记录每个任务的文件范围和完成状态；
- 子代理超时后主代理主动接管。

### 4.3 合并后

- 检查所有未提交改动；
- 检查跨任务接口和模板变量；
- 运行专项测试；
- 运行全量测试；
- 执行语法检查和`git diff --check`；
- 确认测试未污染正式数据库。

### 4.4 真实运行验收

- 停止旧开发服务；
- 检查5000等端口是否被旧EXE或Waitress占用；
- 开发预览使用独立端口；
- 从Windows侧请求开发服务；
- 核对响应头和页面功能标记；
- 使用浏览器检查页面视觉和JavaScript控制台；
- 完整操作一次真实业务链路。

### 4.5 通知用户

通知中必须写清楚：

- 当前状态；
- 正确访问地址；
- 服务端口；
- 可测试的功能；
- 尚未完成的功能；
- 是否已经提交、推送、升级版本和打包。

不得把“部分完成”描述为“全部完成”。

## 五、强制检查清单

### 开发状态

- [ ] 子任务是否真的完成，而不是只写入部分代码？
- [ ] 是否仍有后台任务或失联子代理？
- [ ] 是否需要主代理立即接管？
- [ ] 所有改动是否已经合并检查？

### 测试与数据

- [ ] 专项测试是否通过？
- [ ] 全量测试是否通过？
- [ ] 测试是否使用临时数据库？
- [ ] 正式业务数据是否保持不变？
- [ ] `git diff --check`是否通过？

### 服务与端口

- [ ] WSL端口由哪个PID监听？
- [ ] Windows端口由哪个进程监听？
- [ ] 是否存在旧EXE、Waitress或转发服务？
- [ ] 响应头对应哪个服务器？
- [ ] 用户访问地址是否明确且唯一？

### 浏览器验收

- [ ] 从Windows浏览器访问是否成功？
- [ ] 页面是否包含新增按钮和功能区域？
- [ ] JavaScript是否正常执行？
- [ ] 控制台是否有错误？
- [ ] 页面是否存在裁切、重叠或错位？
- [ ] 完整业务交互是否实际操作成功？

### 对用户沟通

- [ ] 当前结论是否与证据等级一致？
- [ ] 是否错误地将半成品说成已完成？
- [ ] 是否要求用户执行本应由AI完成的排查？
- [ ] 用户截图是否被视为最高优先级真实证据？
- [ ] 是否明确区分已完成和未完成内容？

## 六、最终结论

本次延误的核心不是代码难度，而是AI没有正确管理以下四个阶段：

```text
开发
→ 运行
→ 验证
→ 交付
```

最需要长期遵守的原则是：

> 不能因为代码已写入或自动测试通过，就断言用户实际页面已经完成；更不能在没有确认运行进程、端口和用户真实访问路径之前，让用户反复刷新、重启和寻找不存在的功能。

以后必须以用户真实使用环境中的结果作为最终证据，并在完成全部验证之后，才通知用户开始验收。
